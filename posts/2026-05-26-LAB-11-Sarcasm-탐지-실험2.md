이전 실험을 이어서, Gemma 추론 함수를 작성해보자.

~~~python
import json
import re
import torch

def build_prompt(utterance: str, heart_rate: int = None) -> str: # build_propmpt(): 프롬포트 문자열 만드는 도우미
    """발화(+심박)를 받아 Gemma용 프롬프트 문자열 생성."""

    # 공통 지시문
    instruction = """당신은 한국어 대화 분석 전문가입니다.
주어진 발화의 표면 의미가 아닌, 화자의 진짜 의도(화행)를 분석하세요.

가능한 의도(intent) 라벨:
- SINCERE: 진심 어린 긍정/동의
- SARCASTIC: 비꼬기, 반어법
- FORCED_AGREEMENT: 마지못해 하는 동의
- UNCERTAIN: 판단하기 어려움

반드시 아래 JSON 형식으로만 답하세요. 다른 설명은 일체 금지.
{
  "intent": "SINCERE | SARCASTIC | FORCED_AGREEMENT | UNCERTAIN",
  "confidence": 0.0 ~ 1.0,
  "evidence": "판단 근거를 한 문장으로"
}"""

    # 입력 정보 구성 (심박 있으면 추가)
    if heart_rate is None: # 심박 없으면 -> 발화만
        context = f'발화: "{utterance}"'
    else: # 심박 있으면 -> 발화 + 심박 컨텍스트
        context = f'''발화: "{utterance}"
화자의 심박수: {heart_rate} bpm (평소 70 기준)'''

    return f"{instruction}\n\n{context}"


def ask_gemma(utterance: str, heart_rate: int = None) -> dict: # Gemma 호출하는 메인 함수
    """Gemma에 발화 분석을 요청하고 JSON dict로 결과 반환."""

    # 1) 프롬프트 문자열 받기 -> haert_rate가 none이면 utterance(발화)만, 있으면 심박 포함된 프롬포트 문자열이 들어옴
    prompt = build_prompt(utterance, heart_rate)

    # 2) Gemma chat template 적용
    messages = [{"role": "user", "content": prompt}] # LLM은 역할이 있는 대화 형식을 받음 -> user(사용자)가 prompt를 말함
    inputs = tokenizer.apply_chat_template(
        messages,
        add_generation_prompt=True,
        return_tensors="pt",
        return_dict=True,
    ).to(model.device) # gpu로 이동

    input_length = inputs["input_ids"].shape[1]

    # 3) 생성 (재현성 위해 greedy decoding)
    with torch.inference_mode(): # 추론 전용 모드 -> 학습 시에는 PyTorch가 gradient(미분값)을 계산하느라 메모리를 더 씀 -> 추론 모드 명시해서 메모리 절약 + 속도 빠름
        output_ids = model.generate( # output_ids에 입력 + 생성된 토큰 모두 들어가게됨
            **inputs,
            max_new_tokens=200,
            do_sample=False,  # greedy: 같은 입력 → 같은 출력
            # LLM은 매 토큰마다 다음에 올 토큰의 확률 분포를 계산 / True: 매번 다른 답, False: 매번 같은 값
        )

    # 4) 디코딩 (입력 부분 잘라내고 새로 생성된 부분만)
    generated_ids = output_ids[0][input_length:]
    raw_text = tokenizer.decode(generated_ids, skip_special_tokens=True).strip()

    # 5) JSON 파싱 시도
    try:
        # Gemma가 코드블록 ```json...``` 으로 감싸는 경우 대비
        json_match = re.search(r'\{.*\}', raw_text, re.DOTALL)
        if json_match:
            result = json.loads(json_match.group())
        else:
            result = {"intent": "PARSE_ERROR", "confidence": 0.0, "evidence": raw_text}
    except json.JSONDecodeError:
        result = {"intent": "PARSE_ERROR", "confidence": 0.0, "evidence": raw_text}

    # 6) 원본 응답도 같이 보관 (디버깅용)
    result["_raw"] = raw_text
    return result


print("ask_gemma 함수 정의 완료")
~~~

위 작성된 코드의 구조는 크게 함수 2가지이다.

#### build_prompt()

- 프롬프트 문자열을 만드는 도우미 함수

#### ask_gemma()

- Gemma 호출하는 메인 함수
- 즉, Gemma에 발화 분석을 요청하고 JSON dict로 결과를 반환하는 함수

#### return dict (intent, confidence, evidence, _raw)

- intent, confidence, evidence와 raw 데이터를 합쳐서 반환

위 함수가 동작하는지 간단한 테스트를 해보자

```python
test_result = ask_gemma("네 좋아요.")
print(test_result)
```

코드의 결과로

> {'intent': 'FORCED_AGREEMENT', 'confidence': 0.7, 'evidence': '맥락 정보가 부족하지만, 짧고 단정적인 긍정은 마지못한 동의일 가능성이 높다.', '_raw': '{\n  "intent": "FORCED_AGREEMENT",\n  "confidence": 0.7,\n  "evidence": "맥락 정보가 부족하지만, 짧고 단정적인 긍정은 마지못한 동의일 가능성이 높다."\n}'}

#### 결과를 분석해보자면)

- KoBERT: POSITIVE (0.884): 표면만 보고 긍정 / Gemma: FORCED_AGREEMENT (0.7): 진짜 의도를 의심함
- evidence(근거): "맥락 정보가 부족하지만, 짧고 단정적인 긍정은 마지못한 동의일 가능성이 높다."  
  -> 텍스트 단어만으로 유의미한 추론을 한 것

여기서 나는 **왜 Gemma는 0.7로 진짜 의도를 의심한듯한 결과가 나왔을까??**라는 의문이 들었다.  
이유는 KoBERT는 긍정/부정 분류만 학습했고 Gemma는 세상에 있는 거의 모든 텍스트를 학습했기 때문 -> 보는 깊이가 다름  
KoBERT가 나쁜 모델이 아니라 목적이 다른 도구(감정 라벨 예측이 학습 목표인 분류 모델)일 뿐이다.

### [ 인사이트 ]

#### 1. Gemma가 의심군은 잘 잡는다

- 표면 POSITIVE 발화 2개를 모두 의심군으로 정확히 분류
- KoBERT 단독으로는 0/2 (둘 다 POSITIVE)
- Gemma 단독으로는 2/2 (FORCED_AGREEMENT, SARCASTIC)  
  -> 더 큰 생성 모델은 텍스트만으로도 미묘한 화행을 잡을 수 있다라는 가능성..

#### 2. Gemma는 의심 쪽으로 편향됨 (False Positive 위험)

- 대조군(강한 POSITIVE)까지 FORCED_AGREEMENT로 판정
- evidence를 보면 "맥락 부족"을 의심 사유로 자주 듦  
  -> "맥락 없이 단발 발화만 주면 Gemma는 over-suspect한다"라는 가능성

```
[표면 분류]
KoBERT: 3/3 POSITIVE → 표면만 보면 다 좋은 회의
                                    ↓
[텍스트 심층 분석]
Gemma-A: 2/3 의심 → 의심 발화는 잡지만 대조군도 오버킬
                                    ↓
[멀티모달 통합 필요]
Gemma-B (다음 실험): 심박 정보 추가로
       → 의심군은 그대로 잡고
       → 대조군은 SINCERE로 회복?
```

### [ 인사이트 ]

#### Gemma의 "의심 편향(suspicion bias)"

- Gemma는 "강요된 동의"라는 라벨을 한 번 떠올리면, 어떤 추가 정보가 들어와도 그 라벨을 강화하는 방향으로 해석
- 발화 3에서 심박 68(정상)은 원래 SINCERE의 강한 단서여야 함
- 그런데 Gemma는 "심박수가 평소보다 낮음 = 강한 확신 없음" 이라고 역으로 해석
- 사람이라면 "심박 안정적이니까 진심이네"라고 봤을 텐데, Gemma는 의심 방향으로 해석한 것

> LLM은 confirmation bias(확증 편향) 경햐이 존재 -> 초기 가설을 강화하는 방향으로 새 증거를 해석

하지만 나는 한 가지의 결과만 보고 confirmation bias를 확정짓는것보다 대조군을 확장하는 방향으로 한 번 더 검증해보기로 했다.  
-> 대조군을 충분히 확장하려고 했지만 지난 실습의 결과에서 사용할만한 대조군 데이터가 하나밖에 없어서

#### 결과 해석

- 발화 3 케이스에 대한 결과: "화자의 심박수가 평소보다 낮고 발화 자체에 강한 확신이 없어 마지못해 긍정"
- 추가 대조군에 대한 결과: "심박수가 평소보다 높고, 맥락상 강한 확신보다는 상황을 일단락시키려는 듯한 느낌"  
  -> 즉, 어떤 심박값을 줘도 의심하는 방향으로 해석
  > Gemma는 프롬포트에 제시된 메타정보(심박 데이터)를 자신이 이미 내린 판단을 합리화하는 도구로 사용함  
  > 메타정보의 방향성(높음/낮음)과 무관하게 항상 동일한 결론을 강화함 **"post-hoc rationalization (사후 합리화)"**

***즉, 실험 전에 세웠던 가설 "심박 정보를 프롬포트로 통합하면 Gemma가 더 정확하게 화행을 판단할 것"에 비해  
데이터가 보여준 실제 결과는 "Gemma는 심박 정보를 받지만, 자신의 텍스트 기반 1차 판단을 강화하는데 사용한다. 따라서 단순 프롬포트 통합으로는 멀티 모달의 이점이 발휘되지 않는다."***

#### 4개 발화의 본질)

![](https://velog.velcdn.com/images/xorms/post/58501309-2ce3-4f62-b632-e2b8166b9ef7/image.png)

- KoBERT (표면 분류)의 결과는 전부 POSITIVE -> 표면만 보면 다 좋은 회의
- Gemma-A (텍스트만)의 결과는 의심군 2건에 다른 라벨을 부여(의심의 종류까지 구별)하고 대조군은 둘 다 같은 라벨을 부여
- Gemma-B (텍스트 + 심박)의 결과는 A와 완벽히 정답 분포가 같다 -> 심박 정보 추가가 결과를 바꾸지 못함

> 표면 모델은 위험을 놓치고(false negative), 생성 모델은 진심을 의심한다(false positive).  
> 단순 prompt로 멀티모달을 통합해도 LLM은 자신의 텍스트 판단을 합리화할 뿐이다.  
> 진정한 멀티모달 통합은 representation 레벨에서 이뤄져야 한다.
