# WiFi + HTTPS 더미 테스트 — 가장 큰 리스크를 Day 2에 없앴다

> 사전 준비 11일 일정에서 WiFi를 Day 2 첫 번째로 배치한 건 의도된 결정이었다.

---

## 왜 5/8에 WiFi부터였나

사전 준비 11일 일정을 짤 때 WiFi를 Day 2 첫 번째 작업으로 올린 이유가 있었는데, 단독 테스트 5개 중 외부 의존성이 있는 유일한 작업이었기 때문이었다. 카메라, 마이크, ToF는 부품과 코드만 있으면 됐는데, WiFi는 네트워크 환경이 변수로 들어오는 구조였다.

특히 802.1X(WPA2-Enterprise) 호환성이 불안했는데, 학교 WiFi가 이 방식이라서 `esp_wpa2.h`를 써야 하는 상황이 생기면 사전 준비 11일 전체 일정이 흔들릴 수 있었다. 가장 큰 리스크를 뒤로 미루면 나중에 더 아프다는 걸 이미 알고 있었으니까 Day 2에 박아뒀다.

---

## 시연 네트워크 환경 결정 — 학교 WiFi 통째로 폐기

본 작업에 들어가기 전에 먼저 "어떤 WiFi 환경에서 시연할 건가"를 결정했는데, 결론이 생각보다 빨리 났다.

**학교 WiFi(802.1X / WPA2-Enterprise) 지원을 통째로 폐기했다.**

근거는 세 가지였다.

첫째, `esp_wpa2.h` 호환성 리스크가 사전 준비 11일 중 가장 큰 위험 요소였다. 검증도 안 된 상태에서 학교 WiFi 지원 코드를 붙이면 테스트 환경 자체가 불안정해질 수 있었다.

둘째, 어차피 최종 시연 때는 모바일 핫스팟을 쓸 예정이었다. 발표장에서 학교 WiFi 802.1X를 그대로 쓸 수 없는 구조라서, 처음부터 모바일 핫스팟 기준으로 맞추는 게 맞았다.

셋째, 집 WiFi와 모바일 핫스팟이 둘 다 WPA2-Personal이라서 동일한 코드로 통합 환경이 가능했다.

이 결정 하나로 WiFi 본 작업 시간이 약 40% 단축됐다. 복잡한 엔터프라이즈 인증 없이 WPA2-Personal 단일 코드로 가면 됐으니까.

## 본 작업 (commit `3ec17d4`)

WPA2-Personal 통합 환경을 기반으로 더미 테스트를 구현했는데, 핵심 결정 사항들이 몇 가지 있었다.

**런타임 SSID fallback** — PRIMARY(집 WiFi) → FALLBACK(모바일 핫스팟) 자동 전환 구조로 만들었는데, 환경 바꿀 때마다 코드 수정하는 게 번거롭기도 하고 실수 여지도 있어서 처음부터 fallback을 넣었다.

**WiFiClientSecure + setInsecure()** — HTTPS 처리는 `setInsecure()`로 인증서 검증을 생략했는데, Let's Encrypt 인증서 적용은 11주차 Flask 서버 구성 단계로 미뤘다. PoC 단계에서 TLS 터널만 뚫리면 충분했고, 인증서까지 잡으려면 서버가 먼저 올라와야 해서 순서 문제였다.

**지수 백오프 자동 재연결** — base 1s × 2^retry, 최대 5회로 잡았다. 연결 끊겼을 때 재시도 간격이 고정이면 네트워크 혼잡 상황에서 더 안 좋아지는 패턴이라서 지수 백오프를 적용했다.

**ArduinoJson 7.4.3 더미 페이로드** — `device_id / event_id / rssi / slot` 4개 필드로 구성했는데, 실제 `/api/detect` 구조를 미리 흉내 낸 형태였다.

## 자체 검증 3단계

위임 프롬프트에 강제로 넣어둔 자체 검증 3단계가 이번에도 적용됐다.

- **① 효율성**: 통과
- **② 리팩토링**: 매직 넘버 const화 + 함수 분리 적용됐고, 위임 결과 출력에 수정 사항 명시됐다
- **③ 오류 방지**: 통과

컴파일은 4회 진행했는데 SUCCESS, 빌드 수치 변동 0%.

```
RAM:   13.8%  ( 45,252 / 327,680 bytes)
Flash: 25.8%  (861,777 / 3,342,336 bytes)
```

Day 1 컴파일(RAM 5.6% / Flash 7.6%)보다 많이 올라갔는데, WiFiClientSecure + ArduinoJson + 지수 백오프 로직이 올라간 만큼이었다. 아직 여유는 충분했다.

## 회고

Day 2에 가장 큰 리스크를 먼저 처리한 효과가 명확했다. 802.1X 지원을 폐기하는 결정이 처음엔 "기능을 포기하는 것"처럼 느껴졌는데, 막상 해보니 코드 단순도가 대폭 올라가고 테스트 환경도 안정해졌다. 어차피 쓰지 않을 코드를 붙이지 않는 게 맞는 판단이었다.

`setInsecure()`로 인증서 검증을 생략하는 부분은 졸작 한계점으로 문서에 명시해둘 예정이다. PoC 단계에서의 실용적인 선택이었고, Let's Encrypt 적용은 11주차에 제대로 할 거라서 지금은 이걸로 충분하다.
