# "지금 값이 같다"는 보증이 아니었다: 대조 가드 넷과 "모든 소리"라는 거짓말

## 감사에서 나온 "맞긴 한데 확인 장치가 없다"

발표 전 마지막 개발 구간이었다. 며칠 전에 전 계층을 훑는 감사를 한 번 돌렸는데, 거기서 나온 발견 가운데 꽤 많은 수가 같은 모양이었다. **값은 지금 맞는데, 맞는지 확인하는 장치가 없다.** 마침 서빙 중인 소리 분류 모델을 바꿀 후보도 하나 대기 중이어서, 모델을 바꾸기 전에 막아 둘 구멍부터 메우기로 했다.

하루 반 동안 한 일을 한 줄로 줄이면 "지금 맞는 것"을 "어긋나는 순간 시끄럽게 실패하는 것"으로 바꾸는 작업이었다. 서버가 켜질 때 모델의 라벨 순서를 대조하는 가드, 펌웨어와 서버 사이 그리고 녹음 도구와 학습 도구 사이의 대조 테스트, 현관 기기가 받는 응답 크기의 예산 테스트가 들어갔고, 대시보드에는 사진 자동 재시도와 "이전 알림 더 보기"를 붙였다. 그런데 하다 보니 주석에 적힌 이유가 틀린 곳, 같은 이름의 숫자가 사실은 다른 정의였던 곳, 화면 문구가 코드보다 많이 약속하던 곳이 줄줄이 나왔다.

## 라벨은 개수만 지켜지고 있었다

서버에는 이미 모델 출력 모양을 검사하는 장치가 있었다. 출력이 정해진 개수가 아니면 기동 단계에서 바로 터진다. 그래서 라벨 문제는 다 잡힐 줄 알았다.

실제로는 그 검사가 **개수만** 봤다. 모델 학습 폴더에는 라벨 목록 파일이 따로 있는데도 서버는 그 파일을 읽지 않았고, 서버 코드 쪽에 적어 둔 라벨 순서를 그대로 믿고 있었다. 만약 순서가 틀린 모델이 들어오면 개수는 맞으니 검사를 통과하고, 아무 오류 없이 화재경보와 초인종이 뒤바뀐 채로 돌아갈 수 있었다. 개수가 틀린 쪽은 터지니까 오히려 안전하고, 위험한 쪽은 **틀려도 조용히 도는** 쪽이었다.

그래서 기동할 때 그 목록 파일을 읽어 서빙 라벨 순서와 대조하게 했다. 동작은 이렇게 갈린다.

| 모델 폴더 상태 | 동작 |
| --- | --- |
| 목록 파일 없음(옛 모델) | 경고 한 줄을 남기고 그대로 기동 |
| 순서까지 일치 | 순서를 적은 경고 한 줄을 남기고 기동 |
| 순서 · 개수 · 이름 불일치, 또는 깨진 파일 | 모델을 올리기 전에 기동 실패 |

정본은 여전히 코드 쪽 목록이고, 파일은 대조 대상일 뿐 출처가 아니다. 파일이 없으면 막지 않고 경고만 남기는 것도 옛 모델을 그대로 띄울 수 있게 하려는 선택이었다.

실제 모델 폴더 셋(지금 서빙 중인 모델, 3차 재학습 결과, 교체 후보)을 대조해 보니 **셋 다 순서가 같았다.** 옛 3클래스 모델은 기동에 실패했고, 순서를 일부러 뒤집어 만든 임시 폴더도 기동에 실패했다. 지금 모델들의 라벨이 틀려 있었던 건 아니다. 막은 건 앞으로 생길 수 있는 위험이다.

## 가드를 부러뜨리다 내 테스트가 먼저 속았다

가드가 진짜 그 일을 하는지 보려고 일부러 부러뜨려 보는 검사를 돌렸는데, 여기서 내 쪽 실수가 하나 나왔다. 서브테스트 두 개가 같은 임시 폴더를 쓰고 있어서, "파일 없음" 케이스가 앞 케이스가 남겨 둔 파일을 읽고 **엉뚱하게 통과**한 것이다. 폴더를 케이스마다 나눈 뒤에야 그 케이스가 진짜로 잡히기 시작했다. 이로써 확인 원칙이 한 층 더 생겼다. 가드를 확인하는 검사도, 케이스끼리 상태를 공유하고 있지 않은지까지 봐야 한다는 것이다. 이 일로 제품이 틀리게 동작하거나 피해가 생긴 적은 없었고, 검사 자체를 만드는 단계에서 걸러졌다.

## 지금 같은 값에 "한쪽만 바뀌면 실패"를 걸다

다음은 같은 값이 두 곳에 따로 사는 경우였다. 펌웨어 헤더에 적힌 센서 영역 수와 서버 상수, 그리고 녹음 도구가 쓰는 파일 이름 규칙과 학습 도구가 쓰는 규칙이 그랬다. 지금은 서로 같으니 문제없다고 봤다. 같은 건 맞았다. 다만 두 곳이 따로 적혀 있어서, 한쪽만 고치면 아무도 모르는 구조였다.

그래서 테스트가 원본 파일을 직접 읽어 대조하게 했다. 지금 일치하는 값은 이렇다.

- 센서 영역 수 64 ↔ 64, 묶음 수 16 ↔ 16
- 녹음 파일 이름 규칙: 라벨 2 × 유닛 6 × 테이크 5 = 60조합이 양쪽에서 같게 읽힘

녹음 도구 쪽은 불러오는 순간 서버 설정 파일까지 읽어 버려서 import를 할 수 없었다. 그래서 코드를 실행하지 않고 **구문 트리로만** 읽어 대조했다.

여기서 반전이 하나 있었다. 녹음 유닛 이름에 밑줄을 쓰지 못하게 한 규칙이 있는데, 그 이유가 주석에 적힌 것과 달랐다. 주석은 "그룹 키 계산이 깨진다"고 했지만, 실제로 깨지는 건 **파일 이름 해석**이었다. 유닛 이름에 밑줄이 있으면 라벨이 `knock_a`처럼 읽혀 버린다. 규칙 자체는 맞았고, 틀려 있던 건 주석에 적힌 이유였다. 이유를 바로잡아 두었다.

테스트가 제대로 보고 있는지도 두 방향으로 봤다. 주석의 낱말만 바꾼 대조군은 통과했고, 값을 바꾼 변형은 실패했다.

다만 가드가 하는 일은 어긋나는 순간을 **드러내는 데** 있다. 두 곳을 사람이 같이 고쳐야 하는 구조는 그대로이고, 가드는 한쪽만 고쳤을 때 실패로 알려 줄 뿐이다.

## 응답 크기 숫자가 넷이었는데 다 맞았다

현관 기기는 서버 응답을 고정 크기 버퍼로 받는다. 유효 용량은 767바이트다. 응답이 여기 들어가는지는 이미 계산해 둔 값이 있었다고 생각했는데, 문서를 열어 보니 686, 689, 693이 따로따로 적혀 있었다. 거기에 이번에 테스트로 고정하려고 계산한 값은 737이었다.

넷 중 어느 것이 틀렸나 따져 보다가, 틀린 게 아니라 **세는 정의가 달랐다**는 걸 알았다.

| 값 | 정의 |
| --- | --- |
| 689 | 도달 가능한 한 조합을 손으로 써서 센 값 |
| 737 | 도달할 수 없는 조합까지 넣은 보수 상한 |
| 693 | 예전에 잡아 둔 보수 상한 |
| 686 | 측정 조건이 기록되지 않은 값 |

737이 나머지를 "정정"한 것도 아니다. 정의가 다른 값이라 서로 대체하지 않는다. 689와 737의 차이 48바이트는 필드별로 전부 분해됐다. 반면 693과 737의 차이, 그리고 686은 당시 가정이 남아 있지 않아 분해하지 못했다.

테스트는 보수 최악 응답이 767바이트 이하인지를 본다. 지금 737이라 여유는 30바이트다. 기기가 실제로 읽는 판정 필드는 응답 앞쪽 344바이트 위치에서 끝난다(키 정렬을 끄면 525).

덤으로 새로 드러난 사실도 있었다. 서버를 디버그 모드로 띄우면 응답이 들여쓰기 출력으로 바뀌어 보수 최악이 **890바이트**가 되고, 예산을 넘는다. 이건 확인된 사실이고, 그래서 디버그 모드를 어떻게 다룰지에 대한 운영 규칙은 아직 정해져 있지 않다.

작은 흠도 하나 남았다. 사전에 손으로 계산한 값은 약 735였는데 실측은 737이었다. 그 2바이트의 원인은 끝내 찾지 못했다. 계산에 쓴 스크립트를 남겨 두지 않아서 분해할 원본이 없었다. 짐작이 가는 후보는 있었지만 근거가 없어서 원인처럼 적지 않기로 했다. 이 일 역시 확인 원칙을 한 층 늘렸다. 같은 이름의 숫자를 나란히 놓기 전에 "무엇을 어떻게 셌는가"부터 맞춰야 하고, 사전 계산을 했으면 그 계산 스크립트도 남겨야 한다.

## 화면이 약속한 "모든 소리"

마지막은 대시보드였다. 알림 화면의 문구는 "감지된 **모든** 소리"였고, 나도 그렇게 믿고 있었다. 코드를 열어 보니 실제로는 서버 기본 한 페이지, 20건만 받고 다음 페이지 정보는 버리고 있었다. 문구가 코드보다 더 많이 약속하고 있던 셈이다.

먼저 문구를 "최근 감지된 소리"로 고쳤고, 숫자는 넣지 않았다. 서버 설정이 바뀌면 숫자가 박힌 문구가 다시 거짓말이 되기 때문이다.

그다음 "이전 알림 더 보기"를 붙였다. 누를 때마다 가져오는 개수를 20씩 늘려 최대 100까지 받는 방식이다. 페이지를 이어 붙이는 방식도 생각했지만, 새 알림이 들어오면 목록이 꼬여서 쓰지 않았다. 대신 값을 치른다. 100건까지 펼친 화면은 3초마다 목록을 다시 받는데, 테스트 클라이언트로 무압축 기준으로 재 보니 이렇다.

| 폴링 응답 | 크기 |
| --- | --- |
| 100건, 꽉 찬 행 | 101,456바이트 |
| 100건, 최소 행 | 48,556바이트 |
| 기본 20건 | 20,336바이트 |

즉 최대까지 펼친 화면은 3초마다 약 100KB를 다시 받는다. 이 대가는 알고 선택한 것이다.

사진에도 같은 종류의 문제가 있었다. 사진이 한 번 실패하면 카드에 실패 표시가 영구히 남았고, 재시도 코드가 없었다. 이제는 10초 간격으로 최대 6번 다시 시도한다(첫 요청까지 합쳐 카드당 최대 7요청). 보관 기한이 지난 사진처럼 영원히 안 뜨는 경우가 있어서 상한은 꼭 필요했다. 이 10초와 6회는 잠정값이다.

이 변경은 클라우드 작업 공간에서 가짜 서버, 임시 DB, 헤드리스 브라우저로 확인했다. 알림 130건, 45건, 3건 시나리오로 더 보기 버튼의 상태 전환을 봤고, 사진은 일시 실패, 계속 404, 계속 503, 주소 교체의 네 경우를 돌려 봤다. 화면 문구도 결국 동작 명세였다. 문구가 코드보다 많이 약속하고 있었다면 그건 버그였다.

## 아직 다 된 건 아니다

- **라벨 순서 가드는 기동 때 확인하는 장치다.** 모델을 교체했다는 뜻도, 교체 준비가 끝났다는 뜻도 아니다. 서빙 모델은 그대로이고, 교체 여부는 보드에서 재 본 뒤에 판단한다.
- 지금 모델들의 순서는 셋 다 맞았다. 막은 건 앞으로의 위험이다.
- 대조 가드는 어긋나면 실패로 드러나게 하는 데까지다. 두 곳을 사람이 같이 고쳐야 하는 구조는 그대로 남아 있어서, 동기화 문제가 없어진 게 아니다.
- 응답 크기 737은 686, 689, 693을 바로잡은 값이 아니라 정의가 다른 값이다. 693과 686이 737과 얼마나 어떻게 다른지는 분해하지 못했다.
- 디버그 모드에서 보수 최악이 890바이트로 예산을 넘는다는 건 사실 확인까지다. 그걸 어떻게 운영할지는 정해지지 않았다.
- 손계산 약 735와 실측 737의 2바이트 차이는 원인을 모른다. 계산 원본을 남기지 않았다.
- 대시보드는 가짜 서버 위의 헤드리스 브라우저로만 확인했다. 실제 사용자 화면이나 실제 현관 기기에서 확인한 기록은 아직 없다.
- 사진 재시도의 10초와 6회는 잠정값이다. 더 보기를 최대까지 펼친 화면은 3초마다 약 100KB를 받는다.
- 현관 기기의 2차 녹음 플래그가 특정 순간에 겹치면, 기기를 리셋하기 전까지 버튼과 자동 감지가 "처리 중"으로 무시될 수 있는 창이 있다. 코드는 고치지 않고 주석만 바로잡았다. 지금까지 관측된 적은 없고 창이 얼마나 긴지도 재지 않았다. 알고 받아들이는 위험으로 남겨 두었다.
- 데모 데이터에는 새로 생긴 "기타 소리" 클래스 점수가 여전히 빠져 있다.
- 서버 회귀 테스트는 이번 구간에서 210개에서 230개가 됐다. 이 수는 개발 보고를 합한 값이고, 전체를 새로 돌려 확인한 것은 아니다.

## 마무리

이번 구간의 작업은 거의 다 "지금 맞는 것"을 "틀리면 시끄러운 것"으로 바꾸는 일이었다. 두 파일이 같은 값을 갖고 있다는 건 지금의 사실일 뿐이고, 한쪽이 바뀌면 조용히 어긋난다. "지금 같다"를 "앞으로도 같다"로 바꾸려면 어긋나는 순간 실패하는 테스트가 필요했다.

그런데 그 일을 하다 보니 확인이 한 겹 더 안쪽으로 들어왔다. 값을 맞추는 것보다 **값이 어디서 왔는지**를 맞추는 쪽이 일이 더 많았다. 주석에 적힌 이유, 숫자를 센 방식, 화면 문구가 약속한 범위가 모두 값 못지않게 어긋나 있었다. 가드를 달아 둔 지금도 기기와 사용자 화면에서 확인할 것들이 남아 있고, 다음 확인은 그쪽이다.
