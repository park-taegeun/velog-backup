## 5/13 졸작 중간 발표

데모 시나리오 v1을 발표 자료로 들고 들어갔다. "기존 알림이 '딝동'으로 끝났다면, 본 시스템은 누가 왔고 뭐라고 말했는지까지 알려준다"는 컴셉을 부스 구성(폼보드 벽 + 인터콤 박스 + 책상)과 방문객 진입점 3가지(노크+발화 / 초인종 등록 사이클 / 화재경보 사람 검증 우회)으로 풀어내는 시나리오였다.

교수님 반응은 나쁜 않았고 별다른 피드백은 없었다. 피드백이 없으면 보통 "그대로 가도 된다"는 신호라서, 시연 시나리오 SSoT(decisions.md 카테고리 26)를 v1 그대로 확정하고 다음 단계로 넘어갔다.

## AWS 가입 — 정책이 바뀌었는지 몰랐던 부분

가입 화면 들어가서 가장 먼저 catch한 게 플랜 선택 화면이었다. 옆날 자료들 보면 그냥 "프리 티어"만 있고 12개월 무료 어쩌고 하는데, 실제로는 화면이 이렇게 바뀌어 있었다.

- **무료 플랜**: 200 USD 크레딧 + 6개월 + 자동 해지 (유료 전환 안 하면)
- **유료 플랜**: 기존 방식

2024년 7월부터 신규 가입자는 둘 중 하나를 골라야 하는 구조였고, 옆날 12개월 프리 티어는 적용 대상이 아니었다. 본 프로젝트는 EC2 t3.small 인스턴스를 11주차(7/26+)에야 띄울 예정이라 무료 플랜으로 충분히 커버 가능했고, 무료 플랜 만료일(2026-11-13)이 졸작 종료(9/30) 이후라 일정상으로도 안전했다. 그래서 무료 플랜으로 갔다.

11월 초쯤 유료 전환 여부를 다시 결정해야 하는데, 그건 졸업 후 활용 계획이 잡혀야 답할 수 있는 질문이라 그때 가서 결정하기로 미뤄다.

## AWS 보안 설정 4종

가입 직후에 보안 설정을 먼저 다 잡고 그다음에 작업으로 넘어가는 게 맞다고 판단해서 4종을 한 번에 처리했다.

| 항목 | 설정 내용 |
| --- | --- |
| MFA | Google Authenticator 등록 + 시크릿 키 별도 백업 |
| IAM 사용자 | ddingdong-admin 생성 + AdministratorAccess 정책 부여 |
| Budget — Zero-Spend | $0.01 초과 시 알림 (의도치 않은 과금 즉시 catch) |
| Budget — Monthly | 월 $100 기준 / 85% / 100% 단계별 알림 |

이후 작업은 전부 IAM 사용자로 하고, root 계정은 봉인하는 식으로 운영하기로 했다. AWS 계정 ID는 953926452053이고 이건 외부에 노출돼도 문제없는 값이라 트래킹용으로 메모에 남겼다.

Zero-Spend Budget을 굳이 별도로 둔 이유는 졸작 학부생 입장에서 "내가 모르는 사이에 뭐가 켜져서 과금되는 시나리오"가 제일 무서운 시나리오라서 그러였다. $0.01 초과만 돼도 알림이 오면 그날 안에 catch 가능하니까 위험 비용을 시간 단위로 압축하는 효과가 있었다.

## 카카오 디벨로퍼스 — 비즈 앱 심사를 피해가는 길

여기서 핵심 결정이 두 개 있었다.

### 결정 1: "나에게 보내기" memo API 채택 → 비즈 앱 심사 회피

카카오톡 알림 보내는 방법이 크게 두 가지였는데,

- **친구에게 보내기**: 비즈 앱 심사 필요, 사업자 등록증 같은 거 요구됨
- **나에게 보내기 (memo)**: 비즈 앱 심사 불필요, 개인 개발자 계정으로 충분

본 프로젝트는 타겟이 "1인 가구 청각장애인 본인"이라 결국 알림 받는 사람 = 카카오 계정 본인이었다. 즉 "나에게 보내기"만으로 기능 요구사항이 그대로 충족됐고, 졸작 단계에서 비즈 앱 심사를 거칠 이유가 없었다. 앱 ID는 1456718로 받아두고, 11~14주차에 진입하면 플랫폼 등록 / Redirect URI / 토큰 발급 / 메시지 테스트를 진행할 예정이다.

### 결정 2: talk_message scope를 "선택 동의"로 채택

scope 동의 방식이 3개 옵션 중에서 골라야 했는데, 카카오 디벨로퍼스 공식 문서 기준으로 "필수 동의" / "선택 동의" / "이용 중 동의" 셋이었다. 본인이 본인 계정에 동의하는 단순 구조라 가장 가벼운 방식인 "선택 동의"로 갔다.

"필수 동의"는 로그인 자체를 막아버리니까 OAuth 흐름이 무거워졌고, "이용 중 동의"는 메시지 전송 시점마다 동의 화면이 떠는 구조라서 졸작 데모 흐름에 안 맞았다. "선택 동의"는 OAuth 로그인 때 한 번 묻고 끝이라 11주차 토큰 발급 흐름이 가장 깔끔했다.

## 인수인계 패키지도 그대로 믿으면 안 된다는 catch

이게 사실 5/13의 진짜 핵심이었다.

매일 밤 3-set 루틴 중 Set 3(노션 PoC 트래킹 갱신) 작업할 때, 위임 프롬프트에 이런 지시를 넣어놓았었다.

> DB3 row A: "5/13 발표 후 카테고리 26 갱신 가능성" → 발표 종료에 따라 🟢 자동 전환

근데 Claude Code MCP가 실제 노션에 들어가서 DB3를 catch해보니까 그 row가 부재였다. 위임 프롬프트는 이전 채팅방(PoC-(N))의 인수인계 패키지에 명시된 "기존 row"를 그대로 신뢰해서 작성된 거였는데, 실제 SSoT인 노션을 직접 catch해보니 그런 row가 애초에 존재하지 않았다.

분기 처리로 해결은 됐다. DB2(발표 피드백 로그)에 5/13 발표 결과 row를 추가하고, decisions.md 카테고리 26 cross-reference로 SSoT 일관성을 유지하는 방식이었다. 작업 자체는 어렵지 않았는데, 패턴 자체가 더 중요했다.

## 보고 요약 vs 실제 SSoT 갑, 또 catch됨

이게 사전 준비 11일 동안 같은 패턴이 잡힌 게 6번째였다. 5/10 마이크 작업 때 한 번, 5/11 ToF 작업 때 한 번, 5/12 메모리 self-checkpoint 객관 검증 때 한 번, 그리고 5/13 노션 row 부재까지 누적되니까 슬슬 패턴이 보였다.

요점은 똑같았다 — 인수인계 패키지에 명시된 "기존 row / 카테고리 / 파일" 가정도 그대로 신뢰하면 안 되고, 실제 SSoT를 직접 catch해야 한다는 거였다. 채팅방 분리할 때마다 인계 패키지로 정보를 넘기는 구조라서, 이 인계 패키지가 한 번 잘못 적히면 그 다음 채팅방들이 다 그 가정 위에서 돌아가게 된다. 그래서 위임 작업 시점에 인계 패키지의 가정 자체를 한 번 더 검증하는 단계가 강제로 필요했다.

5/12의 메모리 self-checkpoint catch가 "AI 보고 요약 vs 실제 파일 갑"이었다면, 5/13의 노션 row 부재 catch는 "채팅방 인계 패키지 vs 실제 SSoT 갑"이었다. 같은 원리, 다른 layer.
