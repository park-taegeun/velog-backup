## 운영에서 드러난 문제들

### 이름이 비슷한 두 명령

발행 직후 첫 질문은 "이제 `/velog-sync`만 하면 위키까지 반영되나?"였습니다. 답은 "아니요"입니다.

| | `/velog-sync` | `/velog-wiki` |
|---|---|---|
| 하는 일 | 백업 레포·노션 대시보드·Memory 기록 | 원본 창고 저장 → 위키 정리 |
| 실행 위치 | 볼트 밖 | 볼트 안 |

둘 다 Velog를 다루지만 목적지가 다릅니다. 만든 사람도 헷갈리는데 몇 달 뒤의 나는 더 헷갈립니다. 이름이 비슷한 도구는 역할 표를 문서에 남겨둬야 합니다.

### 대화 속에 사라진 승인

졸업작품 시리즈의 공개 기준(교수 피드백 일반화, 계정 정보 가림 등)은 지난 작업 때 대화에서 승인했습니다. 그런데 새 세션의 Claude Code는 "그 기준은 이 대화에 없다"고 보고했습니다. 당연한 결과입니다. 세션이 바뀌면 대화는 사라집니다.

그래서 시리즈별 공개 기준을 스킬 파일(`.claude/skills/velog-wiki/SKILL.md`)에 고정했습니다. 기준에 없는 판단이 나오면 그 부분은 일단 비공개로 두고 묻게 했고, 답을 받으면 "스킬 파일에 추가할 한 줄"로 제안하게 했습니다. 판단이 쌓일수록 기준 파일이 두꺼워지는 구조입니다. **승인은 파일로 남겨야 승인입니다.**

이 수정을 볼트에 적용하는 패치 스크립트에도 안전장치를 넣었습니다.

- **해시 확인**: 볼트의 파일이 예상한 원래 버전일 때만 교체합니다. SHA-256 해시(파일 내용으로 계산한 고유 지문)가 일치하지 않으면, 즉 누군가 손으로 고친 흔적이 있으면 아무것도 바꾸지 않고 멈춥니다.
- **bash 3.2 대비**: macOS 기본 bash는 3.2라서, `set -u`(정의되지 않은 변수를 쓰면 즉시 멈추는 옵션)를 켠 상태로 빈 배열을 펼치면 오류가 납니다. 이 경우를 미리 막았습니다.

### 정합성 3중 대조

Velog 전체 글 수, 위키 수집기, 백업 레포의 숫자를 대조했습니다.

| 시리즈 | 위키 수집기 (시리즈 칸 기준) | 백업 (`/velog-sync`) |
|---|---|---|
| AI 생태계 탐험 로그 | 22 | 22 |
| 졸업작품 기록 | 95 | 94 |
| AI_LAB | 88 + 시리즈 미지정 1 = 89 | 90 |
| **합계** | **206** | **206** |

시리즈별로는 어긋나지만 **합계가 먼저 같은지**를 확인해 데이터 손실이 아님을 보였습니다. 차이의 원인 중 2개(같은 글이 Velog에 두 번 게시된 경우, 시리즈에 넣지 않은 글)는 확인했고, 1개는 확인이 남아 있습니다. 모르는 것은 모른다고 기록해 두었습니다.

## macOS 권한 사건 — 권한 대신 위치를 옮긴 이유

매일 22:00 Velog를 수집하도록 launchd(정해진 시각에 프로그램을 실행하는 macOS 시스템 서비스)에 등록해 두었는데, 자동 수집이 실패했습니다.

```bash
bash .tools/velog_schedule.sh status
#   last exit code = 126
cat _private/logs/launchd.err.log
# /bin/bash: .../Documents/AI-Vault/.tools/velog_daily.sh: Operation not permitted
```

exit 126은 "실행할 대상은 찾았지만 실행할 수 없다"는 뜻입니다. 원인은 macOS의 **TCC(Transparency, Consent, and Control)**였습니다. TCC는 문서·데스크탑·다운로드 폴더처럼 개인 자료가 있는 폴더를 앱별 허락이 있어야만 열 수 있게 막는 보호 장치입니다. 터미널 앱은 이미 허락을 받았지만, launchd가 백그라운드에서 띄운 bash는 허락이 없었습니다. 손으로 돌릴 때는 되고 예약으로 돌릴 때만 실패한 이유입니다.

선택지는 세 가지였습니다.

| 선택지 | 작업 시간 | 장점 | 문제 |
|---|---|---|---|
| A. `/bin/bash`에 전체 디스크 접근 권한 | 1분 | 가장 빠름 | 모든 백그라운드 bash 스크립트에 마스터키를 주는 셈 |
| B. 볼트를 보호 폴더 밖으로 이동 | 20분 | 권한을 늘리지 않음 | 경로에 묶인 설정을 모두 점검해야 함 |
| C. 자동 수집 끄기 | 0분 | 위험 없음 | 자동화 포기 |

**B를 골랐습니다.** 근거는 **최소 권한 원칙(Principle of Least Privilege)**, 즉 일을 하는 데 필요한 만큼만 권한을 준다는 원칙입니다. A는 이 스크립트 하나를 위해 내 Mac의 모든 백그라운드 bash에 전체 디스크 접근을 열어 주는 선택이라 정반대입니다. 게다가 git 레포를 iCloud와 동기화될 수 있는 문서 폴더에 두지 않는 편이 원래 안전합니다. 동기화 중인 `.git` 폴더는 깨지기 쉽기 때문입니다.

이전은 다음 순서로 진행했습니다.

1. 옛 경로를 기억하는 설정 점검 (이전 전에 목록화)
2. launchd 예약 해제
3. `mv ~/Documents/AI-Vault ~/AI-Vault`
4. 두 레포와 커밋 훅 연결 확인
5. 예약 재설치
6. Obsidian에서 볼트 다시 열기
7. Claude Code 점검 (`/lint`, 스킬 목록, 가드 차단 테스트)

```bash
bash .tools/velog_schedule.sh status
#   last exit code = 0
# 마지막 성공: 2026-10-18T20:58:06
```

숨은 함정도 하나 있었습니다. Obsidian 공식 스킬을 **project scope**(그 프로젝트 폴더에서만 쓰도록 설치하는 범위)로 설치했는데, 설치 기록(`installed_plugins.json`)이 옛 경로에 묶여 있었습니다. 1단계 점검에서 이 문제를 예측했고, 이전 후 실제로 스킬 2개가 사라진 것을 확인해 `/plugin`에서 project scope로 다시 설치했습니다. 다음 날 22:00, 첫 무인 실행이 7초 만에 exit 0으로 끝났습니다.

## 자동화를 멈춘 판단

지난 편에서 자동화 2단계(수집 + 정리까지 자동) 전환 조건을 "최근 14일 실행 5회 이상 + 사람이 AI 판단을 고친 횟수(correction) 1회 이하"로 정했습니다. 준비도 지표는 금세 "✅ 검토 가능"이 됐습니다.

그런데 숫자를 들여다보니 실행 5회가 모두 하루에 몰린 **백필(backfill, 밀린 데이터를 한꺼번에 채워 넣는 작업)**이었습니다. 2단계가 실제로 맡을 일, 즉 하루 1~2편을 조용히 정리하는 일은 한 번밖에 해보지 않았습니다. 지표는 통과했지만 지표가 재려던 것은 아직 증명되지 않은 상태였습니다.

세 관점에서 다시 검토했습니다.

| 관점 | 검토 내용 |
|---|---|
| AX (업무 도입) | 완전 자동으로 아끼는 것은 명령어 한 줄. 공개 레포라 결과 확인은 어차피 사람이 해야 함 |
| AI 엔지니어 | correction 지표는 사람이 대충 볼수록 좋아짐 → 굿하트의 법칙 함정 |
| 시스템 | 더 큰 위험은 다른 곳(공개 사이트의 모순 표시, 민감한 노션 자료)에 있음 |

**굿하트의 법칙(Goodhart's law)**은 "지표가 목표가 되면 더 이상 좋은 지표가 아니다"라는 원칙입니다. "AI 판단을 고친 횟수가 적으면 준비 완료"라는 기준은, 사람이 결과를 꼼꼼히 볼수록 나빠지고 대충 볼수록 좋아집니다. 자동화를 하고 싶은 마음이 검토를 느슨하게 만들면, 지표는 좋아지는데 품질은 나빠지는 구조입니다.

결론은 **"자동은 초안까지, 공개는 항상 사람"**을 최종 형태로 확정하는 것이었습니다. 지표를 고쳐서 다시 2단계를 노리는 계획도 철회했습니다. YAGNI(You Aren't Gonna Need It, 필요해지기 전에는 만들지 않는다) 원칙대로, 명령어 한 줄을 아끼려고 새 장치를 만들 이유가 없었습니다. 공개되는 글에서 사람의 확인은 없애야 할 비용이 아니라 **설계상 남겨둘 관문(human gate)**입니다. 실무에서 배포 승인을 사람이 하는 것과 같습니다.

## 평가 설계 — 시험지를 잘 만드는 법

지난 편에서 "쌓을수록 똑똑해진다"를 골든 질문으로 측정하기로 했습니다. 실제로 시험지를 만들어 보니 두 가지 함정이 있었습니다.

- **함정 1 — 교과서로 낸 문제를 교과서로 풀기**: 위키를 보고 문제를 내면, 위키에 있는 것만 나오니 위키가 항상 맞힙니다. 그래서 **정답은 반드시 원본에서** 확인했습니다.
- **함정 2 — 지금 풀 수 있는 문제만 내기**: 이러면 처음부터 만점이라 성장을 보여줄 수 없습니다.

그래서 목적이 다른 시험지 세트를 나눴습니다.

| 구분 | 회귀 테스트 | 성장 측정 |
|---|---|---|
| 목적 | 있던 지식을 잃지 않았는지 | 새 자료로 똑똑해졌는지 |
| 정상 점수 | 만점 (떨어지면 경보) | 넣기 전 낮고, 넣은 후 높음 |
| 이 프로젝트 | 공개 세트 10문항 | 비공개 세트 5문항 |

**회귀 테스트(regression test)**는 코드를 고친 뒤 예전에 되던 기능이 여전히 되는지 확인하는 테스트입니다. 위키에서는 새 자료를 넣거나 규칙을 바꾼 뒤 있던 지식이 깨지지 않았는지 확인하는 역할입니다. 여기에 **숨겨둔 시험지(held-out set)**를 따로 두었습니다. 시험에 나온 문제만 고쳐서 점수를 올리는 **과적합(overfitting)**, 즉 시험지에만 맞춰지고 실제 실력은 늘지 않는 상태를 확인하기 위한 예비 문항입니다.

공개 세트 10문항은 이렇게 구성했습니다.

| 유형 | 문항 수 |
|---|---|
| 사실·트러블슈팅 | 4 |
| 결정 이유 | 2 |
| 시간에 따른 변화(이력) | 1 |
| 시리즈를 넘나드는 교차 연결 | 2 |
| **위키에 없는 질문** (지어내지 않고 "없다"고 답해야 정답) | 1 |

정답의 핵심 사실은 1~2개로 짧게 잡았습니다. 정답이 길면 지식이 아니라 "답을 얼마나 길게 썼는지"를 재게 되기 때문입니다.

### 첫 판에서 잡힌 것은 사람의 실수였다

"정답은 원본에서" 규칙은 첫 판부터 성과를 냈습니다. 처음 키트에 예시로 넣었던 Q3의 정답("-32000 오류, npx 캐시 비우기")이 **원본 어디에도 없었습니다.** 시험 규칙이 AI가 아니라 시험을 만든 사람의 실수를 잡은 것입니다.

### "무엇"은 있는데 "왜"가 없었다

공개 세트 기준선은 **29/30**이었습니다(10문항 × 3기준). 0점이 나온 1문항을 추적하니 위키에 "무엇을 결정했나"는 있는데 "왜"가 빠져 있었습니다. 같은 문제를 원본 26편과 대조하자 **약 30곳**에서 결정 이유가 빠져 있었습니다. 원본 여러 편을 한 페이지로 대량 압축하는 과정에서 생긴 구조적 손실이었습니다.

여기서 증상(페이지 30곳)이 아니라 **원인(규칙)**을 고쳤습니다. CLAUDE.md에 다음 규칙을 추가했습니다.

> 결정은 "무엇을 골랐나 + 왜 + 무엇을 버렸나"를 함께 적는다. 원본에 이유가 없으면 "(이유 미기록)"으로 표시한다.

그리고 핵심 결정 5곳만 보강했습니다. 세부 결정 20여 곳은 "위키는 요약"이라는 원칙에 따라 그대로 두었습니다. 재평가는 **30/30**이었고, 나머지 9문항도 그대로 맞아 회귀가 없음을 확인했습니다.

## 노션 반영 — 1,370개 중 152개만 넣은 이유

### 3단 분류와 대기실

노션에는 성격이 다른 자료가 섞여 있어 넣기 전에 세 칸으로 나눴습니다.

| 칸 | 내용 | GitHub |
|---|---|---|
| 로컬 전용 | 수업 필기 905개, 2차 대상, 이미지 | 올리지 않음 (원본은 노션에 그대로) |
| 비공개 | 자격증 정리, 인턴 필기·면접 준비 | 비공개 레포 |
| 공개 | 제출이 끝난 공모전의 기술·설계 | 공개 레포 + 사이트 |

원본 창고는 한번 넣으면 수정·삭제가 안 되는 구역입니다. 그래서 그 앞에 **대기실(inbox)**을 두고, 분류와 비밀값 검사를 끝낸 것만 들여보냈습니다.

### 내보내기와 한글 파일명

노션 내보내기는 Markdown & CSV / 데이터베이스는 **기본 보기** / 하위 페이지 포함 / 하위 페이지용 폴더 생성으로 설정했습니다. 한 번에 다 받지 않고, 시험용 내보내기 1개로 구조(5단계 깊이까지)를 먼저 확인한 뒤 나머지를 받았습니다.

그런데 macOS 기본 `unzip`이 한글 파일 이름을 읽지 못해 `Illegal byte sequence`로 실패했습니다. zip 안의 파일명 인코딩을 제대로 처리하지 못한 것입니다. 맥에 내장된 `ditto`로 해결했습니다.

```bash
ditto -x -k "$ZIP" 학기별-시험
```

### 선별 기준 세 가지 질문

내보낸 결과는 9개 페이지, md 파일 약 1,370개였습니다. 졸업작품 94편 정리에 토큰 164만 개가 들었으니 전부 넣으면 10배가 넘습니다. 그래서 파일마다 세 가지를 물었습니다.

1. 다시 물어볼 일이 있나?
2. 다른 지식과 연결되나?
3. 노션에 그냥 둬도 충분하지 않나?

결과적으로 공모전(82), 자격증(31), 인턴 준비(31) 등 **152개만** 1차로 반영했습니다. 수업 필기 905개는 목록 카드 한 장으로만 남기고, 자기소개서 프롬프트는 위키가 아니라 실제로 쓰는 곳으로 보냈고, Velog와 중복되는 노션 대시보드는 제외했습니다.

원본 창고에 넣기 전에는 커밋 훅과 같은 규칙으로 **비밀값 사전 검사**를 했습니다. 값은 출력하지 않고 개수와 위치만 봤습니다. 비밀값 0건, 개인정보 패턴 3건(업체의 공개 연락처, 예제 데이터)이었습니다. 공개 기준도 이번에는 대화가 아니라 CLAUDE.md의 "노션 출처 공개 기준"으로 **먼저 고정한 뒤** 시작했습니다.

한 가지 더 있습니다. 자격증·인턴 준비 진행 상황을 채팅으로 알려주자, Claude Code가 그 내용을 `_private/raw/notes/captures/`에 새 원본 파일로 저장하고 위키 페이지의 근거로 걸었습니다. "위키의 모든 사실은 원본에 근거가 있다"는 규칙을 대화에도 적용한 것입니다.

## 증명 — 같은 답을 더 싸게

노션을 넣기 전과 후에, 같은 비공개 5문항을 질문마다 새 서브에이전트로 풀게 했습니다.

| 비공개 5문항 | 검색 적중 | 사실 정확 | 위키만으로 답함 |
|---|---|---|---|
| 노션 넣기 전 | 1/5 | 4/5 | 1/5 |
| 노션 넣은 후 | **5/5** | **5/5** | **5/5** |

눈여겨볼 칸은 "사실 정확"입니다. 넣기 전에도 4/5를 맞혔습니다. 위키에 없으니 **원본을 직접 뒤져서** 맞힌 것입니다. 넣은 후에는 원본을 한 번도 열지 않고 위키만으로 5문항을 모두 맞혔습니다.

즉 성장의 본질은 "못 풀던 문제를 풀게 됐다"보다 **"같은 답을 더 싸고 빠르게 낸다"**에 있습니다. 질문할 때마다 원본을 다시 찾는 RAG와 달리, LLM Wiki는 정리 비용을 넣을 때 한 번 내고 그 결과를 계속 재사용합니다. 지난 편에서 말한 "복리"가 처음으로 숫자가 된 순간입니다. 위키는 98페이지에서 **119페이지**(공개 신규 12, 비공개 신규 9)가 됐습니다.

## AI의 범위 초과와 독립 검증

노션 반영 중에 원본 노트의 오류 정정을 **1곳만 승인**했습니다. 그런데 Claude Code는 같은 유형의 오류를 스스로 찾아 **48곳**으로 넓혀 적용했습니다. 근거는 원본이 아니라 AI 자신의 지식이었고, 대상은 시험 공부 자료였습니다.

되돌려 버리는 대신 검증하기로 했습니다. **독립 검증(independent verification)**은 결과를 만든 AI가 아니라 **과정을 모르는 다른 에이전트**가 판정하게 하는 방법입니다. 만든 쪽이 채점하면 자기 판단을 다시 확인할 뿐이기 때문입니다. 새 서브에이전트에게 "원본 내용 / 정정 내용"만 주고, 정정 근거는 빼고 판정하게 했습니다.

| 판정 | 건수 |
|---|---|
| 정정이 맞음 | 46 |
| 판단 불가 | 2 |
| 원본이 맞음 | 0 |

판단 불가 2건 중 1건은 원본으로 되돌리고 "확인 필요"로 표시했고, 1건은 같은 코드 안의 함수 선언이 근거라 정정을 유지했습니다.

이 과정에서 새 원칙도 생겼습니다. **시험 대비 자료는 교재 표기를 본문에, 일반·실무 기준은 "참고"로 병기합니다.** 예를 들어 OAuth는 교재 표기인 "인증 및 인가 프로토콜"을 본문에 두고, "참고: RFC 6749 기준으로는 인가 프레임워크"를 함께 적습니다. 시험 답안과 면접 꼬리질문을 한 페이지로 대비할 수 있습니다.

결과는 대부분 맞았지만, 이 일은 correction(AI 판단 오류 기록)에 정직하게 남겼습니다. 결과가 맞아도 **승인 범위를 넘은 것 자체가 관리 대상**이기 때문입니다. AI에게 불리한 기록을 빼면 지표는 다시 굿하트의 함정에 빠집니다. 정정 규칙도 CLAUDE.md에 고정했습니다.

- 원본 안에 근거가 있으면 → 정정
- 원본 밖 지식이 근거면 → 독립 검증 후 판정이 엇갈린 것만 사람에게
- 승인 범위를 넘으면 → 먼저 묻는다

## 회고 — 운영에서 얻은 원칙

1. **승인은 파일로 남겨야 승인이다.** 대화는 세션과 함께 사라집니다.
2. **권한을 넓히기 전에 위치를 바꿀 수 있는지 본다.** 최소 권한 원칙.
3. **경로에 묶인 설정은 이전 전에 목록화한다.** 예측한 함정은 함정이 아닙니다.
4. **지표가 목표가 되면 결정에 쓰지 않는다.** 굿하트의 법칙.
5. **자동은 초안까지, 공개는 항상 사람.** human gate는 비용이 아니라 설계입니다.
6. **정답은 원본에서, 위키에 없는 질문도 시험에 넣는다.** 시험지는 만든 사람의 실수도 잡습니다.
7. **증상이 아니라 원인을 고친다.** 페이지 30곳이 아니라 규칙 한 줄.
8. **결과가 맞아도 범위는 관리한다.** AI에게 불리한 기록도 남겨야 지표가 정직합니다.
