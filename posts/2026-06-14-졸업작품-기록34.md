## Flask 처음 잡고 백엔드 골격 짜기 — 청각장애인 알림 시스템 API v1 설계 (PR #2)

띵동(Ddingdong) 졸작의 Phase 1에서는 React 대시보드를 mock 데이터로 미리 만들어 놨었다. 이제 그 mock을 진짜로 받아줄 백엔드 차례였는데, Flask를 잡아본 적이 한 번도 없었다. Phase 2를 한 번에 통으로 가는 대신 **2-1차(백엔드 골격 단독) / 2-2차(React 연동 + 미니 E2E)** 로 쪼개기로 했고, 본 글은 그 2-1차 — API v1 엔드포인트 4종 + SQLite 모델 + 인증/rate limit/idempotency까지 잡고 PR #2(`37a92b3`)로 머지한 작업 기록이다.

ML 추론은 mock(실제 YAMNet은 11주차에 wire), HTTPS/EC2 배포도 11주차에 미뤘다. 이번엔 로컬에서 **구조에 집중** 하는 게 목표였다.

## app factory 패턴으로 시작

처음에 Flask 튜토리얼 보면 `app = Flask(__name__)`을 전역에서 만들어 쓰는 게 흔한데, 본 프로젝트는 처음부터 **`create_app()` 팩토리 함수가 앱을 조립해서 반환** 하는 구조로 갔다. 이유는 두 가지였다.

- 테스트 환경 / 개발 환경 / 11주차 EC2 운영 환경에서 config를 갈아끼울 수 있어야 했고, 전역 객체로는 그게 깔끔하지 않았다
- `db` 같은 SQLAlchemy 확장이 라우트 파일에서 import되는 구조면 순환 import가 거의 무조건 터지는데, factory 패턴이 이걸 자연스럽게 회피했다

폴더 구조는 이렇게 잡혔다.

```
server/
├── run.py
├── requirements.txt
├── .env.example
├── README.md
└── app/
    ├── __init__.py      # create_app()
    ├── config.py
    ├── extensions.py    # db = SQLAlchemy()
    ├── constants.py
    ├── utils.py
    ├── errors.py
    ├── auth.py
    ├── rate_limit.py
    ├── models.py
    └── routes.py
```

`extensions.py`에 `db`를 따로 두고, `create_app` 안에서 `db.init_app(app)`을 호출하는 패턴. `routes.py`는 `db`를 `extensions`에서 가져다 쓰니까 앱 객체에 의존하지 않았고, 이게 Flask 공식 문서에서 미는 패턴이기도 했다.

## SQLAlchemy 모델 — DB 행과 응답 JSON의 경계

모델은 두 개만 만들면 충분했다.

| 모델 | 역할 |
| --- | --- |
| `notifications` | 알림 1건 = DB 한 행. 대시보드 응답 JSON이랑 1:1 |
| `idempotency_keys` | 24시간 TTL, `client_request_id` 기준 중복 차단 |

여기서 신경 쓴 게 **DB 행과 응답 JSON의 경계** 였다. SQLAlchemy 모델이 곧 응답 JSON이 되는 게 편하긴 한데, 그러면 DB 컬럼 추가가 바로 외부 API 변경이 돼버려서 위험했다. 그래서 모델에 `to_dict()` 메서드를 두고, 외부에 보낼 때는 무조건 이 직렬화 경계를 거치도록 했다.

타임존도 한 번 정리하고 가야 했다. SQLite는 타임존 자체를 모르는 DB라서, 저장은 **UTC** 로 통일하고 응답 직렬화 시점에만 **KST** 로 변환해서 내려주는 식. 이렇게 안 잡으면 11주차에 EC2(서울 리전) 올렸을 때 로컬 개발 환경이랑 시간 표현이 묘하게 어긋나는 사고가 거의 무조건 났다.

`notifications` 모델의 주요 컬럼은 대시보드 `dashboard/src/types/notification.ts` 와 1:1로 맞췄다.

- `predicted_class` enum (초인종 / 노크 / 화재경보, 카테고리 4 SSoT)
- `client_request_id` (ESP32가 발급) / `request_id` (서버가 ULID로 발급, 시간순 정렬 가능)
- `created_at` / `confidence` / `image_url` / `transcript` (사진과 STT는 2차에 채워지니까 nullable)

## API v1 엔드포인트 4종 설계

URL 버저닝을 굳이 처음부터 잡은 이유는, **ESP32 펌웨어는 한 번 배포되면 OTA 없이는 못 바꾸기 때문** 이었다. 졸작 종료 후에라도 서버 쪽 API 형태를 깨는 변경이 필요해지면 `/api/v2`로 새로 파고 `/api/v1`을 한동안 같이 살려둘 수 있어야 했다. Blueprint를 `url_prefix="/api/v1"`로 잡으면 라우트 정의 시점에 prefix를 신경 안 써도 돼서 깔끔했다.

```python
# app/__init__.py 일부
def create_app(config_class=Config):
    app = Flask(__name__)
    app.config.from_object(config_class)

    db.init_app(app)
    register_error_handlers(app)

    from .routes import api_v1
    app.register_blueprint(api_v1, url_prefix="/api/v1")

    return app
```

엔드포인트는 네 개.

| 엔드포인트 | 호출자 | 역할 |
| --- | --- | --- |
| `POST /api/v1/detect` | ESP32 → 서버 | 1차 추론(mock) + notification 저장 + `request_id` ULID 발급 |
| `POST /api/v1/enrich` | ESP32 → 서버 | 2차 사진/STT 채우기 (mock) |
| `GET /api/v1/notifications` | React → 서버 | 알림 리스트, cursor pagination |
| `GET /api/v1/stats` | React → 서버 | `?period=today` 집계 |

`/detect`는 ESP32가 음향 트리거를 잡은 직후 호출하는 1차 알림이라 빠르게 끝나야 했고, `/enrich`는 사진 + 추가 5초 녹음을 보내는 2차라서 별도 엔드포인트로 분리됐다. 응답 JSON은 그냥 임의로 디자인한 게 아니라 `dashboard/src/types/*.ts` 의 실제 타입과 1:1로 맞췄다 — types가 SSoT, 서버는 거기 맞추는 쪽.

## Device Token vs Dashboard Token — 권한 도메인 분리

처음에는 토큰을 하나만 쓰려고 했는데, 곧 문제가 보였다.

- ESP32는 펌웨어에 토큰을 박아서 배포하니까 한 번 유출되면 회수가 거의 불가능
- React 대시보드는 사용자가 발급받아서 쓰는 거라 회전이 비교적 자유로움

이 둘이 같은 토큰을 쓰면 한쪽이 털렸을 때 양쪽이 다 무너지고, 권한 범위도 다른데(`/detect`·`/enrich` vs `/notifications`·`/stats`) 같은 토큰이 모든 라우트를 다 열어주는 게 의미상으로도 어색했다. 그래서 **Device Token / Dashboard Token을 분리** 하고 데코레이터로 라우트별로 다르게 걸었다.

```python
# app/auth.py 일부 (구조)
def device_auth(fn):
    @wraps(fn)
    def wrapper(*args, **kwargs):
        token = _extract_bearer(request)
        expected = current_app.config["DEVICE_TOKEN"]
        if not expected or not hmac.compare_digest(token, expected):
            return jsonify(error="unauthorized"), 401
        return fn(*args, **kwargs)
    return wrapper

# 라우트에서
@api_v1.post("/detect")
@device_auth
def detect():
    ...
```

여기서 두 가지가 핵심이었다.

1. **`hmac.compare_digest` 상수시간 비교** — `==` 로 토큰 비교하면 일치하는 글자 수에 따라 응답 시간이 미세하게 달라지는 타이밍 공격 표면이 생긴다. 졸작 수준에서 실전 공격을 걱정할 일은 없지만, 정답 코드를 한 번 익혀두는 게 맞았다.
2. **빈 토큰 무조건 차단** — `expected`가 비어 있으면(`.env`에 설정 누락) 어떤 입력도 통과시키지 않게 했다. 설정 누락이 곧 인증 우회가 되는 시나리오가 가장 위험했다.

## rate limit + idempotency

ESP32 음향 트리거가 노이즈로 잘못 발동하거나 펌웨어 버그로 폭주하는 시나리오가 충분히 가능했다. 그래서 **device 기준 5초당 1회** 로 rate limit을 깔았다.

```python
# 의사 코드
if elapsed_since_last_call(device_id) < 5:
    retry_after = 5 - elapsed
    return jsonify(error="too_many_requests"), 429, {"Retry-After": str(retry_after)}
```

`429`만 던지면 클라이언트가 언제 재시도해야 할지 모르니까 `Retry-After` 헤더까지 같이 내려줬다.

Idempotency는 비슷한 결을 다른 layer에서 잡는 장치였다. ESP32가 `/detect`를 호출했는데 네트워크가 흔들려서 응답을 못 받으면 펌웨어는 재시도를 할 텐데, 서버 입장에서는 같은 알림이 두 번 저장되면 안 됐다. 그래서 ESP32가 발급한 `client_request_id`를 `idempotency_keys` 테이블에 24시간 보관하고, 같은 key가 다시 들어오면 **이전 응답을 그대로 replay** 하는 방식.

이렇게 하면 펌웨어 쪽 재시도 로직을 단순하게 "응답 못 받으면 그냥 재시도"로 짤 수 있어서 책임이 깔끔하게 분리됐다.

> ⚠️ **솔직한 한계**: 지금 rate limit은 in-memory `dict` 라 11주차에 Gunicorn 워커 2개로 띄우면 워커마다 dict가 따로 돌아서 무효화된다. Redis로 갈아끼우는 작업이 11주차 배포 시점에 필요한데, 지금은 골격 단계라 일부러 미뤘다. decisions.md 카테고리 6에 미결로 기록.

## 대시보드 타입과 1:1 맞추기 — cursor는 additive로

응답 JSON 설계할 때 추측으로 깎지 않고 `dashboard/src/types/*.ts` 를 먼저 catch했다. 라이브 코드의 타입이 곧 SSoT, 서버는 거기에 맞추는 입장.

그런데 `api.ts` 의 `NotificationsApiResponse` 를 보니 cursor pagination 메타(`next_cursor`, `has_more`)가 없었다. Phase 1에서 mock 데이터로 만들 때는 pagination이 필요 없어서 안 잡혀 있던 상태였다. 그래서 판단을 한 번 갈랐다.

- **백엔드는 미리 cursor 메타를 내려준다** — 페이지가 늘어났을 때를 대비해서. 단, 기존 `notifications` 키는 유지.
- **프론트 types 추가는 2-2차로 미룬다** — 지금 추가하면 본 PR의 범위가 React까지 번진다.

이렇게 하면 백엔드가 더 많은 정보를 내려주는데 프론트가 안 받는 형태가 되니까(additive) 호환성이 깨지지 않았다. 2-2차에서 `api.ts`에 cursor 필드 추가하면서 자연스럽게 받기 시작하면 됐다.

## curl 15종으로 검증

배포 전이라 사용자 테스트는 못 했지만, curl로 시나리오 15종을 짜서 다 통과시켰다.

- 인증 401 (토큰 없음 / 잘못된 토큰 / 도메인 분리 — Device Token으로 `/notifications` 못 부르는지)
- 필드 누락 400 / 잘못된 enum 400 / 잘못된 period 400
- 정상 201 (`/detect` 알림 생성) / 정상 200 (`/enrich`, `/notifications`, `/stats`)
- Idempotency replay 200 (같은 client_request_id 재호출, 같은 response_body)
- Rate limit 429 (`Retry-After` 헤더 같이 확인)
- Enrich 404 (없는 request_id) / 409 (이미 enrich된 알림)
- Pagination 중복 없음 (커서 페이지 넘어가도 같은 알림 두 번 안 나오는지)
- Stats 집계 정확 (DB 직접 카운트랑 매칭)

에러 응답은 HTTP Status 8종(200/201/400/401/404/409/429/500)으로 정해두고 전부 동일한 JSON 형식(`{"error": "...", "message": "..."}`)으로 통일했다. 프론트에서 에러 핸들링이 단순해졌다.

## Flask 처음 잡으면서 배운 것들

며칠을 통으로 Flask에 쏟은 셈인데, 처음에 헤맸던 개념 몇 가지가 끝나고 나니 자연스러워졌다.

- **app factory + Blueprint 분리** — 라우트가 늘어나도 한 파일에 다 박지 않을 수 있는 구조. 작은 프로젝트에선 오버스펙처럼 보이는데, 11주차에 인증 라우트나 관리 엔드포인트가 추가될 걸 생각하면 처음부터 잡아두는 게 맞았다.
- **세션 / `db.session` 흐름** — 트랜잭션 경계를 어디서 끊는지가 처음엔 헷갈렸는데, "한 요청 = 한 세션"으로 잡고 응답 직전에 `commit`하거나 예외 시 `rollback`하는 패턴으로 통일했다.
- **데코레이터로 cross-cutting 잡기** — 인증 / rate limit이 라우트마다 박혀 있으면 끔찍해지는데, 데코레이터로 빼니까 라우트 본문은 본인 책임만 표현하게 됐다.

"백엔드 골격 먼저, 실제 ML은 11주차"로 쪼갠 판단이 이번에 잘 들어맞은 것 같다. ML이 같이 있었으면 어디서 막혔을 때 — Flask 구조 문제인지 ML wire 문제인지 — 격리가 안 됐을 거고, Flask 학습 자체에 집중하기도 어려웠을 거다. 골격이 curl로 다 통과한 상태로 PR이 머지된 지금 시점에서, 2-2차에 React 연동만 신경 쓰면 되는 게 마음이 한결 가벼웠다.
