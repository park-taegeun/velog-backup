## 카메라 더미 테스트 — Version A / B (commit `aa6116d`, `8ce56ed`)

### 왜 두 버전인가

카메라 코드를 짜면서 `fb_get` 블로킹 처리 방식이 고민됐는데, 두 가지 접근이 있었다.

- **Version A: cameraTask 단독** — `fb_get` → 처리 → `fb_return`을 하나의 태스크 안에서 순서대로 처리하는 구조
- **Version B: writerTask 분리** — `fb_get` 블로킹을 격리하고, queue로 다른 태스크에 프레임을 넘기는 구조

어느 쪽이 안정적인지는 부품이 도착해서 실제로 돌려봐야 알 수 있는 문제였다. 지금 단계에서 정답을 정하려는 게 아니라, 두 구조를 미리 짜두고 5/15~5/28 부품 도착 후 `fb_get` 안정성을 직접 비교하는 게 목적이었다.

### 주요 설계 결정

- **카메라 모델 분기**: OV2640을 기본으로 하고 OV3660 분기 코드를 런타임에 PID `0x36` 감지로 처리했다. XIAO Sense Pre-Soldered에 실제 어떤 카메라가 탑재되는지 부품 도착 전까지 100% 확신하기 어려운 상황이었고, 양쪽 다 커버하는 게 안전했다.
- **메모리 진단 코드 포함**: PSRAM total/free, heap free, assertion을 포함시켰는데, 부품 도착 후 실측에서 바로 확인할 수 있게 미리 넣어둔 구조였다.
- **Core 할당**: `cameraTask` → Core 1 핀고정, priority 4 / `writerTask` → Core 1, priority 3

### 컴파일 결과

부품 없이 컴파일만 통과시키는 게 목표였는데, 둘 다 통과했다.

| | RAM | Flash |
| --- | --- | --- |
| `env:camera_v1` | 7.0% | 9.4% |
| `env:camera_v2` | 7.0% | 9.4% |

Day 2 WiFi 코드(RAM 13.8% / Flash 25.8%)보다 낮은 건 `WiFiClientSecure`가 없는 구조라서였다. 통합 시에는 합산되는 수치라 11주차 동적 heap 추적이 필요한 이유가 여기 있었다.

## Khangura 6개 함정 전체 검토

출처: Manjot Khangura — *Getting ESP32-S3 Sense OV3660 Camera Working: A Weekend Deep Dive*

### 4 → 6 정정이 나온 배경

직전 작업이 "4가지 함정"이라는 전제로 진행됐는데, 학부생이 "원문 다시 확인해보니 6개 아니냐"고 정정했다. 확인해보니 맞았다. 출처의 전체 항목 개수를 사전에 확인하지 않고 진행한 게 원인이었는데, 이게 이번 학습 13의 발단이었다.

### 6개 함정 분류 결과

| # | 함정 | 분류 | 비고 |
| --- | --- | --- | --- |
| #1 | OCTAL PSRAM | ✅ 완전 반영 | `BOARD_HAS_PSRAM` + `fb_location = CAMERA_FB_IN_PSRAM` 반영 |
| #2 | Frame Buffer Overflows | 🟡 부분 반영 | Version A/B 분리로 비교 예정, 부품 도착 후 |
| #3 | Ran Out of PSRAM | ❌ 미반영 | 현재 단독 테스트라 무관, 통합 시 재검토 |
| #4 | JPEG timeout | ✅ 완전 반영 | `vTaskDelay(pdMS_TO_TICKS(30))` 반영 |
| #5 | Kconfig WiFi | ❌ 미반영 | 본 작업 범위와 무관 |
| #6 | Dark Images | 🟡 부분 반영 | `xclk_freq_hz` 설정 반영, 실측은 부품 도착 후 |

코드 보강은 0건이었는데, 이미 사전 반영 7가지에 포함된 항목들이었다. `decisions.md` 카테고리 25를 신설해서 표를 보존했다.

## 학습 13 — 전제 검증 누락 패턴

이번 사례에서 **출처의 전체 항목 개수를 사전에 확인하지 않은 채로 진행하면 부분 인용으로 끝난다**는 걸 다시 확인했는데, 이걸 학습 13으로 정착시키면서 프로젝트 지침 *Claude Code MCP 활용 원칙* 6번에 영구 반영했다. 외부 출처 인용 시 전체 항목 개수 사전 명시 또는 후속 검증 강제 원칙이었다.

## 매일 밤 3-set 루틴 (commit `282a973`, `2a7c1d8`, `1cd6f14`, `3b5c7bd`)

`decisions.md` 갱신은 카테고리 4개가 변경됐다.

- **카테고리 16.1 신설**: 5/8~5/9 더미 테스트 누적 RAM/Flash 측정 표
- **카테고리 17.1.1 갱신**: 5/9 카메라 측정값 추가 + 정적 budget 검증 한정 명시
- **카테고리 17 갱신**: 11주차 동적 heap 추적 항목 추가 (`ESP.getMinFreeHeap()` + stack high-water mark)
- **카테고리 25 신설**: Khangura 6개 함정 코드 반영 표

`decisions-log.md`에는 2026-05-09 entries 5건 추가 + hash 보강이 들어갔는데, 1차 commit으로 entry 추가하고 2차 commit으로 hash를 보강하는 2-step 패턴(학습 11)을 그대로 따랐다. Claude Code MCP가 자기 commit hash를 자체 참조해서 보강하는 방식이었다.

노션 PoC 트래킹은 5단계 워크플로우 그대로 — DB1 Day 3 row 추가, 메타 콜아웃 overwrite, 체크박스 갱신(✅ 6건 / ⏸ 2건), 일정 vs 실제 표 갱신(일정 +300%), DB3 자동 전환 정량 룰 적용(변경 0건).

## 부수 작업 — Claude Code MCP 환경 정리

`Auto-update failed` 오류가 났는데, npm prefix 충돌(`~/.npm-global` vs Homebrew Node)이 원인이었다. 잔여 폴더 청소 후 재설치로 해결했고, 2.1.119 → 2.1.137로 정상 업데이트됐다. 학습 12로 정착시키고 `decisions-log.md`에 1줄 기록했는데, 개인 환경 이슈라 프로젝트 SSoT에 영향은 없었다.

## 5/9 종합

8개 commit, 환불 확인 + 카메라 코드 2버전 + 함정 6개 검토 + SSoT 동기화까지 마무리했다. 부품이 없는 상태에서 할 수 있는 건 다 했다는 느낌이었는데, 컴파일 통과 + 메모리 측정 패턴을 미리 잡아두면 부품 도착 후 실측이 훨씬 빠르게 돌아간다.

다음 글에서는 데모 시나리오 구체화 과정을 기록할 예정이다. "소리 감지 → 카카오톡 알림"으로 끝나는 시연이 아니라, 청각장애인 입장에서 진짜 임팩트 있는 흐름을 어떻게 설계했는지를 정리할 예정이다.
