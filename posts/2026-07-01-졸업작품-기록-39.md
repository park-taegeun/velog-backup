# "초딩도 말할 느낌"이었던 화재 수칙 — 페르소나 정합이라는 또 다른 층위

전편(접근성 3조각)이 WCAG라는 기계적 기준을 지키는 작업이었다면, 이번 chunk는 결이 좀 달랐다. **접근성이 "규칙을 지켰는가"라면, 페르소나 정합은 "이 사람한테 실제로 맞는가"** 였다.

대시보드는 Phase 1·2·Phase B(접근성)까지 다 끝난 상태였다. 근데 `npm run dev`로 화면을 처음 직접 실행해보는 순간이 있었는데 — 인계 패키지에 "UI polish 미착수"라고 적혀 있어서 은근히 미구현인 줄 알았던 화면들이 사실 이미 다 구현돼 있었다. 눈으로 직접 보니까 그동안 텍스트로만 확인하던 것과는 다른 게 보였고, 그중 하나가 도움말 화면의 화재경보 대응 수칙이었다.

"119에 즉시 신고하세요"로 시작하는 카피를 보는데 위화감이 들었다. 딱히 뭐가 틀렸다고 콕 집을 순 없었는데, **초등학생도 말할 수 있는 느낌** 이었다. 뭔가 못 미더웠다.

## 위화감이 4개 결함으로 번역되는 과정

이 막연한 위화감을 그냥 넘기지 않고 베테랑 관점으로 뜯어봤다. 결과가 표면적인 문제(예: 문장이 어색하다)가 아니라 **페르소나 치명 결함** 이었다.

핵심 결함은 하나였다 — **"119에 즉시 신고하세요"가 음성통화를 전제하고 있었다.** 근데 본 시스템의 타겟 사용자는 청각장애인이다. 음성통화 자체가 안 되는 사람한테 "즉시 신고"를 1번 행동 지침으로 준 거였다. 이게 페르소나를 완전히 놓친 카피였다.

거기서 더 들여다보니 결함이 3개 더 나왔다.

| 결함 | 기존 카피 | 문제 |
|------|-----------|------|
| ① 음성통화 전제 | "119에 즉시 신고" | 청각장애인은 음성통화 불가 |
| ② 순서 역전 | 신고 → 대피 | 화재는 대피가 먼저, 안전 확보 후 신고 |
| ③ "불이야" 외치기 | 주변에 알리기 항목 포함 | 청각장애인 화자에게 발성 지시가 부적절 |
| ④ 구조요청 방식 | (음성 전제 서술) | 시각·문자 수단으로 대체 필요 |

**"초딩도 말할 느낌"이라는 막연한 감이 결국 근거로 번역되는 과정** 이 이번 작업의 진짜 핵심이었다. 처음엔 "왠지 못 미덥다"는 감밖에 없었는데, 하나씩 파고드니 구체적인 페르소나 누수 4건으로 쪼개졌다.

## 안전 콘텐츠에는 출처 등급을 강제해야 한다

화재 대피 정보는 잘못 알려주면 실제로 위험해질 수 있는 콘텐츠다. 그래서 Claude Code MCP에 위임할 때 그냥 "잘 찾아봐"로 던지지 않고, **출처 등급을 명시적으로 강제** 했다.

- 1차 출처(소방청 청각장애인 교재, 손말이음센터 107)만 단독 근거로 인정
- 블로그·개인 정리글은 단독 근거 금지, 교차검증 용도로만

이렇게 강제한 이유가 명확했다. 화재 대피 정보에 출처가 불분명한 개인 블로그 내용이 섞이면, 그게 틀렸을 때 오히려 더 위험해진다. AI한테 "잘 찾아봐"라고만 하면 검색 결과 상위에 뜨는 아무 글이나 근거로 쓸 수 있는데, 안전과 직결된 콘텐츠는 이 부분을 느슨하게 두면 안 됐다.

조사 결과 소방청 청각장애인 교재(1차 출처) + 손말이음센터 107(공식 중계 서비스) + 긴급신고 바로앱(공식 앱)을 근거로 카피를 재구성했다.

**정정된 4단계**: 대피 우선 → 안전 확보 후 신고 → 119 영상통화(수어) 또는 문자 신고 → 「긴급신고 바로앱」 활용. 결함 4건을 다 교정한 버전이었다.

### 앱 최신성을 정직하게 보고한 것

이 과정에서 시키지도 않은 걸 MCP가 알아서 체크한 게 있었다. 「긴급신고 바로앱」을 조사하다가 최신 업데이트 시점을 확인했는데, **내가 예상한 것보다 훨씬 오래된 2024-01-20** 이었다. 요청한 적 없는 부가 정보였는데, 이걸 숨기지 않고 정직하게 보고했다.

이게 나중에 중요한 의미를 갖게 됐다.

### B안(앱 보조 병기)이 결과적으로 옳았던 이유

신고수단 우선순위를 정할 때 두 가지 안이 있었다 — A안(앱을 메인 수단으로), B안(영상통화·문자를 메인, 앱은 보조). B안을 채택했었는데, 이유는 영상통화·문자가 통신사·정부 인프라로 확정적으로 유지되는 수단이고, 앱은 상대적으로 불확실성이 있다는 판단이었다.

그런데 조사 결과 앱 최신 업데이트가 2년 가까이 경과된 상태였다는 게 확인되면서, **B안이 우연이 아니라 원칙의 결과였다는 게 증명됐다.** "확정적인 수단을 메인에 두고, 불확실할 수 있는 수단은 보조로"라는 원칙을 따랐던 게, 나중에 실제로 앱이 노후 상태였다는 사실로 정당화됐다.

## 라이트 테마 — 왜 다크 기본이 안 맞았나

화재 수칙을 정리하고 나서 테마도 손봤다. 원래 대시보드는 `prefers-color-scheme`을 따라가는 구조라 시스템이 다크면 다크로 뜨는 방식이었다.

근데 타겟 사용자가 **5060 중증 청각장애인** 이다. 노안이 진행된 연령대인데, 다크 배경에 밝은 텍스트는 저시력 사용자한테 눈부심이나 가독성 저하를 일으키는 경우가 많다. 그래서 라이트를 기본으로 고정하고, 다크는 원하는 사람만 켜는 opt-in으로 바꿨다.

```tsx
// SettingsContext.tsx (구조)
// 이전: matchMedia(dark) ? "dark" : "light"  (시스템 추종)
const [theme, setTheme] = useState<Theme>(
  () => (localStorage.getItem("theme") as Theme) ?? "light"   // 라이트 고정, opt-in만 localStorage
);
```

여기서 위임 프롬프트에 있던 가정 하나가 틀린 걸로 판명 났다. 처음엔 "라이트 테마 토큰이 다크 위주로 정의돼 있어서 새로 짜야 할 것"이라고 가정하고 위임했는데, MCP가 실제 CSS 변수를 까보니 **`:root`에 라이트 토큰이 이미 완비돼 있었다.** 가설이 거짓으로 판명됐고, 실제로는 기본값 전환 로직만 손보면 되는 작업이었다.

연결 상태 배지도 3구분(연결됨/끊김/재연결)으로 명확히 하고, 폰트 크기를 전반적으로 상향했다. 다 같은 방향 — 5060 노안 가독성.

## 시스템 건강 카드 — 에러 화면에서 안심 화면으로

이번 chunk에서 제품 메시지 관점으로 제일 마음에 든 변화였다.

원래 대시보드에서 알림이 하나도 없는 상태(=정상적으로 조용한 상태)일 때 화면에 "통계를 불러오지 못했습니다" 류의 에러 카드가 떴다. 근데 이게 사용자 입장에서 **고장인지 정상인지 구분이 안 됐다.** "그냥 알림이 없는 거야, 아니면 시스템이 죽은 거야?"

청각장애인 1인 가구 사용자가 이 화면을 흘끗 볼 때 원하는 정보는 "지금 잘 작동하고 있나?"였다. 그래서 빈 상태를 에러 카드가 아니라 **"시스템 정상 작동 중"이라는 안심 카드** 로 바꿨다.

```tsx
// stats.ts (SystemHealth 확장, 구조)
interface SystemHealth {
  device_status: "online" | "offline" | "processing";  // 기존 재사용
  device_last_seen_at: string;                          // 기존 재사용
  signal_strength: SignalStrength;                      // additive
}
```

```tsx
// SystemHealthSummaryCard.tsx (구조)
// 3지표: device_status / device_last_seen_at / signal_strength
// online = 초록 + "정상 작동 중" / offline = 회색 + "연결 끊김" / processing = 파랑 + "처리 중"
```

여기서 타입 설계를 고민했다. 상수를 하드코딩(ㄱ안)하는 것보다 **`stats.ts` 타입을 확장해서 서버 mock → 카드까지 1:1로 잇는 구조(ㄴ안)** 를 택했다. 지금은 mock 값이지만 구조 자체는 실제라서, 11주차에 실제 device heartbeat가 연동되면 카드 로직은 안 건드리고 값만 실제로 바뀌면 됐다. "구조는 실제로 살아남고 값만 mock"이라는 원칙.

기존 `device_status` / `device_last_seen_at` 필드는 이미 존재해서 재사용했고, `signal_strength`만 additive로 새로 추가했다. 여기서도 위임 프롬프트에 있던 가정 하나가 또 틀렸다 — 처음엔 "device_status랑 last_detected_at을 신규로 추가해야 한다"고 가정했는데, 실측해보니 **이미 존재하는 필드였다.** 신규 추가가 아니라 재사용으로 방향을 바꿨다.

### 빈 vs 에러 구분은 유지

여기서 중요한 디테일이 하나 있었다. "빈 화면을 안심 카드로 바꾼다"고 해서 **진짜 에러 상황까지 안심 카드로 덮어버리면 안 됐다.** 실제로 fetch가 실패했는데 "정상 작동 중"이라고 뜨면 그게 더 위험한 거짓 정보였다.

```tsx
// NotificationList.tsx (구조)
// 분기 순서: loading → error → empty
// emptySlot prop = "정상적으로 비어있음"일 때만 안심 카드로 대체
// 실제 fetch 실패(error)는 기존 에러 카드 그대로 유지
{loading ? <Spinner /> : error ? <ErrorCard /> : items.length === 0 ? emptySlot : <List items={items} />}
```

`emptySlot`은 "정상-빈" 케이스만 대체하는 prop으로 설계했다. loading → error → empty 분기 순서를 지켜서, 에러는 여전히 에러로 보이게 남겨뒀다. 안심을 주려다가 실제 장애를 감추면 안 됐다.

## 3-set 정리 — 그리고 노션 ID가 또 틀렸다

작업 마무리하면서 decisions.md 갱신, 프로젝트 지침 갱신, 노션 미러링까지 3-set을 돌렸는데, 여기서 작은 사건이 하나 더 있었다.

노션 DB3의 실제 ID를 확인하는 과정에서, 기존에 SSoT로 박혀 있던 값이랑 이전 인계 패키지에 정정값으로 적혀 있던 값이 **둘 다 틀렸다.** decisions.md/지침에 박힌 값은 DB1 ID 꼬리가 잘못 복붙된 거였고, 이전 인계 패키지의 "정정값"도 자릿수가 안 맞는 malformed 상태였다. Live fetch로 실제 ID를 다시 확인해서 확정했다.

채팅방 초반에 "이 정정값도 9자리 hex라 이상한데?"라고 한번 의심했던 게 실제로 맞았던 사례였다. AI가 정정해놓은 값조차도 다시 한번 의심하고 실측해야 한다는 원칙이 여기서도 작동했다.

## 세 번 연속 확인된 원칙 — AI가 박은 것도 검증 대상

이번 chunk에서 유독 이 패턴이 세 번 연속으로 나왔다.

1. 라이트 테마 토큰이 "다크 위주로 정의돼 있을 것"이라는 위임 가설 → 실측으로 거짓, `:root`에 이미 완비
2. `device_status` / `last_detected_at`을 "신규 추가해야 한다"는 위임 가정 → 실측으로 기존 존재 확인, 재사용으로 전환
3. 화재경보 앱 최신성이 "최근"일 거란 암묵적 기대 → MCP가 시키지도 않고 2024-01-20으로 정직 보고

세 건 다 결이 같았다. **AI가 만든 가정이든, AI가 박아둔 SSoT 값이든, 실제로 코드/API/문서를 까보기 전까지는 확정된 게 아니다.** 사람이 세운 가정만 의심하는 게 아니라 AI가 세운 가정도 똑같이 의심 대상이라는 게, 이번엔 라이트 테마·타입 설계·화재 정보 세 영역에서 다 확인됐다.

## 정리하면

전편이 WCAG라는 규칙을 지키는 작업이었다면, 이번은 그 규칙 위에서 **실제로 이 사람한테 맞는가** 를 점검하는 작업이었다. 화재 수칙의 막연한 위화감이 4개 구체적 결함으로 번역됐고, 안전 콘텐츠라 출처 등급을 강제했고, 그 과정에서 B안(앱 보조)이 원칙의 결과로 정당화되는 걸 확인했다. 라이트 테마와 시스템 건강 카드는 각각 노안 가독성과 안심이라는 페르소나 니즈에 맞춘 변화였고, 셋 다 "빈 vs 에러 구분 보존" 같은 디테일에서 안전을 놓치지 않으려 했다.

접근성이 기계적 준수라면 페르소나 정합은 사람에 맞추는 일이었다. 이번 chunk에서 두 층위 다 한 번씩 지나온 셈이다.
