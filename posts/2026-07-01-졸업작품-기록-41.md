# 학습된 모델을 꺼내 쓰려다 만난 벽 — Keras 3 SavedModel export와 AI 산출물 3층위 검증


## 88.7% 다음에 남은 한 걸음

직전 글에서 데이터 파이프라인을 세우고 예비학습까지 돌려서 test accuracy 0.887 / macro F1 0.848을 찍었다. 거기까지 오니까 "이제 이 모델 배포만 하면 되겠거니" 하는 마음이 들었는데, 정작 서빙 형태로 꺼내려니 그게 안 됐다.

학습 산출물인 `best.keras` 자체는 멀쩡했다. 로드해서 추론 돌리면 잘 나왔고. 근데 이걸 서버가 물고 쓸 SavedModel 포맷으로 export하려니까 `untracked resource` 에러가 터졌다. 파이프라인 때 만난 함정들이 **데이터 쪽**에 숨어 있었다면, 이번 벽은 성격이 좀 달랐는데 — 벽이 데이터가 아니라 **AI가 만들어낸 산출물 자체**(위임으로 짠 코드, 그리고 그 코드를 검증했다는 보고서)에 있었다.

작은 버그였지만, 이걸 걷어내는 과정에서 catch가 세 군데에서 따로따로 나왔다. 그게 이 글의 본론이다.

## 버그의 정체 — frozen hub이 안고 온 리소스

우리 모델 구조는 frozen YAMNet backbone(TF-Hub에서 로드) 위에 head 몇 층을 얹은 형태다. backbone은 학습 안 하고 얼려두고, head만 fine-tuning했다.

문제는 이 hub 모듈이 내부적으로 자기만의 SavedModel 리소스를 들고 있다는 점이었다. 구식 경로인 `tf.saved_model.save()`로 통째 저장을 시도하면, 이 서브모듈이 물고 있는 리소스를 저장 그래프가 제대로 추적하지 못하고 `untracked resource`로 뱉어냈다.

해법은 Keras 3에서 미는 정공법인 `model.export()`였다. 이쪽은 저장 시점에 serving용 `tf.function`을 실제로 트레이스하는데, 그 트레이스 과정에서 backbone이 안고 있던 리소스까지 함께 포착해서 SavedModel 그래프에 제대로 물려준다. 그래서 구식 경로가 놓치던 걸 신식 경로는 잡아낸다.

```
best.keras
   └─ model.export("inference_savedmodel/")
        └─ serving tf.function 트레이스 → hub 리소스 포착
             └─ inference_savedmodel/  (서빙용 아티팩트)
```

여기서 하나 결정한 건, export를 **재학습과 분리한 독립 엔트리포인트**로 뺐다는 것이다. `ml/training/export.py`를 따로 두고, `best.keras`만 있으면 학습 다시 안 돌려도 서빙 SavedModel을 뽑을 수 있게 했다. `ckpt.exists()`로 체크포인트 존재를 먼저 가드하고 없으면 `FileNotFoundError`로 친절하게 안내하도록 했고, 테스트나 오프라인 환경을 위해 backbone을 외부에서 주입할 수 있는 여지도 남겼다.

## 첫 번째 catch — 위임 전제도 코드로 다시 봤다

이 버그를 고치라고 코딩 에이전트(Claude Code)에 위임을 던질 때, 나는 원인을 "frozen hub backbone 변수가 추적이 안 돼서"라고 적어서 보냈다. 얼추 맞는 감이었다.

근데 에이전트가 코드를 실측해보니 정확한 메커니즘은 살짝 달랐다. 진짜 범인은 backbone 변수 자체가 아니라, `build_inference_model` 안에 있던 Lambda 레이어(`yamnet_backbone`)의 **클로저**였다. 이 Lambda가 raw `hub.load()` 결과를 클로저로 캡처하고 있었는데, 그 클로저가 참조하는 trackable 객체가 모델의 객체 그래프에 등록이 안 돼 있었던 거다. 그래서 저장 그래프가 리소스를 못 따라간 거고.

이게 지난 파이프라인 글에서 세운 원칙(학습 19: AI의 근본원인 진단도 코드로 재검증)과 이어지는 대목인데, 이번엔 결이 좀 달랐다. 파이프라인 때는 내 진단이 **완전히 틀려서** 코드로 반증되고 no-op으로 끝났다("split이 01을 읽는다"→실은 처음부터 02를 읽고 있었음). 반면 이번엔 방향은 맞았고("hub 리소스가 추적 밖") 다만 **정확한 지점이 갈렸다**(변수 → Lambda 클로저). 그래서 접근 자체는 폐기 안 하고 유지했지만, 문서에는 실측한 메커니즘으로 정정해서 남겼다.

말하자면 AI 오진에도 정도가 있다. "완전 틀림"과 "방향은 맞고 디테일이 갈림"은 다르게 다뤄야 하고, 후자는 접근을 살리되 기록만 바로잡으면 된다.

| 층위 | 원인 진단 | 실측 결과 |
|------|-----------|-----------|
| 파이프라인 글(선행) | split이 01_clips를 읽음 | 처음부터 02를 읽고 있었음 → **완전 오진(no-op)** |
| export 버그(이번) | hub backbone 변수 미추적 | Lambda 클로저가 hub.load() trackable 미등록 → **부분 오진(방향○·메커니즘 갈림)** |

## 두 번째 catch — "검증 완료" 보고서도 곧이 안 믿었다

고치고 나서 에이전트가 올린 보고서에는 "실제 `build_inference_model`로 만든 모델을 export → reload까지 돌려서 최고 충실도로 통과했다"고 적혀 있었다. 얼핏 보면 끝난 것 같았는데, 뜯어보니 실제로는 **합성 더미 backbone을 주입한 상태**로 돌린 검증이었다.

즉 이건 코드 경로가 도는지를 확인한 것이지, 진짜 YAMNet을 export할 수 있다는 증명은 아니었다. 더미로는 hub 리소스 추적 문제가 재현이 안 되니까, 정작 원래 걸렸던 그 지점을 검증한 게 아니게 된다.

그래서 진짜 클로즈는 로컬에서 실제 `best.keras` + 실제 YAMNet으로 직접 돌린 뒤에 잡았다. `inference_savedmodel/`이 실제로 생성되고, 그걸 다시 `tf.saved_model.load`로 reload해서 `serving_default`로 추론했을 때 출력 shape이 `(1, 3)`으로 나오고 softmax 합이 정확히 1.0인 걸 눈으로 확인하고 나서야 완료 처리했다.

이 과정에서 시그니처도 하나 바로잡았다. export 로그에 입력이 `(None, None)`으로 찍혀서 순간 헷갈렸는데, 이건 `tf.function`의 polymorphic 표기였을 뿐이고 실제 Keras 입력은 `Input(shape=(None,), batch_size=1)` — 즉 배치 1 고정에 가변 길이 waveform이라 `(1, None)`이 맞았다. 최종 서빙 시그니처는 이렇게 정리됐다.

```
serving_default
  입력:  waveform  (1, None)  float32   # 배치 1 고정, 가변 길이
  출력:  logits    (1, 3)     float32   # doorbell=0 / knock=1 / fire_alarm=2
```

라벨 인덱스는 config의 `CLASSES`를 그대로 상속받아서 코드 전체에서 한 곳으로 관리되게 했다.

## 세 번째 catch — `No module named`

여기서 학습 18(웹에서 PR 머지한 뒤 로컬 main 동기화)이 실물로 한 번 걸렸다. 로컬 터미널에서 `python -m ml.training.export`를 돌렸는데 대뜸 `No module named ...`가 떴다.

이유는 단순했다. `export.py`는 PR 브랜치에만 있던 파일이었고, 아직 로컬 main에는 없었던 거다. 에이전트 세션이 원격에 push하고 PR을 올려도, **내 로컬 터미널의 main은 그것과 완전히 별개**라서, 웹에서 squash 머지한 다음 로컬에서 `git checkout main && git pull`을 해줘야 비로소 그 파일이 손에 들어온다. 머지 + pull 하고 다시 돌리니 정상 실행됐다.

## 마무리 — 세 겹으로 겹친 그물

버그 자체는 한 줄로 요약되는 작은 문제였다(`tf.saved_model.save` → `model.export`). 근데 이걸 닫는 과정에서 catch가 세 층위에서 따로 나왔다는 게 오래 남을 것 같다.

- **위임 전제**(내가 짠 원인 진단)에서 한 번 — 방향은 맞았지만 메커니즘이 갈렸다
- **AI 보고서**("검증 통과")에서 한 번 — 실은 더미 주입이라 실 환경 증명이 아니었다
- **실 환경 실행**(로컬 터미널)에서 한 번 — 로컬 main이 아직 그 파일을 몰랐다

AI에게 설계를 위임하고, 다른 에이전트가 실행하고, 내가 검증하는 구조에서는 이 세 지점이 각자 다른 방식으로 새어서, 결국 사람 눈이 층층이 걸러줘야 한다는 걸 다시 확인했다. catch 그물이 한 겹이 아니라 여러 겹으로 겹쳐서 작동한 셈이다.

부수적으로 회귀 방지도 챙겼다. `test_export_smoke.py`에 ① 구식 `tf.saved_model.save`가 untracked resource로 실패하는 걸 재현하는 assert, ② `model.export`가 성공하는지, ③ reload한 `serving_default` 추론이 정상인지를 넣어서, 나중에 누가 구식 경로로 되돌리면 CI에서 걸리게 해뒀다.

이제 손에 서빙 아티팩트가 생겼으니 11주차 서버 배포로 자연스럽게 이어진다. Keras 3 시대엔 `model.export()`가 정공법이라는 실전 교훈도 하나 챙겼고. 남은 ML 미결은 pitch shift 대상 지정과 SpecAugment 적용, 이렇게 2건으로 좁혀졌다.
