# 발표 피드백 — 검증하고, 시나리오를 짜고, 알고리즘을 다시 봐라

> 지금까지 정리한 설계 내용을 발표 자료로 만들어서 두 번째 발표를 진행했다.  
> 이번엔 피드백 세 가지가 나왔는데, 첫 번째 발표보다 더 구체적인 수준의 이야기들이었다.

---

## 발표 내용 요약

발표 흐름은 아래와 같았다.

- **이전 피드백 반영 결과** — 초인종 개인 등록(코사인 유사도 2차 필터링), 데모 시나리오 구상 중
- **하드웨어 구성** — ESP32, INMP441, HC-SR501(PIR), VL53L0X(ToF) 4종 구성 및 3단계 필터링 구조
- **Flask 서버** — AWS EC2 + Nginx + Gunicorn 구조, Let's Encrypt SSL, venv + requirements.txt
- **로그 저장** — SQLite + Flask-SQLAlchemy ORM, timestamp / sound_type / confidence / is_alerted
- **카카오톡 API** — 친구에게 보내기 방식, 액세스(6시간) + 리프레시(60일) 토큰 자동 관리
- **웹 대시보드** — Vite + React + shadcn/ui, REST API 폴링(3초), 접근성 UI 설계
- **초인종 등록 및 유사도 비교** — 3~5회 녹음 → 멜 스펙트로그램 템플릿 저장 → 코사인 유사도 2차 필터

## 교수님 피드백

### 1. 데모 시나리오를 구체화해라

> "어디서부터 시작해서 어디에서 끝날 건지 구체적으로 생각해보고 시나리오를 짜봐라."

첫 번째 발표에서도 나왔던 피드백인데, 이번엔 더 직접적으로 짚었다. 시스템이 동작한다고 해서 시연이 잘 된다는 보장은 없고, 어떤 순서로 무엇을 보여줄 건지 미리 그려놓지 않으면 현장에서 흐름이 무너질 수 있다는 뜻이었다.

### 2. 선례나 논문을 찾아보고 사전 테스트 방법을 고민해라

> "지금 구상한 시스템 설계가 성공률이 높다고 생각하는 단계인데, 선례나 논문을 찾아보고 사전 테스트 방식이 있는지 고민해봐라."

설계가 이론적으로 그럴듯해도 실제로 구현해봤을 때 예상대로 동작하는지는 별개의 문제라서, 비슷한 구조로 만든 사례나 관련 논문을 먼저 찾아보고 구현 전에 가능성을 검증하는 방법을 생각해두라는 의미였다.

### 3. DTW랑 코사인 유사도를 합쳐보는 방식을 고려해봐라

> "생각보다 연산량이 많지 않을 거고, 두 방식을 합친 알고리즘도 있을 테니까 찾아봐라."

연산량 부담 때문에 DTW를 배제하고 코사인 유사도만 쓰기로 했던 부분에 대한 피드백이었다. 생각보다 부담이 크지 않을 수 있고, 두 방식을 결합한 알고리즘이 이미 있을 수 있으니 먼저 찾아보라는 뉘앙스였다.

## 받아들인 것들

세 피드백 모두 지금 단계에서 당연히 해야 할 것들인데 미뤄두고 있었던 것들이었다.

데모 시나리오는 구현하다 보면 자연스럽게 정해지겠지 하고 계속 뒤로 밀어뒀는데, 시연 준비는 구현과 별개로 먼저 그림을 그려야 한다는 걸 다시 상기시켜 준 피드백이었다.

선례 조사는 설계에 확신이 생기다 보니 검증 없이 바로 구현 단계로 넘어가려 했는데, 그 자신감 자체가 리스크일 수 있다는 걸 짚어줬다.

DTW + 코사인 유사도 혼합 방식은 막연하게 "연산량이 많을 것 같다"고만 판단했지, 실제로 찾아보지는 않았던 거라서 조사해보는 게 맞았다.
