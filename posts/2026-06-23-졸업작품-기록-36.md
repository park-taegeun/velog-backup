## 5월에 짜둔 펌웨어를 실물에 올렸더니 함정 3종이 줄줄이 — ESP32-S3 첫 부팅 디버깅

5월 사전 준비 11일 동안 PlatformIO monorepo를 미리 짜두고 컴파일까지는 맞춰뒀었다. 부품이 없던 상태라 플래시를 못 했고, 그 코드가 한 달 넘게 그대로 남아 있었다. 부품이 전부 도착한 6/22에 드디어 첫 실물 부팅을 시도했는데 — USB-C 하나만 꽂아서 확인할 수 있는 카메라(camera_v1)와 WiFi(poc) 두 env부터 시작하기로 했다. 마이크/ToF는 브레드보드 결선이 필요하니까 2단계로 미뤘다.

"컴파일은 됐었으니까 금방 되겠지"라고 생각했는데 함정이 3종 나왔다 — pio 환경 소실, 빌드 잠복 회귀, WiFi 외장 안테나 미장착. 순서대로 잡으면서 결국 카메라 + WiFi 첫 부팅을 통과시켰다.

## 함정 1: pio가 통째로 사라졌다

첫 빌드 시도부터 pio CLI가 없다는 에러. 패키지 캐시(`~/.platformio/packages`)는 멀쩡한데 CLI 구동 venv만 증발한 상태였다.

원인은 5월에 venv를 `/tmp/pio-venv`에 깔았던 거였다. decisions.md 카테고리 16에 그 경로가 SSoT로 박혀 있었는데, macOS가 재부팅할 때 `/tmp`를 비워버리니까 한 달 사이에 날아간 거였다. 정적으로 기록해둔 내용이 시간이 지나면서 현실과 어긋난 첫 번째 케이스였다.

해결은 간단했다 — 공식 installer로 표준 위치 `~/.platformio/penv`에 재설치.

```bash
curl -fsSL https://raw.githubusercontent.com/platformio/platformio-core-installer/develop/get-platformio.py -o get-platformio.py
python3 get-platformio.py
```

`/tmp`가 근본 원인이었으니까 표준 위치로 이전하면 재발 자체가 사라졌다. 패키지 캐시는 이미 있어서 재다운로드도 없었다.

## 함정 2: WiFi 빌드(env:poc)가 깨졌다 — blacklist 잠복 회귀

pio가 살아났으니 본 빌드. env:poc(WiFi + HTTPS 더미)를 올리려는데 링커 에러가 떴다.

```
multiple definition of `setup()'
multiple definition of `loop()'
```

main.cpp / mic_test.cpp / tof_test.cpp 세 파일이 각자 setup() / loop()를 갖고 있어서 충돌한 거였다. 원인을 따라가 보니 platformio.ini의 env:poc 빌드 필터였다.

```ini
; 5월 시점의 env:poc (문제 상태)
[env:poc]
build_src_filter = +<*> -<camera_test_v1.cpp>
```

`+<*>`로 src/ 전체를 포함시키고 카메라 테스트만 제외하는 **blacklist 방식**이었는데, 5/10과 5/11에 mic_test.cpp / tof_test.cpp가 추가됐을 때 이 glob이 그 파일들도 빨아들여버린 거였다.

```ini
; camera_v1 / mic_dummy / tof_dummy (정상, whitelist 방식)
[env:camera_v1]
build_src_filter = -<*> +<camera_test_v1.cpp> +<camera_common.cpp>

[env:mic_dummy]
build_src_filter = -<*> +<mic_test.cpp>
```

카메라/마이크/ToF env들은 `-<*>`로 전체를 먼저 비우고 필요한 파일만 명시적으로 포함시키는 **whitelist 방식**이었다. 이 방식은 src/에 새 파일이 추가돼도 자동으로 빨아들이지 않아서 안전했다.

핵심은 env:poc가 5/8에 "컴파일 SUCCESS"로 검증됐을 때 src/에는 main.cpp 딱 하나만 있었다는 거다. 그 뒤 5/10·5/11에 파일이 추가됐고, poc를 그 사이에 한 번도 재빌드한 적이 없어서 한 달간 잠복하다가 첫 실물 빌드에서 터진 거였다.

이번 부팅은 "검증 전용, 코드 파일 0 수정" 규율로 진행하고 있었기 때문에 임시 우회로 처리했다.

```bash
# 파일 건드리지 않고 환경변수로 override
PLATFORMIO_BUILD_SRC_FILTER="-<*> +<main.cpp>" pio run -e poc -t upload
```

영구 수정(env:poc를 whitelist로 통일)은 별도 작업으로 미뤘고, 이게 decisions.md 카테고리 27.6에 "다음 작업" 항목으로 기록됐다.

### 왜 whitelist가 맞는가

같은 실수를 반복하지 않으려면 방식 자체를 교체해야 했다. `+<*>` blacklist는 "지금 있는 파일 기준으로 동작"하는데, 프로젝트가 계속 파일을 추가하는 구조라면 매번 새 파일을 제외 목록에 추가하지 않으면 묵시적 포함이 발생한다. `-<*>` whitelist는 반대 — 명시적으로 포함시키지 않는 한 아무 파일도 안 들어온다. 파일이 늘어나도 기존 env가 자동으로 영향을 받지 않는다.

## 함정 3: WiFi가 안 붙는다 — 외장 안테나 필수

빌드가 통과하고 부팅했는데 WiFi가 연결이 안 됐다. main.cpp는 PRIMARY / FALLBACK 두 SSID를 순서대로 시도하는 구조였는데 양쪽 모두 timeout으로 떨어졌다.

```
Trying PRIMARY...  [timeout]
Trying FALLBACK... [timeout]
WiFi connection failed.
```

코드(main.cpp)를 다시 봐도 이상한 게 없었다. SSID / 비번을 secrets.h에 박아둔 구조라 타이포도 없었고, 2.4GHz 대역도 문제없는 환경이었다. 양쪽 SSID가 동시에 timeout으로 떨어진다는 게 코드 문제보다는 RF 수신 자체가 안 되는 징후였다. 진단 0순위로 하드웨어를 의심했고, 정답이었다.

### XIAO ESP32-S3는 내장 안테나가 없다

XIAO ESP32-S3는 IPEX 전용 보드다. PCB 위에 패턴 안테나나 세라믹 안테나가 없고, 외장 u.FL 안테나를 꽂아야 RF가 살아난다. 안테나 없이 WiFi를 켜면 극도로 낮은 신호 강도로 간간히 잡히거나(가까운 공유기에서) 아예 못 잡히는 상태가 된다. 그리고 여기서 Sense 모델 전용 함정이 있었다.

### Sense 확장보드가 IPEX 커넥터를 덮는다

XIAO ESP32-S3 Sense는 메인보드 위에 카메라 확장보드(B2B 커넥터로 연결)가 올라가는 구조인데, 이 확장보드가 메인보드의 IPEX 안테나 커넥터 위치를 정확히 덮어버렸다. 안테나를 꽂으려면 확장보드를 분리해야 한다는 뜻이었다. 장착 순서는 이렇게 됐다.

1. 확장보드(B2B) 분리 → 메인보드 IPEX 커넥터 노출
2. u.FL 안테나 장착 — 한쪽 가장자리를 먼저 걸치고 반대쪽을 눌러서 딸깍. 수직으로 정통 누르면 잘 안 들어가는 구조
3. 확장보드 재결합

안테나를 장착하고 나서 부팅하니까 결과가 바로 달라졌다.

```
Trying PRIMARY...
Connected via PRIMARY (SSID=…, IP=…)
RSSI: -53 dBm
IP assigned in 0.7s
POST /api/v1/detect → 200 OK
```

PRIMARY 연결, RSSI -53dBm(강신호), IP 할당 0.7초, HTTPS POST 200까지 한 번에 통과했다. secrets.h의 SSID / 비번은 처음부터 정상이었고, 순전히 안테나가 원인이었다.

## (곁가지) 카메라 OV3660 확정 + PID 비교 버그

env:poc와 같이 부팅한 env:camera_v1 결과를 정리하면 이렇다.

| 항목 | 결과 |
| --- | --- |
| 카메라 init | OK |
| 센서 PID (시리얼) | 0x3660 → OV3660 확정 |
| PSRAM | 8MB OCTAL |
| xclk_freq_hz | 20,000,000 Hz |
| QVGA JPEG 연속 캡처 | 정상 (fb_get NULL 0건) |

보드 사양에 OV3660이라고 적혀 있었는데, 실측으로 PID `0x3660`이 찍혀 나오면서 확정됐다. decisions.md 카테고리 1에 업데이트.

그런데 여기서 버그 하나가 발견됐다. camera_common.cpp의 `sensorIdToName()` 함수에서 PID 비교가 이렇게 박혀 있었다.

```cpp
// camera_common.cpp (버그 상태)
if (sensor_id == 0x36) return "OV3660";    // ← 0x36 으로 잘려 있음
```

실제 OV3660의 PID는 `0x3660`인데 `0x36`으로 잘렸으니까 매칭이 실패해서 시리얼에 "UNKNOWN"이 찍혔다. 더 큰 문제는 이 비교가 실패하면 OV3660 전용 보정(dark-image 보정, Khangura 함정 #6)이 안 걸린다는 거였다. 캡처 자체는 정상이어서 빠르게 발견하기 어려운 잠복 버그였다.

이것도 이번 부팅은 "0 수정" 규율이라 코드를 건드리지 않고 발견만 기록해뒀다. 수정은 다음 작업에서 처리할 예정이다.

## 배운 것들

이번 부팅의 진짜 교훈은 **"정적으로 기록해둔 것이 시간이 지나면 현실과 어긋날 수 있다"**는 거였다.

`/tmp/pio-venv` 위치도, "5/8 컴파일 SUCCESS"라는 기록도, 마지막 검증 이후에 환경이 바뀌면 그 기록은 더 이상 보증이 아니다. pio venv는 macOS가 `/tmp`를 비웠고, poc 빌드는 그 사이에 src 파일이 늘었다. 검증 시점의 스냅샷이 현재 상태를 보장하지 않는다는 거 — 코드가 바뀌지 않아도 환경이 바뀐다.

whitelist vs blacklist 얘기도 결국 같은 맥락이었다. `+<*>` blacklist는 "지금 상태 기준 성공"이고, 나중에 파일이 추가되면 묵시적으로 실패한다. `-<*>` whitelist는 새 파일이 추가돼도 기존 env에 영향이 없다. 변화를 예상하고 설계하는 쪽이 더 나았다.

"검증 전용 0 수정" 규율로 돌린 것도 잘 된 선택이었다. 발견한 버그(env:poc / PID)를 코드와 섞지 않고 기록만 해뒀으니까, 이번 부팅에서 뭔가 깨졌을 때 "내가 건드린 게 없으니 원래 있던 문제"라고 격리할 수 있었다. 디버깅 범위가 훨씬 단순해졌다.

XIAO Sense 안테나 함정은 데이터시트나 핀맵만 봐선 모르는 거였다. Sense 확장보드가 안테나 커넥터를 덮는다는 게 실물로 직접 해봐야 아는 종류였다.
