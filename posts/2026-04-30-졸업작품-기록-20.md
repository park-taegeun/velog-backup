# "하나가 됐으면 전체도 의심해봐야지" — 시스템 4개 영역 1차 증거 검증

> 카메라+마이크 검증 방법론이 먹혔고, 그대로 시스템 전체에 적용했다. 결과로 설계 3가지가 즉시 바뀌었다.

---

## 첫 조사가 만든 자신감

카메라+마이크 조사가 "이론상 가능합니다" 한 줄이 아니라 ESP-IDF 드라이버 코드와 5건의 사례로 결론이 났던 게 컸다. 같은 방법론을 시스템 전체로 확장하면 본 개발 진입 전에 더 많은 함정을 발견할 수 있겠다는 생각이 들었다.

6월~8월에 들어가면 발견하는 함정마다 일정이 1~2주씩 밀린다. 5월 초에 발견하면 설계 단계에서 흡수 가능한데, 시간 차이가 결정적이었다.

---

## 의심이 남는 4개 영역

전체 시스템을 다 검증할 필요는 없었다. 이미 검증된 것과 PoC 중 자연스럽게 확인할 수 있는 것은 빼고, **"여기서 막히면 시스템 설계가 무너지는" 4개 영역**만 골랐다.

| # | 영역 | 핵심 질문 |
|---|------|---------|
| 1 | VL53L5CX 사람 검증 | 8x8 그리드로 사람 형체를 실시간 검증할 수 있나? |
| 2 | EC2 t2.micro 메모리 | 1GB RAM에서 YAMNet + STT 동시 처리가 되나? |
| 3 | Google STT 한국어 | 인터폰 음질에서 한국어 정확도가 어느 정도인가? |
| 4 | 카카오톡 이미지 첨부 | 친구 메시지 API에 이미지 첨부가 정말 되나? |

## 검증 #1: VL53L5CX 사람 검증 — 🟡 단계적 알고리즘 채택

"VL53L5CX + person detection" 전용 오픈소스는 GitHub에서 0건이었는데, ST 공식과 Edge Impulse, 학술 논문에서 알고리즘 사례 5건을 확보했다. ST 공식 케이스 스터디(천장 2.4m 마운트)에서 NanoEdge AI 분류 98.14%, CNN 97.1%라는 수치가 나왔다.

채택한 단계적 알고리즘 구조는 이렇다.

- **Stage A**: zone count 임계값 — 1m 이내 ≥8개 zone 동시 트리거 = "사람 후보"
- **Stage B**: Motion Indicator + per-zone threshold — 정적 사물(택배상자, 화분) 무시
- **Stage C** (선택): NanoEdge AI 32-프레임 분류기 — A+B로 부족할 때만
- **Stage D** (선택): Passing-by filter — 1m 이내 ≥1.5초 정지 = 진짜 방문

잔여 리스크가 하나 남았는데, ST의 98% 케이스는 천장 2.4m 마운트고 우리는 벽면 도어벨(눈높이 ~1.5m)이라서 이 시나리오 직접 데이터는 없었다. PoC 5주차에 50cm/1m/1.5m 거리와 다양한 옷 색상으로 자체 측정이 필수였다.

## 검증 #2: EC2 t2.micro — 🔴 t3.small로 업그레이드

이게 제일 충격적이었다. **TensorFlow를 import만 해도 RSS가 340MB** 였다.

근거가 명확했다. TF 공식 이슈 #36459에서 import 직후 RSS가 47.6MB에서 340.2MB로 뛰었고, 실제 t2.micro에서 Flask+Gunicorn OOM kill 사례가 여러 건 발견됐다.

워커 2개 기준 추정:
- 워커당 (TF 340MB + 모델 50MB + Flask/STT 80MB) ≈ 470MB
- 워커 2개 × 470MB + 마스터 ≈ 1.0~1.2GB
- → t2.micro 1GB에서 swap 없으면 거의 확정 OOM

졸작 시연에서 OOM 한 번이면 망하는 거라서, 6개월 × 9,000원 = 54,000원으로 안정성을 사는 게 맞다고 판단했다. **t3.small(2GB)로 업그레이드 확정.**

## 검증 #3: Google STT 한국어 — 🟡 Naver Clova로 전환

이 조사에서 가장 큰 발견은 rtzr의 공개 벤치마크였다.

| 서비스 | CER (일반) | CER (인터폰급 저음질) |
|--------|----------|-------------------|
| Google STT v2 | 11.82% | **14.11%** |
| Naver Clova Speech | 8.05% | **6.49%** |
| Whisper large | 12.06% | 17.27% |

인터폰급 노이즈 환경에서 **Naver Clova가 Google보다 CER이 절반 수준**이었다. 가격은 비슷하고(월 100건 기준 ~400원), 한국어 특화 + PSTN(전화망) 강점도 인터폰 시나리오에 딱 맞았다. "택배요" 같은 핵심 키워드에 대한 키워드 부스팅도 지원됐다.

Whisper 자체 호스팅도 검토했는데, 한국어에서 쓸만한 정확도가 나오는 모델은 t2.micro/t3.small에서 OOM이라 사실상 옵션이 아니었다.

자막이 잘못 인식되면 A-3 자체의 가치가 떨어지는 구조라서, CER 2배 차이는 졸작에서 결정적이었다. **Google STT → Naver Clova로 전환 확정.**

## 검증 #4: 카카오 이미지 첨부 — 🟡 카카오 자체 API로 해결, S3 불필요

이게 가장 긴장됐던 검증이었다. 카카오 친구 메시지에 이미지 첨부가 안 되면 시스템 설계 전체를 뒤엎어야 했으니까.

세 가지 발견이 나왔다.

**발견 1**: 카카오 메시지 템플릿은 이미지 URL 형태만 받는다. EC2 로컬 디스크 경로로는 안 되고 외부 호스팅이 필요하다는 의미였다.

**발견 2**: 처음엔 "S3 도입해야 하나" 싶었는데, **카카오 자체 이미지 업로드 API**가 있었다. EC2 로컬 사진을 multipart로 업로드하면 카카오 CDN URL이 발급되고, 그걸 feed 템플릿 image_url에 넣으면 됐다. HTTPS 자동, 100일 보관, S3 추가 불필요.

**발견 3**: "친구에게 보내기"는 비즈 앱 심사가 필요한데, 졸작 일정에 큰 리스크였다. 그런데 컨셉이 "청각장애인 본인이 받는 시스템"이라서 **"나에게 보내기"로 단순화**가 가능했다. 비즈 앱 심사 회피, 토큰 관리 1인분, 동의항목 1개만.

**나에게 보내기 + 카카오 이미지 업로드 API 확정.** 외부 인프라 의존성 0개 추가, 심사 리스크 0.

## 변경 사항 정리

| 항목 | Before | After |
|------|--------|-------|
| EC2 인스턴스 | t2.micro | **t3.small** (월 +9,000원) |
| STT 서비스 | Google STT | **Naver Clova Speech** |
| 카카오 메시지 방식 | 친구에게 보내기 | **나에게 보내기** |
| 이미지 호스팅 | S3 (?) | **카카오 이미지 업로드 API** |
| VL53L5CX 알고리즘 | 단일 거리 임계값 | **단계적 Stage A→D** |

부수 효과도 컸는데, 외부 인프라 의존성 0개 추가에 비즈 앱 심사 리스크가 사라지면서 STT 정확도는 2배 향상됐고 OOM 리스크도 제거됐다. 추가 비용은 6개월 기준 약 56,400원이었다.

## 본 개발 시 자체 측정 필요 항목

조사 보고서에서 정직하게 명시한 한계들은 결국 직접 측정이 답이었다.

1. **YAMNet 메모리 실측** (t3.small에서) — 워커 2개+모델+STT 동반 RSS
2. **VL53L5CX 벽면 도어벨 정확도** (5주차) — 50cm/1m/1.5m, 다양한 옷 색상
3. **Naver Clova STT 인터폰 음질 WER** — INMP441 녹음 10건 자체 측정
4. **카카오 토큰 갱신 24시간 안정성** — refresh_token 자동 갱신

## 두 번의 조사를 마치고

세 가지가 분명해졌다.

첫째, **"이론상 가능"으로는 부족하다.** 1차 증거(코드/사례/벤치마크)를 명시적으로 요구하는 게 결정적이었다.

둘째, **사전 검증의 시점이 중요하다.** 5월 초에 발견한 함정은 설계 단계에서 흡수됐는데, 7월에 발견했으면 일정이 깨졌을 거였다.

셋째, **객관적 벤치마크는 발표 자료가 된다.** rtzr CER 6.49% vs 14.11% 같은 수치는 "왜 Naver Clova를 골랐나?" 질문에 그 자체로 답이 됐다.

즉시 변경 3건이 나오긴 했는데, 시스템 전체의 구현 가능성에는 빨간불이 없었다. 이 자신감이 본 개발 진입에 큰 힘이 됐다.
