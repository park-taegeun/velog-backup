## 랩미팅 피드백

랩미팅에서 별다른 지적은 없었고, 방향 제시가 한 줄이었음

> "이렇게 만든 것을 실제로 멀티모달 축에 어떻게 전달할지... 파이프라인?
> 산출물: 음향 특징 추출 알고리즘"

74번까지의 작업은 전부 검증이었음
- 어조 정보가 텍스트 위에 무언가를 얹는지
- 어느 구간에서 얹는지

정보가 존재한다는 확인은 마무리되었고, 남은 질문은 그 정보를 실제로 어떻게 넘길 것인가
즉 **검증에서 구현으로 넘어가라는 취지**

## 무엇이 문제인가

지금까지 벡터를 만들려면 노트북을 순서대로 돌려야 했음
-> 실험을 위한 구성이며 다른 사람에게 넘길 수 있는 형태가 아님

멀티모달 과제이므로 파트마다 담당자가 있고 언젠가 합쳐야 함
-> "이런 것을 만들어 이런 형태로 넘긴다"가 정의되어야 함

현재 파이프라인)
```
wav → 63차 추출 → 층2 계산 → projection → 소프트 토큰 → gemma
```

이 중 어디까지가 오디오 모듈이고 어디부터가 융합단인지 경계가 정해진 적이 없음

## 환경 제약

GPU 서버가 사용 기간 종료로 영구 폐쇄됨
- 서버 내 산출물과 학습 체크포인트 전부 재접근 불가
- 로컬 RTX 5070 12GB로는 gemma E4B를 올릴 수 없어 학습·추론 모두 불가능

이 제약이 범위 결정에 직접 작용함
- projection까지를 산출물로 잡으면 학습된 가중치가 필요한데, 체크포인트가 없고 재학습도 불가능하므로 착수 자체가 안 됨
- 반면 63차 추출과 층2 계산은 학습과 무관하므로 현재 환경에서 가능

## 산출물의 경계를 어디에 그을 것인가

세 가지 후보)

| 후보 | 조건 |
|---|---|
| 63차 추출까지 | 입출력 규격만 정의. GPU 불필요 |
| 층2 계산 포함 | 화자 기준점 확보가 문제로 남음. CPU 가능 |
| projection까지 | 학습된 가중치가 산출물. 현재 착수 불가 |

**선택: 63차 추출 + 층2 계산까지**

근거)
- 과제 명세가 "음성에서 MFCC 및 피치변화량을 추출하여 어조를 분석"이며 "모듈 통합"은 별도 항목. 명세상 구분과 일치함
- projection 이후는 전달 형식이 결정되어야 설계할 수 있는 부분
- 다만 이 범위는 잠정이며 확인이 필요함

## 추출기 분리

**먼저 코드를 찾음**
- 노트북 50, 51번이 저장소에 없어 소실된 줄 알았음
- git 히스토리를 조회한 결과 애초에 커밋된 적이 없었음
- 그러나 동일한 계산이 `scripts/nb50_extract.py`에 파라미터까지 남아 있었음

-> 추출 로직은 소실되지 않았음

**이 파일은 두 층으로 나뉨**

| 구분 | 내용 |
|---|---|
| 계산부 (약 50줄) | 소리에서 숫자 63개를 뽑는 부분 |
| 조달 코드 (약 145줄) | zip 순회, mp4 디코딩, csv 조인 등 데이터셋 전용 |

조달 코드는 이 데이터셋에서 벡터를 뽑기 위한 것이므로 산출물이 아님
계산부만 `src/tone_fusion/features.py`로 분리, 수치 로직은 한 줄도 변경하지 않음

**입력 규격**
- 기존 코드는 이미 메모리에 올라온 16kHz mono 배열만 받고 파일 경로를 받지 않음
- 실제 XR에서는 파일이 존재하지 않고 마이크 신호가 직접 들어오므로 배열 입력이 맞음
- 그러나 검증과 테스트에는 경로 입력이 편함
- **두 형태를 모두 받도록 함** -> 실시간 전환 시 앞단만 교체하면 되는 구조

**검증**
- 옮긴 모듈과 원본 함수의 출력 차이가 **0.0**
- 이식 과정에서 값이 달라지지 않았으므로 기존 실험과 같은 계산임이 확인됨

**부수적으로 정정된 것**

63차의 실제 구성
```
f0 기본       6
MFCC 평균    13
MFCC std     13
f0 동적       5
delta1 std   13
delta2 std   13
```

기존 기록에 "MFCC delta 26"으로 뭉뚱그려져 있던 항목이 delta1과 delta2로 나뉜 것이었음
층1의 어느 성분이 기여했는지를 나중에 분리할 때 필요한 정보

## 벡터 재확보

**문제**
- 서버 폐쇄로 63차 벡터 파일에 접근 불가
- 모듈은 생겼으나 그 모듈이 만든 결과물이 없는 상태
- 층2를 설계하려면 화자별 벡터가 필요하므로 이것이 선행 조건

**기존 스크립트를 그대로 쓸 수 없었던 이유**
- `nb50_extract.py`는 서버의 라벨 csv에서 발화 구간을 읽어 옴
- 그 csv도 서버와 함께 소실됨
- 발화 구간과 라벨을 로컬 원본 JSON에서 직접 파싱하는 스크립트를 새로 작성
- 계산은 분리한 모듈을 호출하므로 추출 로직이 두 곳에 존재하지 않음

**결과**
```
21,564발화 / 80화자
NaN 0 / inf 0 / 분산 0 컬럼 0
유성음 비율 중앙 0.544
```

기존 로컬 재구축(21,606발화)과 42발화 차이
- 0.2초 미만 구간을 제외한 필터로 설명됨
- 기존 재구축은 라벨만 파싱해 이 필터가 없었음
- 규모가 일치하므로 같은 대상을 다루고 있음이 확인됨

**부수적으로 확인된 것**
- 한 대화에서 두 화자의 f0 평균이 서로 달랐음
  -> 화자별 기준선이 실제로 구분된다는 뜻
  -> 평소 대비 편차라는 층2의 정의가 데이터에서 성립할 자리가 있음
- 반대로 한 대화에서 한 화자의 발화는 7개 수준
  -> 기존 실험이 화자당 200발화 이상으로 기준점을 만든 것과 큰 차이
  -> 실전에서 기준점 표본이 얼마나 부족해지는지가 드러남

## 결론

연구 단계가 바뀌었다
지금까지는 "어조 정보가 기여하는가"를 재는 실험이었고, 이제는 "그것을 어떻게 전달할 것인가"의 구현이다

산출물의 경계를 63차 추출과 층2 계산까지로 잡았다
과제 명세의 구분과 일치하며, 계산 자원이 없는 현재 환경에서 실제로 진행할 수 있는 유일한 범위이기도 하다

추출기를 독립 모듈로 떼어냈고 원본과의 차이가 0.0임을 확인했다
전에는 노트북을 순서대로 돌려야 벡터가 나왔지만, 이제는 모듈 하나를 import하면 63차가 나온다
노트북도 서버도 필요하지 않다

서버에서 잃은 벡터도 새 추출기로 다시 확보했다
21,564발화 / 80화자이며 기존 재구축과 규모가 일치한다

다만 범위는 잠정이다
63차까지인지 층2 포함인지, projection을 포함할지는 확인이 필요하다

그리고 확인 과정에서 다음 문제가 드러났다
층2는 화자별 기준점을 필요로 하는데 한 대화에서 한 화자의 발화가 7개뿐이다
기존 실험은 화자당 200발화 이상을 썼다

실전에서는 기준점을 어떻게 만들 것인가
그리고 애초에 기존의 기준점 설계가 실전에서 계산 가능한가
다음 편의 주제다
