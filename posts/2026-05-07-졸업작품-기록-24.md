# 22주 졸업작품을 위한 운영 체계 — SSoT, 채팅방 분리, AI 위임 전략

> 학부생 1명이 4개 도메인을 22주 동안 굴리려면 코드보다 운영 체계가 먼저였다.

---

## 운영 체계가 필요했던 이유

4/29 중간 발표가 끝나고 본격 개발 진입을 앞두면서 위기감이 들었다. firmware / ML / server / dashboard, 4개 도메인을 병렬로 22주 동안 혼자 진행해야 하는 구조였는데, 채팅방을 새로 열 때마다 "어디까지 했더라?"를 반복하고 결정 사항이 어디 있는지 헷갈리는 상황이 이미 몇 번 있었다.

단순히 GitHub 쓰는 걸로는 부족했다. "어디에 뭘 기록하고, 어디서 결정하고, 코드는 누가 짜고, 그걸 어떻게 추적하는가"를 한 번 명확히 정리해야 했다. 5/7 하루를 메타 트랙에 투자한 이유였다.

---

## SSoT 우선순위 + 채팅방 운영 구조

### SSoT 4개 후보 비교

여러 곳에 분산된 정보 중 어디를 "진짜 기준"으로 삼을지부터 정했는데, 후보가 네 가지였다.

- **GitHub repo** (decisions.md / decisions-log.md): 정밀하고 기계적으로 추적 가능
- **의사결정 채팅방**: 흐름과 맥락을 같이 추적 가능
- **도메인 채팅방**: 도메인별 작업 격리
- **노션**: 시각화와 가독성

비교해보니 정답은 명확했다. **GitHub repo를 최상위 SSoT**로 두고, 나머지는 역할에 맞게 아래에 배치했다.

```
1. GitHub repo (decisions.md / decisions-log.md) — 최상위 SSoT
2. 의사결정 채팅방 — 도메인별 분리
3. 도메인 위임 프롬프트 생성기 채팅방 — 직접 코드 X, 위임 프롬프트만 출력
4. Claude Code MCP — 실제 작업 수행
5. 노션 PoC 트래킹 — 사람용 VIEW (SSoT 아님)
```

### 작업 체인

```
[의사결정 채팅방]
    ↕ 일정/방향성 합의
[도메인 위임 프롬프트 생성기]
    ↓ 위임 프롬프트 (find-skills + MCP 활용 지시)
[Claude Code MCP]
    ↓ 실제 작업 (skill + github/context7/firecrawl/playwright/notion)
[GitHub repo + 노션 트래킹]
```

중요한 원칙이 하나 있었는데, 도메인 채팅방은 코드를 직접 짜지 않고 **위임 프롬프트만 출력**하는 역할이었다. 실제 코드는 Claude Code MCP가 담당하고, 학부생 본인은 결과 검증과 의사결정만 담당하는 구조였다.

### 채팅방 분리 트리거

채팅방이 무거워지면 분리해야 하는데, 세 가지 기준으로 잡았다.

- **시점 기반**: chunk 종료 (사전 준비 종료 / PoC 종료 / 영역 전환)
- **컨텍스트 무게 기반**: 응답이 느려지거나 이전 결정이 헷갈리기 시작할 때
- **사건 기반**: 큰 의사결정 후 (Plan B 전환 / 일정 충돌 발견)

채팅방 분리 시 인계 패키지 형식도 표준화했다. SSoT 링크, 직전 채팅방 완료 사항 5~7개, 진행 중/미결 사항 3~5개, 다음 채팅방 첫 액션 1~3개, 미결정/보류 사항, 작업 원칙 순서로 구성했다.

## Claude Code MCP + Skills 활용 원칙

### 위임 프롬프트 작성 표준 순서

코드 작성이나 리서치를 위임할 때마다 지켜야 하는 순서를 강제로 정했다.

1. **find-skills MCP로 적합 skill 탐색 먼저** (생략 불가)
2. skill 발견 시 → skill + 관련 MCP 조합으로 수행
3. skill 없으면 → MCP 단독 수행

### 활용 가능 MCP 5개

| MCP | 역할 |
| --- | --- |
| **github** | repo 작업 (commit, push, PR) |
| **context7** | Arduino / PlatformIO 공식 문서 조회 |
| **firecrawl** | 라이브러리 호환성 / 사례 검색 |
| **playwright** | GitHub Issues / 블로그 스크래핑 |
| **notion** | 트래킹 페이지 갱신 |

### 자체 검증 3단계 강제

코드 작성 관련 모든 위임 프롬프트에 다음 내용을 항시 포함하기로 했다.

- **① 효율성 검토**: 시간/메모리/CPU 점유율, 불필요한 연산, 알고리즘 복잡도
- **② 리팩토링 검토**: 가독성, DRY 원칙, 매직 넘버 const화, 네이밍 일관성
- **③ 오류 방지 검토**: 엣지 케이스, null/undefined, 메모리 누수, 동시성, 보안, 컴파일 경고

각 단계별 발견 사항과 수정 사항을 출력 끝에 별도 섹션으로 명시하도록 강제했다.

적용 범위는 신규 코드 작성, 기존 코드 수정, 라이브러리 통합, 빌드 설정 변경이었고, 단순 문서 작성이나 노션 갱신, 리서치는 예외로 뒀다.

## 노션 PoC 트래킹 도입

### 왜 노션인가

GitHub decisions.md는 정밀하지만 마크다운 텍스트라 가독성이 낮았다. 22주 진행 과정을 한눈에 보고 싶은 니즈가 있었는데, 단 노션은 SSoT가 아니라 **사람용 VIEW**라는 걸 명확히 했다. 의사결정은 절대 노션에서 하지 않고, GitHub decisions.md와 충돌이 생기면 GitHub 우선이었다.

### 페이지 구조

```
📂 띵동(Ddingdong) PoC 트래킹
├── 🎯 현재 상태 대시보드 (overwrite, 매일 갱신)
├── 📅 일자별 진행 로그 (데이터베이스, 최신순)
├── 🧪 사전 검증 결과 보관 (데이터베이스)
├── 🚨 미결정 / 트래킹 항목 (데이터베이스)
├── 📊 일정 vs 실제 (사전 준비 11일 + 22주 마스터)
└── 🔗 외부 링크
```

컬러 코드도 통일했는데, 🟢 완료 / 🟡 진행 중 / 🔴 이슈 / ⚪ 보류 / 🎯 마일스톤으로 고정했다.

### 매일 갱신 5단계 표준 워크플로우

매일 작업 종료 시 Claude Code MCP에 노션 갱신을 위임하는 방식인데, 5단계가 표준이었다.

1. DB1 일자별 로그에 새 row 추가 (날짜 + 단계 + 상태 + 핵심 결정 + commits)
2. 페이지 상단 메타 콜아웃 overwrite (마지막 갱신 / 현재 단계 / 다음 마일스톤)
3. 오늘의 작업 체크박스 갱신
4. 일정 vs 실제 표 해당 날짜 행에 실제 결과 입력
5. DB3 미결정 항목 상태 자동 전환 (트리거 임박 시 🟡 보류 → 🔴 트리거 임박)

## Git 브랜치 전략 (5/18 도입 예정)

### 현재 (사전 준비 11일, ~5/17)

main 직 push를 유지했는데, 학부생 1명 + Claude Code MCP 구조에서 작업 단위가 작아서 아직은 괜찮은 판단이었다.

### 5/18 PoC 1주차 시작 시 정식 도입

GitHub Flow 단순화 모델을 도입하기로 했다.

- 브랜치 명명: `feat/{domain}-{task}` (firmware/ml/server/dashboard/fix)
- main 보호 룰: PR을 통해서만 머지
- Squash merge 기본
- PR 머지 조건: 컴파일 통과 + 한국어/이모지 commit + 금지 파일 미수정 + self-approve
- Claude Code MCP: 브랜치 생성 + 작업 + push + PR 자동 처리
- 학부생: PR 리뷰 + 머지

5/18에 도입하는 이유는 그 시점에 도메인 4개가 병렬로 시작되기 때문이었는데, main이 깨지면 시연과 발표에 직접 영향을 주는 구조라서 안전망이 필요한 시점이 딱 그때였다.

## 매일 밤 작업 종료 루틴

매일 작업이 끝나면 의사결정 채팅방에서 3가지를 동시에 출력하는 루틴을 만들었다.

1. **decisions.md 갱신 위임 프롬프트** → Claude Code MCP에 던지기 (그날 결정 + 작업 결과 + 미해결 이슈 종합, github MCP로 commit + push)
2. **프로젝트 지침 수정본** → 학부생이 직접 클로드 프로젝트 지침 갱신 (정적 변경 시만, 매일 강제 X)
3. **노션 갱신 위임 프롬프트** → Claude Code MCP에 던지기 (5단계 워크플로우 기반)

충돌 시 우선순위: **GitHub decisions.md > 프로젝트 지침 > 노션**

컨텍스트 무게 자체 모니터링도 추가했는데, Claude가 채팅방이 무거워졌다고 판단하면 능동적으로 분리를 제안하는 방식이었다. 신호는 6가지로 정의했다. 응답 텀 길어짐, 이전 결정 재확인 빈도 증가, 동일 주제 반복 질문, 컨텍스트 윈도우 한계 근접, 한 채팅방에 도메인 4개 이상 누적, 큰 의사결정 후 chunk 종료 시점 도래.

## 회고

### 5/7 메타 트랙 종합

단순히 GitHub + Notion을 쓰는 수준에서 SSoT 우선순위 + 작업 체인 + 자체 검증 3단계를 갖춘 운영 체계로 진화했다. 학부생 본인은 의사결정과 검증을 담당하고, 반복적인 작업은 Claude Code MCP에 위임하는 구조가 정착됐다.

22주 후 발표 시 "어떻게 운영했는가" 자체가 어필 요소가 될 수 있다는 것도 부수 효과였다.

### 솔직한 평가

운영 체계 짜는 데 5/7 하루를 투자한 건 펌웨어 작업 시간 압박으로 돌아오는 선택이었다. 매일 3-set 루틴도 작업 종료 후 30~40분 추가 부담이 생기는 구조였고, 솔직히 지켜지지 않는 날도 있을 거라는 걸 알면서 만든 체계였다.

그래도 22주 누적 효과로 충분히 회수 가능하다고 판단했다. 채팅방이 무거워질 때마다 "어디까지 했더라?"를 반복하는 비용이 30~40분보다 훨씬 크다는 걸 이미 경험했으니까.
