# 파이프라인은 돌려봐야 안다 — ML 함정 4개 잡고 YAMNet 예비 학습 88.7%까지

전편(6/30)이 대시보드 **앞단** — 사람이 보는 화면을 다듬은 페르소나 정합 작업이었다면, 이번(7/1)은 **뒷단** — 소리를 실제로 분류하는 모델을 세우는 작업이었다. 경험을 다듬는 것과 엔진을 돌아가게 만드는 것, 같은 시스템의 다른 층위였다.

하드웨어는 부품 결선이랑 실물 검증이 필요해서 시간이 걸린다. 반대로 ML은 부품이 없어도 할 수 있는 크리티컬 패스였다. 그래서 이번 chunk는 "하드웨어가 시간 걸리는 동안 ML을 당기자"에서 시작했다. dataset 파이프라인을 세우고 "이제 학습만 돌리면 되겠지" 했는데 — 실제 데이터를 넣는 순간 함정이 4개나 튀어나왔다.

## 파이프라인은 코드 리뷰를 통과해도, 돌려봐야 진짜다

`ml/pipeline`을 00~05 스테이지로 설계했다. preprocess(16kHz mono 검증) → 원본 단위 group split → train만 augment → 05 최종 조립. 합성 더미 데이터로 각 스테이지를 검증했고, 로직 자체는 코드 리뷰에서도 문제없어 보였다.

그런데 실제 데이터(01_clips 2,798개)를 넣는 순간부터 함정이 하나씩 드러났다. 결론부터 말하면 **합성 더미 검증은 필요조건이지 충분조건이 아니었다** — 더미로는 절대 못 잡는 "실제 데이터의 지저분함"이 있었다.

### 함정 ① 빈 클립 — augment가 FFT 크래시로 죽다

```
ValueError: Invalid number of FFT data points (0) specified.
```

첫 실행에서 augment 스테이지가 이렇게 죽었다. 파보니 AI Hub에서 받은 화재경보(fire_alarm) 원본 데이터 중에 **길이가 0인 빈 wav 파일 6개** 가 섞여 있었다. 데이터를 다운로드할 때부터 손상돼 있었던 건지, 원본 자체가 문제였던 건지는 알 수 없었지만, 어쨌든 이 6개가 preprocess를 그냥 통과해서 augment까지 살아남았다가 FFT 연산에서 0으로 나누는 꼴이 나서 터진 거였다.

```python
# config.py
MIN_DURATION_SEC = 0.1
MIN_SAMPLES = 1600   # 16kHz * 0.1s
```

preprocess 단계에 최소 길이 가드를 추가해서, 이 기준 미달인 클립은 원본 삭제 없이 **skip 처리** 하도록 했다. 원본은 그대로 두고 파이프라인만 걸러내는 방향 — 나중에 데이터가 복구되거나 다른 용도로 필요할 수 있으니 삭제는 하지 않았다.

## 함정 ② 파일단위 누수 — 가장 값진 크래시

가드를 넣고 재실행했더니 이번엔 다른 곳에서 걸렸다. 파이프라인에 넣어둔 **누수 방지 가드가 진짜 leakage를 잡아낸 것** 이었다.

원본 오디오를 여러 개의 3초 조각으로 잘라서 클립을 만드는 구조였는데, 파일명이 이런 패턴이었다.

```
9Oqtu..._0000000.wav
9Oqtu..._0003000.wav
9Oqtu..._0006000.wav
```

같은 원본(`9Oqtu...`)에서 나온 3개 조각인데, split을 파일 단위로 돌리다 보니까 이 셋이 train / test로 **흩어져서** 배정되는 문제가 있었다. 같은 원본에서 나온 소리가 train에도 있고 test에도 있으면, 모델이 test 셋에서 "본 적 없는 새 소리"를 맞히는 게 아니라 사실상 **본 적 있는 소리를 다시 맞히는** 상황이 된다. 정확도가 가짜로 부풀려지는 전형적인 데이터 누수였다.

이게 좋은 크래시였던 이유는, 이 가드가 없었으면 파이프라인이 조용히 끝까지 돌아서 학습까지 진행됐을 거고, 그 결과 나온 정확도는 실제보다 부풀려진 숫자였을 거다. 지침에 "파일 단위 분할"이라고 적혀 있었던 게, 실제로 데이터를 보니 그게 아니라 **원본(source) 단위 분할** 을 의미해야 했다는 걸 데이터가 직접 알려준 셈이었다.

```python
# split.py (구조)
PIECE_SUFFIX_PATTERN = re.compile(r"_\d{7}$")

def source_key(stem: str) -> str:
    return PIECE_SUFFIX_PATTERN.sub("", stem)   # 조각 접미사 제거 → 원본 식별자
```

파일 stem에서 7자리 조각 접미사를 떼어내면 원본 식별자가 나오고, 이 원본 단위로 group split을 돌려서 같은 원본의 모든 조각이 반드시 같은 split에 속하도록 고쳤다.

여기서 자잘한 함정이 하나 더 있었다. 파일명 중 일부가 `_30.0_40.0_0000000` 같은 소수점을 포함하는 형태였는데, `Path().stem`을 그대로 쓰면 이 소수점을 확장자 구분자로 착각해서 stem이 잘못 잘리는 문제가 있었다. 이건 `Path` API 대신 순수 문자열 정규식만으로 처리해서 회피했다.

## 함정 ③ stale — 내 진단이 틀렸다는 걸 MCP가 반증했다

원본 단위 split으로 고치고 다시 학습을 돌렸는데, 이번엔 학습 도중에 또 빈 클립 크래시가 났다. 분명히 preprocess에서 빈 클립을 걸렀는데 왜 다시 나오지, 싶었다.

여기서 내가 직접 진단을 하나 내렸다 — **"split이 01_clips(원본, 가드 이전 상태)를 읽고 있어서 빈 클립이 부활한다"** 는 가설이었다. 그럴싸해 보였고, 이 가설을 바탕으로 수정 위임까지 짰다.

근데 위임을 받은 MCP가 바로 고치지 않고 `git log -L`로 코드 히스토리를 실측했다. 결과는 예상과 달랐다 — **split은 PR #10이 처음 만들어진 시점부터 단 한 번도 01_clips를 읽은 적이 없었다.** 처음부터 02_preprocessed를 읽는 구조였다. 내 진단은 완전히 no-op이었다.

진짜 원인은 다른 데 있었다. preprocess와 augment가 02/03 폴더에 결과를 쓸 때, 이전 실행에서 남아 있던 **stale(오래된) 파일을 지우지 않고 덧쓰기만** 하고 있었다. 그래서 예전에 빈 클립 가드가 없던 시절에 만들어진 stale 빈 클립이 02 폴더에 계속 남아 있었고, 그게 재현된 거였다. 가드는 새로 처리하는 파일에는 잘 작동했지만, 과거에 이미 만들어진 찌꺼기 파일까지는 안 건드렸던 것.

```python
# preprocess.py / augment.py (구조)
def clean_stage_class_dirs(stage_dir: Path):
    # 폴더명 검증 + 직하위 파일만 (안전 가드)
    for class_dir in stage_dir.glob("*/"):
        if class_dir.name in VALID_CLASSES:
            for f in class_dir.glob("*.wav"):   # 하위 재귀 X
                f.unlink()
```

write 직전에 02/03 폴더를 auto-clean하도록 고쳤다. 폴더명이 유효한 클래스인지 검증하고, 직하위 파일만 지우도록 안전장치를 걸었다(재귀 삭제는 위험하니까 배제).

이 사건이 decisions.md에 **학습 19**로 신설됐다 — "AI 본인의 진단(위임 프롬프트 포함)도 코드로 재검증해야 하고, no-op이면 맹목적으로 적용하지 않는다"는 원칙. 이전부터 있던 "AI가 박은 것도 catch 그물 대상"(학습 17)이 한 단계 더 들어간 형태였다. 이번엔 AI가 박은 *값*이 아니라 AI가 내린 *진단 자체*가 검증 대상이 됐고, MCP가 그 진단을 그대로 따르는 대신 코드로 반증한 뒤에 pivot 승인을 받고서야 수정을 진행했다.

## EPERM 벽 — OS 권한이 개발을 막다

함정을 다 잡고 학습을 돌리려는데 전혀 다른 종류의 벽이 나왔다. 데이터가 데스크탑에 있었는데, 학습용 Python venv가 그 폴더에 접근할 때마다 `EPERM`이 났다.

macOS의 TCC(Transparency, Consent, and Control) 권한 시스템이 원인이었다 — 터미널에서 실행되는 프로세스가 데스크탑/문서 폴더 같은 보호된 위치에 접근하려면 명시적 권한이 필요한데, venv 파이썬 프로세스가 그 권한을 못 받은 상태였다. 터미널 앱에 권한을 줘봐도, 재발급을 해봐도 계속 막혔다.

결국 근본적으로 우회하는 쪽으로 갔다. Finder에서 데이터 폴더를 드래그해서 **홈 디렉토리** (`~/ML 학습 데이터/`)로 옮겼다. TCC가 보호하는 위치 자체를 벗어나니까 문제가 사라졌다. 코드는 멀쩡한데 OS 권한이 발목을 잡는 경험이었는데, 생각보다 실전 개발에서 자주 만나는 종류의 벽이었다.

## 예비 학습 성공 — test 88.7%

함정을 다 정리하고 나서야 본 학습을 돌릴 수 있었다.

`ml/training`에서 YAMNet을 frozen backbone으로 두고, 그 위에 학습 가능한 head만 얹었다.

```python
# model.py (구조)
# YAMNet (hub, frozen) → 1024-dim embedding
# → Dense(128, activation='relu') → Dropout(0.5) → Dense(3, activation='softmax')
# trainable params: 131,587 / non-trainable: ~3.7M (YAMNet backbone)
```

클래스 불균형(doorbell 436개로 최소, fire_alarm 다수)을 반영해서 `class_weight`를 자동 계산해 넣었다(doorbell 2.10 / knock 1.31 / fire_alarm 0.57).

30 epoch을 돌리고 early stopping이 18번째에서 최적점을 잡았다.

```
Epoch 18 (best): val_accuracy 0.9016, val_macro_f1 0.8564
```

그리고 한 번도 안 쓴 test set(n=424)에 대해 평가한 결과가 이렇게 나왔다.

| 지표 | 값 |
|------|-----|
| test accuracy | **0.887** |
| test macro_f1 | **0.848** |

클래스별로 나눠보면 doorbell f1 0.736(recall 0.742), knock f1 0.881(recall 0.889), fire_alarm f1 0.927(recall 0.921)이었다.

### 사전테스트 대비 — 왜 fine-tuning이 필요한지 숫자로 증명

이전에 pre-trained YAMNet(fine-tuning 전) 그대로 돌려본 사전테스트가 있었는데, 그때 Top-1 정확도가 초인종 30% / 노크 40% / 화재경보 20%였다. 이번 fine-tuning 결과의 recall과 나란히 놓으면 이렇다.

| 클래스 | 사전테스트 (pre-trained) | 이번 (fine-tuned, recall) |
|--------|--------------------------|----------------------------|
| 초인종(doorbell) | 30% | 74% |
| 노크(knock) | 40% | 89% |
| 화재경보(fire_alarm) | 20% | 92% |

"왜 fine-tuning이 필요한가"라는 질문에 말이 아니라 숫자로 답할 수 있게 됐다.

### confusion matrix가 다음 할 일을 알려줬다

test set에서 헷갈린 패턴을 보니, **doorbell을 fire_alarm으로 잘못 분류한 게 10건으로 최다** 였다. 그리고 doorbell이 436개로 세 클래스 중 데이터가 제일 적었다. 데이터가 적은 클래스에서 오분류가 제일 많이 난다는, 어떻게 보면 당연한 패턴이었는데, 이게 8주차 직접 녹음 계획에서 **초인종 90클립을 우선순위 1번** 으로 잡은 근거가 됐다.

오분류 방향도 살펴봤는데, 이게 나쁘지 않은 패턴이었다 — doorbell을 fire로 착각하는 건 **과알림**(초인종 왔는데 화재경보로 잘못 뜨는) 쪽이고, 반대로 진짜 위험한 방향인 fire를 doorbell로 놓치는 오분류는 8건뿐이었다. 페르소나 관점에서 안전 쪽으로 치우친 오류였다.

## 정리하면

파이프라인은 코드 리뷰나 합성 더미 검증을 다 통과해도, 실제 데이터를 넣어봐야 진짜 함정이 드러난다는 걸 이번에 확실히 느꼈다. 빈 클립(데이터 자체의 결함) → 파일단위 누수(설계 가정의 결함) → stale(재현성의 결함), 세 층위가 다 달랐고 각자 다른 원인이었다.

그중에서도 함정 ③이 가장 인상 깊었다. 내가 세운 진단이 그럴싸했는데 실측으로 반증됐고, 그걸 그대로 따르지 않고 코드로 확인한 뒤 진행한 게 이번 chunk의 핵심이었다. 6/30에 "AI가 박은 값도 검증 대상"이었다면, 7/1은 "AI가 내린 진단도 검증 대상"으로 한 단계 더 들어간 셈이었다.

다음은 이 test 성적표가 알려준 대로 doorbell 직접 녹음을 우선하는 것, 그리고 하드웨어 쪽 브레드보드 확보 후 마이크·ToF 결선으로 넘어가는 2단계다.
