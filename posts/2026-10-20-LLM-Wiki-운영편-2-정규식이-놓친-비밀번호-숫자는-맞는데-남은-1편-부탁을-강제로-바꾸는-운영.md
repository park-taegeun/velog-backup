## 정규식이 놓친 비밀번호

### 상황

노션 2차 반영은 운영편에서 세운 절차를 그대로 따랐습니다. 대기실(inbox)에 넣고, 비밀값 사전 검사를 하고, 선별해서 원본 창고에 복사한 뒤, Claude Code가 계획을 내면 승인하고 반영하는 순서입니다. 사전 검사 결과는 비밀값 1건(JWT 서명용 secret, 마스킹 처리)과 개인정보 2건이었습니다.

그런데 사전 검사를 통과한 파일을 Claude Code가 읽다가, 실습 노트 한 줄에 **데이터베이스 root 비밀번호가 평문으로** 적혀 있다고 보고했습니다. 원본 창고에는 이미 복사됐지만 아직 커밋 전이었습니다.

### 왜 놓쳤나 — 오탐과 미탐의 트레이드오프

비밀값 검사에는 두 종류의 실패가 있습니다.

- **오탐(false positive)**: 문제가 아닌데 막는 것. 구축편에서 실험 수치 `671.3042602539062`를 주민등록번호로 잡은 일이 그 예입니다.
- **미탐(false negative)**: 문제인데 통과시키는 것. 이번의 짧은 비밀번호가 그 예입니다.

둘은 시소 관계입니다. 오탐을 줄이려고 규칙을 좁히면 미탐이 늘어납니다. 기존 규칙은 오탐을 피하려고 "16자 이상, 숫자 포함"인 값만 잡게 되어 있었고, 그래서 짧은 비밀번호는 처음부터 검사 대상이 아니었습니다.

이번 사고를 막은 것은 **심층 방어(defense in depth)**였습니다. 보안 장치 하나에 기대지 않고, 성격이 다른 장치를 여러 겹 두어 한 겹이 놓친 것을 다른 겹이 잡게 하는 설계입니다.

| 겹 | 장점 | 약점 |
|---|---|---|
| 기계 검사 (정규식) | 빠르고 결정론적, 매번 같은 결과 | 정해둔 모양만 잡음 |
| 의미 검사 (AI가 읽고 판단) | "이 줄은 비밀번호를 적어둔 것"이라는 문맥을 이해 | 느리고 가끔 틀림 |

첫 번째 겹이 놓친 것을 두 번째 겹이 잡은, 교과서 같은 사례였습니다.

### 대응 순서

**사고 대응(incident response)**은 보안 사고가 났을 때 피해를 막고, 범위를 확인하고, 재발을 막는 순서를 말합니다. 이번에는 다음 순서로 대응했습니다.

| 순서 | 한 일 | 목적 |
|---|---|---|
| 1. 가리기 | 원본 창고와 로컬 사본 양쪽에서 값을 가림 (커밋 전) | 더 퍼지지 않게 |
| 2. 범위 확인 | 공개·비공개 두 레포의 git 기록 전체 검색 → 0건 | 이미 퍼졌는지 |
| 3. 교체 | 비밀번호를 무작위 값으로 바꾸고 안전한 저장소에 보관 | 옛 값을 무력화 |
| 4. 재발 방지 | 문맥 기반 탐지 규칙 추가 (패치 6.9) | 같은 유형 차단 |
| 5. 전수 재검사 | 새 규칙으로 기존 파일 전체 재검사 → 공개 0건, 비공개 0건 | 놓친 게 그 1건뿐인지 |

1번은 사람이 직접 했습니다. 원본 창고는 "추가만, 수정 금지" 구역이라 AI는 원본을 고칠 수 없게 막혀 있기 때문입니다.

### 실수 하나 — 그래서 "지우기보다 바꾸기"

대응 중에 실수가 하나 있었습니다. 값을 가리는 처리 스크립트가 **값을 터미널에 한 번 그대로 출력**했습니다. 파일에서는 지웠지만, 이번에는 터미널 기록에 남은 것입니다.

이 일로 원칙이 분명해졌습니다. **파일에서 지우는 것보다 값을 바꾸는 것이 확실한 해결입니다.** 지우기는 "어디에 복사됐는지 다 찾았다"는 가정에 기대지만, **비밀값 교체(secret rotation)**, 즉 노출됐을 수 있는 값을 새 값으로 바꿔 옛 값을 쓸모없게 만드는 방법은 그 가정이 필요 없습니다. 옛 값이 어디에 남아 있든 더는 열리지 않기 때문입니다.

이후 모든 검사·처리 명령은 값을 출력하지 않고 **"파일:줄 (종류)"만** 출력하도록 바꿨습니다. 성공할 때뿐 아니라 실패할 때도 값이 찍히지 않게 짰습니다.

## 패치 6.9 — 길이가 아니라 문맥으로

규칙을 넓히는 대신 **판단 기준을 바꿨습니다.** "값이 얼마나 긴가(길이)"가 아니라 "값이 어디에 적혀 있나(문맥)"를 봅니다.

| 구분 | 내용 |
|---|---|
| 새로 잡는 자리 | "비밀번호 입력(…)" 같은 안내 문구 뒤, `password:` 같은 설정 키, DB 접속 명령의 `-p` 옵션, 계정 생성 SQL |
| 통과시키는 것 | 자리표시자(`<REDACTED>`, `your_password` 등), 환경변수 참조, 코드 변수명 |

### 적용 전에 전수 검사부터

적용 순서는 **가짜 값으로 새 규칙 시험 → 기존 파일 전체를 새 규칙으로 미리 검사 → 교체**였습니다. 공개 쪽에서 하나라도 걸리면 교체를 중단하게 했습니다.

전수 검사를 먼저 한 이유는 운영을 멈추지 않기 위해서입니다. 새 규칙은 배포 직전 public-gate에도 들어갑니다. 공개 파일 중 하나라도 새 규칙에 걸리면 다음 배포가 갑자기 막힙니다. 적용 전에 0건을 확인해야 규칙을 바꿔도 운영이 멈추지 않습니다.

### 새 규칙이 자기 자신을 막았다

시험 중 재미있는 일이 있었습니다. **새 규칙이 자기 설명 주석에 적힌 예시 비밀번호 때문에 자기 자신의 커밋을 막았습니다.** 규칙은 정확하게 동작한 셈입니다. 배포 전에 주석 예시를 자리표시자로 고쳤고, 패치 체크리스트에 "패치 파일 자체도 새 패턴으로 스캔한다"를 추가했습니다. 검사 규칙은 자기 자신에게도 적용됩니다.

### 못 잡는 것도 문서에 적는다

남은 한계도 있습니다. **영문자로만 된 비밀번호**는 여전히 못 잡습니다. 잡으려 하면 일반 영어 단어까지 걸려 오탐을 감당할 수 없습니다. 이 영역은 의미 검토가 맡는다고 문서에 명시했습니다. 못 잡는 것을 숨기지 않고 적어두면, 나중에 사람이 "여기는 기계가 안 본다"는 것을 알고 의미 검토를 생략하지 않게 됩니다. 이것도 설계입니다.

## 노션 2차 — 판단 보류를 규칙으로

이번에 넣은 108개는 연구실 노트, 백엔드 스터디, 코딩테스트, AI 코딩 도구 노트입니다. 본문 없이 링크만 있는 목차 파일 약 33개는 정리 대상에서 빼고 기록만 남겼습니다.

### 판단 보류 5건 → 규칙 5줄

공개 기준만으로 판단할 수 없는 경우, Claude Code는 그 부분을 비공개로 두고 묻습니다. 이번에는 5건이 나왔고, 답을 대화에만 두지 않고 CLAUDE.md에 기준으로 추가했습니다.

| # | 상황 | 정한 기준 |
|---|---|---|
| 1 | 학회에 게재·발표된 팀 논문 | 기술 내용은 공개, 저자·소속·내 역할은 비공개 |
| 2 | 외부 교육 프로그램 참여 기록 | 프로그램 이름은 공개, 지부명·운영진은 제외 |
| 3 | 면접 대비 CS 문답 | 내 말로 정리한 개념은 공개, 지원 동기·면접 맥락은 비공개 |
| 4 | 교재를 정리한 코딩테스트 노트 | 출처(sources)에 교재명을 밝힘 |
| 5 | 인터넷 프롬프트를 통째로 옮긴 자료 | 위키에 넣지 않고 로그에만 남김 |

다음에 같은 상황이 오면 AI는 묻지 않고 처리합니다. **예외 처리가 반복되면 규칙이 됩니다.** 운영편의 "승인은 파일로 남겨야 승인이다"의 연장선입니다.

### 정정은 처음부터 두 종류로

운영편에서는 AI가 정정을 1곳 승인에서 48곳으로 넓혔습니다. 이번에는 처음부터 둘로 나눴습니다.

| 종류 | 예 | 처리 | 건수 |
|---|---|---|---|
| 원본 안에 근거가 있는 정정 | 오타, 같은 글의 앞뒤 불일치, 나중 회의 결론과 다른 앞부분 기록 | 바로 고치고 "(정정)" 표시 | 약 20건 |
| 원본 밖 지식이 필요한 정정 | 일반 기술 지식으로만 판단 가능한 오류 | 과정을 모르는 독립 에이전트가 검증 | 27건 중 근거가 분명한 8건만 반영 |

나머지 19건은 검증 결과 반영할 것이 없었습니다. 그리고 도구의 단축키·기본값처럼 **버전마다 바뀌는 사실**은 고치지 않고 "작성 시점 기준 (YYYY-MM)"으로 표기했습니다. 지금 기준으로 고치면 그것도 언젠가 틀리기 때문입니다.

## 성장 측정 2차 — 6/8 → 8/8

신규 공개 페이지 11개(claude-code, spring-boot, spring-data-jpa, swagger, claude-code-hook, rest-api, jwt, eeg-감정-인식, 시간-복잡도, python-코딩테스트-문법, 코딩테스트-알고리즘)가 생겼고, 기존 페이지 30여 개가 보강돼 위키는 **119 → 130페이지**가 됐습니다. 비공개 평가에는 새 문항 3개를 추가해 8문항으로 늘렸습니다.

| 비공개 8문항 | 검색 적중 | 사실 정확 | 위키만으로 답함 |
|---|---|---|---|
| 노션 2차 넣기 전 | 6/8 | 6/8 | 6/8 |
| 노션 2차 넣은 후 | **8/8** | **8/8** | **8/8** |

1차(1/5 → 5/5)에 이은 두 번째 확인입니다. 이번 평가에서는 두 가지가 더 눈에 띄었습니다.

- **틀린 것을 고쳤나도 본다**: 새 문항 하나는 공개 위키에 있던 **잘못된 해석**(나중 회의에서 정정된 내용)을 반영 후 바로잡았는지 확인하는 문제였습니다. 평가가 "새로 배웠나"뿐 아니라 "틀린 것을 고쳤나"까지 보게 된 것입니다.
- **평가가 결함을 찾는다**: 평가 답변이 한 분석 수치의 앞뒤가 맞지 않는다고 지적했습니다. 비율로 역산한 모집단 크기와 평가셋 크기가 달랐습니다. 원본으로 확인할 수 없어 고치지 않고 페이지에 "확인 필요" 메모를 남겼습니다. 평가가 채점 도구를 넘어 위키의 결함 탐지기로도 쓰인 사례입니다.

## 모순 17건 — 지어내지 않기

공개 사이트에 남아 있던 모순 표시 17건을 네 갈래로 분류했습니다.

| 분류 | 뜻 | 처리 |
|---|---|---|
| 시간 차이 | 실험이 진행되며 값이 바뀐 것 | 이력으로 정리 |
| 조건 차이 | 측정 조건이 달라 값이 다른 것 | 조건을 명시 |
| 출처 오타 / 옮겨 적기 오류 | 원본이나 위키 작성 과정의 실수 | 정정 |
| 판단 불가 | 기록으로도 기억으로도 확인 불가 | 원인 미확인 |

17건 중 **8건을 해결**했습니다. 그중 2건은 위키를 작성하며 생긴 옮겨 적기 오류였습니다. 예를 들어 위키에는 "화자 828명"으로 적혀 있었는데 원본은 "발화 828개"였습니다. 사람 수와 문장 수는 전혀 다른 숫자입니다.

나머지 9건은 원인을 확인할 수 없었습니다. 여기서 가장 쉬운 실수는 그럴듯한 설명을 지어내 한쪽으로 고치는 것입니다. LLM이 가장 잘 저지르는 실수이기도 합니다. 그래서 고치지 않고 아래 형태로 남겼습니다.

```markdown
> [!note] 기록 간 차이 · 원인 미확인
> 확인 경로: (예) 연구실 회의에서 원 실험 기록으로 확인
```

그런데 노션 2차가 들어오자 그중 **1건이 새 원본에서 근거를 찾아 저절로 풀렸습니다.** 현재 미확인은 8건입니다. 위키가 쌓일수록 예전 문제가 풀리는 것도 "복리"의 한 모습입니다.

## 자동화 첫날의 빈틈 — 숫자는 맞는데 1편이 남았다

### 상황

운영편 글을 발행한 날 밤 22:00, launchd(정해진 시각에 프로그램을 실행하는 macOS 시스템 서비스)로 돌아가는 자동 수집이 AI 없이 그 글을 원본 창고에 저장했습니다. 다음 날 위키 반영 명령 `/velog-wiki`를 실행했더니 "새 글 0편"이라며 아무것도 하지 않았습니다.

숫자는 완벽했습니다. Velog, 백업 레포, 노션 대시보드, 위키 원본이 모두 **207편**으로 일치했습니다. 그런데 결정론적 점검 스크립트의 미처리 원본 수는 0이 아니라 **1**이었습니다.

```bash
python3 .tools/wiki_check.py pending   # 반영 안 된 원본 수 (0이 정상)
```

### 정합성과 완결성은 다른 확인이다

- **정합성(consistency)**: 여러 시스템의 숫자가 서로 맞는가
- **완결성(completeness)**: 들어온 것이 전부 처리됐는가

이번에는 정합성이 완벽했는데 완결성이 깨져 있었습니다. 숫자가 다 맞아서 오히려 정상처럼 보였습니다. 운영편에서 "합계가 같은지부터 확인"하는 습관을 만들었는데, 합계 확인만으로는 이 빈틈을 볼 수 없었습니다.

### 이벤트 기반 vs 상태 기반

원인은 `/velog-wiki`의 설계 방식이었습니다.

| 방식 | 기준 | 약점 |
|---|---|---|
| 이벤트 기반 (edge-triggered) | "이번 실행에서 무엇이 새로 생겼나" | 다른 누군가 그 이벤트를 먼저 가져가면 영원히 놓침 |
| 상태 기반 (level-triggered) | "지금 처리 안 된 것이 무엇인가"를 매번 계산 | 매번 전체를 계산하는 비용 |

`/velog-wiki`는 "이번 실행에서 새로 가져온 글"만 반영하는 이벤트 기반이었습니다. 자동 수집이 먼저 글을 가져가 버리면 `/velog-wiki` 입장에서는 새 글이 없으니, 그 글은 영원히 반영되지 않는 구조였습니다. 자동 수집 알림은 "/velog-wiki로 정리하세요"라고 안내하는데, 시키는 대로 하면 아무 일도 일어나지 않았던 것입니다.

**패치 6.10**에서 반영 대상을 **"미처리 원본 전부"(상태 기반)**로 바꾸고, 작업을 마칠 때 미처리 수가 0인지 스스로 확인하게 했습니다. 적용 후 0개를 확인했습니다. 쿠버네티스의 조정 루프(reconcile loop)가 "원하는 상태와 현재 상태의 차이"를 매번 계산해 맞추는 것과 같은 발상입니다. 누가 언제 가져왔든 처리 안 된 것은 결국 처리됩니다.

자동화는 켜는 순간이 아니라 **처음 실제로 돌았을 때** 빈틈이 드러납니다. 수집과 반영을 따로 만들면, 둘 사이의 경계에서 일이 샙니다.

## 스스로 보고한 위반 → 부탁 대신 강제

같은 날 Claude Code가 위키 목차 두 줄을 셸 명령 `sed -i`(파일을 그 자리에서 고치는 명령)로 수정했습니다. 가드인 PreToolUse 훅(도구 실행 직전에 도는 검문 스크립트)은 Write/Edit 도구 호출만 검사하므로, 셸로 쓰면 "쓰는 순간 비밀값 검사"를 건너뜁니다.

Claude Code는 **스스로 규칙 위반을 보고**했습니다. 고친 내용은 날짜와 문구뿐이라 커밋 검사에서도 문제가 없었습니다. 그래도 규칙서의 부탁("파일은 Write/Edit 도구로만")을 더 세게 쓰지 않고, **가드가 셸로 위키를 쓰는 것 자체를 막도록** 강화했습니다.

| 구분 | 내용 |
|---|---|
| 막는 것 | `sed -i`, 리다이렉트(`>`, `>>`, 명령 출력을 파일에 쓰는 기호), `tee`, 위키 밖에서 안으로 `cp`/`mv` |
| 시험 | 막아야 할 명령 8개 차단, 허용해야 할 명령 6개(읽기, 검색 등) 통과 확인 후 적용 |

구축편에서 겪은 "Python 스크립트로 가드를 비켜 간 쓰기"와 같은 계열의 빈틈입니다. 그때는 규칙서에 한 줄을 추가했고, 이번에는 강제로 막았습니다. **부탁이 한 번 어겨지면, 그 부탁은 강제로 옮길 차례입니다.** AI가 위반을 숨기지 않고 보고했기 때문에 가능한 개선이기도 합니다.

같은 날 Claude Code의 커밋이 권한 검사에서 이유 표시 없이 거부된 일도 있었습니다. 원인을 추측해서 권한을 넓히지 않고, 사람이 직접 커밋해 처리했습니다.

## 회고 — 운영 3일에서 굳어진 원칙

1. **기계 검사와 의미 검사를 겹친다.** 정규식은 모양을, AI는 문맥을 봅니다.
2. **지우기보다 바꾼다.** 교체는 "다 찾았다"는 가정이 필요 없습니다.
3. **검사·처리 명령은 값을 출력하지 않는다.** 위치만 출력하고, 실패할 때도 마찬가지입니다.
4. **검사 규칙은 자기 자신에게도 적용된다.** 패치 파일도 스캔합니다.
5. **못 잡는 것도 문서에 적는다.** 한계를 아는 사람이 빈칸을 메웁니다.
6. **처리는 상태 기준으로 한다.** "새로 온 것"이 아니라 "처리 안 된 것".
7. **숫자 일치와 처리 완료는 따로 본다.** 정합성과 완결성은 다른 확인입니다.
8. **부탁이 어겨지면 강제로 옮긴다.** 그리고 모르는 것은 지어내지 않습니다.

## 마무리

이번 편에서는 노션 2차를 반영하며 정규식이 놓친 비밀번호와 자동화 첫날의 빈틈을 만났고, 둘 다 "부탁"이 아니라 "강제"로 고쳤습니다. 구축 후 3일 동안 패치가 10건 나왔는데, 전부 설계 단계에서는 보이지 않고 실제로 돌렸을 때 드러난 문제였습니다.

지금까지 위키의 효과를 보여준 근거는 평가 점수뿐입니다. 다음 편은 **실사용편**입니다. 쌓인 백엔드·CS 페이지로 면접 예상 질문을 근거 링크와 함께 뽑아보며, 위키가 실제 일에서 얼마나 쓸모 있는지 확인해보겠습니다.
