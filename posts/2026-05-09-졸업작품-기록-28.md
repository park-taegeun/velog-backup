## 킥과 디테일 — 지난 발표 피드백을 데모로 연결시키기

4/29 중간 발표에서 교수님 피드백 두 가지를 받았는데, 둘 다 시스템 방향을 엎지 않고 흡수할 수 있는 방향이었다.

## 4/29 중간 발표 피드백

교수님 피드백은 두 가지였다.

첫째, "킥이 필요하다" — A와 A+처럼 비슷한 두 개를 청각장애인에게 구별해줄 수 있는 참신한 무언가가 있으면 좋겠다는 뜻이었다. 기능 자체는 좋은데 차별화 포인트가 더 강해야 한다는 의미였고, 뉘앙스는 기능 추가 쪽에 가까웠다.

둘째, "데모 시나리오를 구체화해라" — 시연 보는 입장에서 몇 초 안에 간단하게 끝날 것 같다는 막연함이 있다는 피드백이었다. 시스템 구조는 복잡한데 시연은 너무 단순해 보인다는 지적이었다.

두 피드백 다 받았을 때 처음엔 막막했는데, 생각해보니 연결된 문제였다. 킥이 없으면 시연도 임팩트가 없고, 시나리오가 없으면 킥도 전달이 안 된다.

## 피드백 1 대응 — 두 기능 추가로 킥 만들기

### 고민 시작점

기존 흐름은 마이크 → 음향 감지 → ML 분류 → 카카오톡 알림이었는데, 이 흐름에서 청각장애인 입장에서 진짜 빠져 있는 게 뭔지를 다시 봤다.

알림이 와도 여전히 답답한 상황이 있었는데, 문 너머에서 무슨 일이 일어나고 있는지 알 수 없다는 거였다. 비장애인은 인터폰으로 "누구세요?" 묻고 답을 듣지만, 청각장애인은 그게 안 된다. 결국 문을 열기 전까지 모르거나, 위험을 감수하고 열거나, 무시하거나 셋 중 하나였다.

### 기능 1: 도어캠 — "누가 왔는지"

카메라로 방문자 사진을 촬영해서 카카오톡 알림에 첨부하는 기능이었다. 인터폰 음성을 들을 수 없는 청각장애인이 가장 답답한 부분인 "누가 왔는지"를 시각적으로 전달하는 구조였다.

### 기능 2: 음성 자막화 — "뭐라고 했는지"

마이크로 방문자 발화를 추가 녹음하고 STT로 텍스트화해서 자막으로 알림에 첨부하는 기능이었다. STT는 Naver Clova Speech를 썼는데, rtzr 공개 벤치마크에서 인터폰급 노이즈 환경 CER이 6.49%로 Google STT(14.11%)보다 2배 이상 정확했던 게 근거였다.

### 컨셉 한 줄

> "기존 알림이 '띵동'으로 끝났다면, 본 시스템은 누가 와서 뭐라고 했는지까지 알려준다."

이게 교수님이 말씀하신 킥이라고 판단했다. 기능을 추가한 게 아니라 청각장애인의 진짜 불편함을 해소하는 방향으로 시스템이 자연스럽게 확장된 거였다.

## 피드백 2 대응 — 데모 시나리오 구체화

### 막연한 출발점

처음엔 페르소나 잡고 시나리오 흐름도 그리고 시간 옵션(5분/10분/15분)까지 나눠서 설계하려고 했는데, 너무 무거워졌다. 뭔가 방향이 잘못됐다는 느낌이 들었는데, 학과 졸작 발표 환경을 다시 떠올리니 단번에 단순화됐다.

우리 학과 졸업작품 발표는 강의실에 각자 부스를 차리고 교수들이랑 학생들이 돌아다니면서 보는 축제 부스 형태였다. "발표"가 아니라 "체험"이 본질이었다.

### 시연 컨셉 픽스

체험형 부스 — 관람객(교수, 학생)이 직접 노크하고 초인종 누르고, 카카오톡 알림을 눈앞에서 받아보는 형태로 잡았다. "보고 끝나는 시연"이 아니라 "직접 만져보고 끝나는 시연"이 목표였는데, 청각장애인 사용자가 어떤 경험을 하는지 1~2분 안에 직접 느끼게 만드는 게 핵심이었다.

### 부스 공간 구성

3영역으로 분할했는데, 각자 역할이 명확했다.

```
[좌측: 폼보드 가벽]    [가운데: 책상]    [우측: 가이드/포스터]
  현관문 모형            시연 인터랙션       안내 + 차별점
  ESP32 + 센서 내장      도어벨 4개           시스템 통계
  노크면 + 손잡이         스마트폰/노트북
```

**좌측 폼보드 가벽 (70×130cm, 10T)**

현관문 모형으로 만들었는데, 인터폰 박스 안에 ESP32-S3 Sense + OV2640 카메라 + INMP441 마이크 + VL53L5CX ToF를 통합했다. 노크면에 MDF 5T 보강재를 뒤쪽에 부착한 이유가 있었는데, 폼보드만 두드리면 ML이 학습한 진짜 문 노크 소리와 달라서 분류 정확도가 떨어질 위험이 있었다. PoC 1주차 마이크 단독 테스트로 재검토 예정이다.

**가운데 책상 (약 120×60cm)**

시연용 도어벨 4개를 책상 앞쪽에 일렬 배치했는데, 서로 확실히 다른 멜로디 4개로 선정 예정이다. 카카오톡 알림 받을 스마트폰과 대시보드 띄울 노트북도 책상 뒤쪽에 뒀다. ESP32에서 나온 USB-C 케이블이 폼보드 뒤로 빠져서 노트북에 연결되는 구조라 겉에서 보면 깔끔하게 보이는 게 목표였다.

**우측 가이드/포스터**

관람객이 부스에 도착하면 먼저 보게 되는 자리인데, 시스템 차별점과 핵심 통계를 한 번에 인지할 수 있게 구성할 예정이다.

### 진입점 3가지 — 자유 선택형 시연

관람객이 어느 진입점이든 어떤 순서든 자유롭게 선택하는 방식으로 운영하기로 했는데, 학부생이 머뭇거리는 관람객한텐 ②를 적극 추천할 예정이다.

#### 진입점 ① 노크 + 발화

가벽을 노크하고 "안녕하세요 택배입니다" 같은 인사말을 하면, ESP32가 감지 → 서버로 전송 → ML이 노크로 분류한다.

- 5초 안에 카카오톡 1차 알림: "누군가 노크했어요" (텍스트)
- 15초 안에 카카오톡 2차 알림: 방문자 사진 + 발화 자막

관람객이 스마트폰에서 알림이 두 번 울리는 걸 직접 보는 구조인데, 핵심 메시지는 "누가 와서 뭐라고 했는지" 였다.

| 기능 | 적용 여부 |
| --- | --- |
| ML 분류 | ✅ |
| ToF 사람 검증 | ✅ |
| SP/DTW 개인화 | ➖ |
| 방문자 사진 | ✅ |
| STT 자막 | ✅ |
| ToF 우회 | ➖ |

#### 진입점 ② 초인종 등록 + 분리 시연

이 진입점이 가장 임팩트가 크다고 판단했는데, 흐름이 이렇다.

1. 도어벨 4개 중 하나 골라서 "우리집 초인종"으로 등록 (3~5번 누름)
2. 다른 도어벨 누르면 알림 X — 옆집 초인종으로 판단했기 때문
3. 등록한 도어벨 누르면 1차 + 2차 알림 정상 발송
4. 해제하고 다른 도어벨로 재등록 가능 — 이사 가도, 초인종 바꿔도 등록만 하면 됨

핵심 메시지는 "우리집 vs 옆집 구분" 이었다. 옆집 초인종에 잘못 반응해서 문을 열어주는 일이 청각장애인한텐 단순한 불편이 아니라 실제 안전 위험이 될 수 있는데, 이걸 SP/DTW + cosine distance로 해결하는 구조를 관람객이 직접 체험하게 되는 시연이었다.

#### 진입점 ③ 화재경보

학부생이 핸드폰으로 화재경보 음원을 재생하는 방식으로 진행하기로 했다. 관람객이 직접 트리거하는 게 안전상 어렵기도 하고, 실제 감지기를 부스에서 작동시키면 다른 팀 시연에 방해가 될 수 있어서였다.

이 진입점의 차별점은 ToF 사람 검증 우회였는데, 진입점 ①②는 문 앞에 사람이 있어야 알림이 발송되는 구조인 반면, 화재경보는 자고 있어도, 아무도 없어도 즉시 알림이 가는 구조였다. 화재 났을 때 가장 위험한 게 청각장애인인데, 그래서 안전 관련 이벤트는 위치 검증을 우회하도록 설계했다.

추가로 정부 지정 화재 시 대응 수칙도 함께 발송하는데, 청각장애인이 화재 상황에서 안내방송을 못 들으니까 검색할 여유도 없다는 판단이었다. 2차 알림 없이 1차만 빠르게 발송하는 구조다.

핵심 메시지: "안전 우선, 자고 있어도 알림 + 대응 가이드"

## 시연 핵심 메시지 3가지

세 진입점에서 보여주는 게 다르긴 한데, 결국 세 가지 메시지로 수렴됐다.

**① "누가 와서 뭐라고 했는지" — 사진 + STT 자막 (진입점 ①②)**

기존 시각 신호표시기는 빛만 깜박이는 구조인데, 띵동은 방문자 정보를 풍부하게 전달한다. 시각 신호표시기 보급률이 0.3%에 불과한 현실에서, 청각장애인이 스마트폰에서 바로 확인할 수 있는 구조라는 게 차별점이었다.

**② "우리집 vs 옆집 구분" — SP/DTW 개인화 (진입점 ②)**

같은 아파트면 초인종 소리가 같은 경우가 많은데, 사용자가 자기 집 초인종을 등록하면 시스템이 구분해준다. 어떤 집 초인종이든 학습 가능하고, 이사 가거나 초인종이 바뀌어도 재등록하면 된다.

**③ "안전 우선, 자고 있어도 알림" — 화재경보 ToF 우회 (진입점 ③)**

청각장애인이 화재 상황에서 가장 취약한 이유가 경보음을 못 듣기 때문인데, 사람 유무와 관계없이 즉시 알림이 발송되고 대응 수칙까지 같이 전달되는 구조였다.

## 회고

두 피드백 모두 시스템 방향 자체를 엎지 않고 자연스럽게 흡수할 수 있었는데, 생각해보면 처음 설계가 충분히 확장 가능한 구조였기 때문이기도 했다.

데모 시나리오 구체화 과정에서 가장 크게 배운 건 "발표"가 아니라 "체험"이 본질이라는 거였다. 처음엔 페르소나, 시나리오 흐름도, 시간 옵션까지 너무 무겁게 접근했다가, 학과 부스 형태라는 걸 다시 떠올린 순간 단번에 단순화됐다. 직접 만져보고 1~2분 안에 끝나는 시연이 핵심 메시지 전달에 훨씬 강력하다는 걸 이번에 다시 확인했다.

남은 과제는 도어벨 4개 모델 선정, 노크면 보강재 검증, 가이드 보드 디자인 정도가 있었는데, 이건 PoC 1주차 이후 단계에서 정리할 예정이다.
