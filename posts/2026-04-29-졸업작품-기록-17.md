# 5초 알림은 깨졌다 — 그래서 나는 알림을 둘로 나눴다

> A-1+A-3 통합으로 컨셉은 잡혔는데,  
> 막상 시간을 계산해보니 기존 요구사항이 산산조각 났다.  
> "그냥 10초로 늘릴까"를 잠깐 고민했다가, 더 나은 방법을 찾았다.

---

## 5초 알림이 깨졌다

기존 요구사항 중 하나가 "소리 감지 후 알림까지 5초 이내"였다. 카메라 캡처 + STT가 추가되면서 흐름을 시간으로 분해해봤는데,

| 작업 | 시간 |
|------|------|
| 소리 감지 트리거 | ~0.1초 |
| ToF 사람 검증 | ~0.5초 |
| 마이크 녹음 (STT용) | 3~5초 |
| 카메라 캡처 | ~0.5초 |
| multipart 업로드 (사진+WAV) | 1~3초 |
| 서버: YAMNet 추론 + STT API | 2~5초 |
| 카카오톡 발송 | 0.5~1초 |
| **합계** | **9~17초** |

5초는 명백히 불가능했다. 처음엔 "그냥 요구사항을 10초로 완화할까"도 생각해봤는데, 발표 때 "왜 5초에서 10초로 늘렸나?"라는 질문이 뻔히 보였고, 무엇보다 사용자 경험이 어색해졌다. 다른 방법이 필요했다.

---

## 세 가지 옵션

**옵션 A: 마이크 녹음 시간 단축 (5초 → 2초)**

전체 시간을 줄일 수 있었는데, STT 텍스트가 너무 짧아지는 게 문제였다. "택배요" 정도만 잡혀서 A-3의 가치가 떨어졌다.

**옵션 B: 2단계 알림 구조**

1차 알림은 5초 이내에 "현관에서 초인종 감지"만 발송하고, 2차 알림은 처리가 끝나면 사진 + STT 자막을 추가로 보내는 구조였다.

**옵션 C: 요구사항 완화 (5초 → 10초)**

단순하긴 한데, "왜 늘렸나?" 질문을 피할 수 없었다.

---

## 옵션 B를 골랐다

이유는 시연 임팩트와 사용자 경험 양쪽이 다 잡히는 구조라서였다.

첫째, **시연 임팩트**가 달라졌다. "띵동! 알림 옴 → 5초 후 카톡 → 잠시 후 누가 왔는지 사진+자막 또 옴"이라는 흐름이라서, 두 번의 와우 모먼트가 생겼다.

둘째, **4/29 피드백 1순위와 정합**이 됐다. 다른 시스템은 1차 알림에서 끝나는데, 본 시스템은 2차 알림으로 차별화되는 구조였다.

셋째, **5초 목표를 유지**할 수 있었다. 요구사항을 수정하지 않아도 됐다.

넷째, **실제 사용 시나리오에도 자연스러웠다.** 빨리 "누가 왔다"는 걸 알고, 좀 있다가 자세한 정보를 보는 흐름이 어색하지 않았다.

단점인 "메시지가 2번 온다"는 점은 같은 스레드 내 이어지는 메시지로 디자인하면 해결됐다. 1차는 "🔔 초인종 감지", 2차는 "📸 방문자: [사진] / 💬 '택배입니다'" 같은 식으로.

---

## 2차 알림 시간을 15초로 잠정 확정한 이유

처음엔 8~10초로 타이트하게 가자는 생각도 있었는데, PoC 실측 데이터 없이 너무 일찍 수치를 잡으면 나중에 뒤집어야 하는 상황이 생길 수 있었다. 일단 15초로 두고 PoC 후 단축 여부를 검토하기로 했다.

PoC에서 측정해야 할 항목들은 이렇다.

- ESP32-S3 카메라 + 마이크 동시 녹음 완료 시간
- multipart 업로드 시간 (Wi-Fi 환경)
- STT API 왕복 시간 (Google STT vs Whisper 비교)
- 카카오톡 API 응답 시간

---

## PIR + ToF 두 센서를 VL53L5CX 하나로 통합

기존 설계는 PIR(사람 감지) + VL53L0X(거리 측정)를 따로 썼는데, 카메라가 추가되면서 메인 보드를 ESP32-S3로 바꿔야 했고, 그 김에 센서 구성도 정리했다.

**VL53L5CX 멀티존 ToF** 하나로 통합했는데, 8×8 그리드(64 zone)로 깊이 정보를 한 번에 측정할 수 있어서 사람 형체 + 거리를 동시에 판단할 수 있었다. 시야각 65°에 I2C 단일 인터페이스라 핀 수도 절약됐다.

부품 1개로 두 가지 역할을 하는 게 장점인데, 가격이 5만원으로 비싸고 멀티존 처리 알고리즘을 직접 짜야 한다는 단점이 있었다.

## 새 시스템 흐름도

```
┌──────────────────────────────────────────────────┐
│ ESP32-S3 (XIAO Sense)                            │
│                                                  │
│ [1] 마이크 상시 모니터링 (INMP441, I2S1)              │
│      ↓ 임계값 초과                                  │
│ [2] VL53L5CX 사람 검증 (8x8 그리드, ~0.5초)           │
│      └─ 사람 없음 → 무시 (오탐 차단)                   │
│      └─ 사람 있음 → 다음 단계                         │
│                                                  │
│ [3] 1차 트리거: 짧은 오디오 (2초) 추출                  │
│      ↓ HTTPS POST /api/detect (WAV ~50KB)        │
│                                                  │
│ [4] 백그라운드 동시 진행:                             │
│      ├─ 카메라 캡처 (OV2640, JPEG ~200KB)           │
│      └─ 추가 마이크 녹음 (3~5초, WAV ~300KB)         │
│      ↓ HTTPS POST /api/enrich (multipart ~500KB) │
│        + event_id (1차 응답으로 받은 값)              │
└──────────────────────────────────────────────────┘
        ↓ (1차)                    ↓ (2차)
┌──────────────────────────────────────────────────┐
│ Nginx → Gunicorn → Flask                         │
│                                                  │
│ ◆ 1차 처리 (≤5초 목표)                              │
│   POST /api/detect                               │
│   ├─ raw waveform → YAMNet 추론                   │
│   ├─ 신뢰도 ≥70% & 클래스 확인                       │
│   ├─ (초인종이면) SP/DTW 2차 필터                     │
│   ├─ event_id 발급 + SQLite 1차 로그                │
│   ├─ 카카오톡 1차 발송 ("🔔 초인종 감지")               │
│   └─ Response: { event_id, class, confidence }   │
│                                                  │
│ ◆ 2차 처리 (≤15초 목표, PoC 후 재조정)                 │
│   POST /api/enrich                               │
│   ├─ 이미지 EC2 로컬 디스크 저장                       │
│   ├─ STT API 호출 (Google STT)                    │
│   │   └─ 실패 시 5초 후 1회 재시도                    │
│   ├─ 카카오톡 2차 발송 (사진 + 자막)                   │
│   └─ SQLite 2차 로그 업데이트                        │
└──────────────────────────────────────────────────┘
```

## 주요 설계 결정 4가지

| 항목 | 결정 | 이유 |
|------|------|------|
| VL53L5CX 검증 위치 | ESP32에서 사전 검증 | 오탐 트래픽 차단, 카메라 프라이버시 방어 |
| 2차 처리 방식 | 단순 동기 처리 | 졸작 시연 환경엔 동시 트래픽 없음 |
| 이미지 저장 | EC2 로컬 디스크 | 단순, 추가 비용 없음. 30일 보존으로 EBS 8GB 충분 |
| 2차 알림 실패 처리 | best-effort + 1회 재시도 | "실패 알림" 또 보내면 노이즈 |

VL53L5CX 사전 검증이 단순 효율 최적화가 아니라는 게 중요했는데, "카메라가 24시간 작동하는 게 아니라 사람이 감지될 때만 활성화된다"는 뜻이라서 프라이버시 방어 논거로도 쓸 수 있었다.

2차 처리를 단순 동기로 구현한 것도 명확한 이유가 있었다. 졸작 시연 환경에서 동시 트래픽이 없어서 Gunicorn 워커 2개로 충분했고, 다수 사용자 지원이 필요해지면 Celery 도입을 향후 개선 항목으로 문서화하는 방향이었다.
