### Zero-shot

- 모델에게 질문을 던질 때 프롬포트에 아무 예시 없이 바로 질문만 던지는 것을 의미함  
  ex.. "이 강아지 품종이 뭐야?" (그냥 바로 물어봄)

### Few-shot

- 모델에게 질문을 던질 때 프롬포트에 예시 몇 개를 던져주고 질문을 던지는 것을 의미함  
  ex.. "이건 푸들이고, 이건 골든리트리버야. 그럼 이 강아지는 뭐야?" (예시 보여주고 물어봄)

#### 두 가지 방식을 비교해보자면)

Few-shot은 예시를 내가 만들어야 한다. -> 이 말은 해당 예시에 내 생각이 들어간다는 것이고 Gemma가 내 생각을 따라할 수도 있다는 것이다.  
Zero-shot은 모델 혼자서 얼마나 잘하는지를 보는 거싱기 때문에 진짜 실력을 측정할 수 있다.

#### Zero-shot 방식으로 우리 연구 실습을 진행하고 방향은 두 가지가 있다.

1. 텍스트만 전달
2. 텍스트 + 심박 정보(추가 컨텍스트) 전달 -> 입력 정보가 많아짐

**"네 좋아요"**라는 텍스트만 준다면 해당 텍스트가 표면적으로는 POSITIVE한 반응을 띄지만 여기서 **화자 심박수: 92 bpm (평소보다 높음)**라는 힌트를 같이 주면 모델이 텍스트와 심박수를 같이 보며 판정한다.

> 그래서 두 가지 방식을 둘 다 돌려서 결과를 비교하면 "심박 정보가 얼마나 도움이 되는가?"라는 효과의 크기를 수치로 정량적인 결과 파악이 가능해질 것이라고 생각한다.

### [ 모델 출력 형식 ]

#### 1. 모델 출력 형식을 자유 텍스트로 받는 상황

```
프롬프트: "이 발화 분석해줘: 네 좋아요"

Gemma 답변:
"음, 이 발화는 표면적으로는 긍정적으로 보이지만
맥락에 따라서는 마지못해 동의하는 느낌일 수도 있고,
경우에 따라서는 진심일 수도 있겠네요. 화자의 상황을..."
```

위와 같이 답변이 오면 결과를 표로 정리하지 못 함 -> 가독성이 안 좋아지며 매번 다른 형식으로 말할 것이다.

#### 2. 모델 출력 형식을 JSON으로 받는 상황

```
프롬프트: "다음 발화를 분석하고 JSON으로만 답해줘.
형식: {"intent": "...", "confidence": 0~1, "evidence": "..."}

발화: 네 좋아요"

Gemma 답변:
{
  "intent": "FORCED_AGREEMENT",
  "confidence": 0.7,
  "evidence": "짧은 동의 표현으로 진심 부족 가능성"
}
```

위와 같이 답변이 와서 깔끔하게 표로 정리할 수 있어 결과 비교에 용이하다.

그래서 나는 본 실험 전에 JSON 출력 받을 때 받을 3가지 필드를 정의하였다.

| 필드 | 뜻 | 예시 값 |
| --- | --- | --- |
| `intent` | 발화의 진짜 의도 | `SINCERE`, `SARCASTIC`, `FORCED_AGREEMENT`, `UNCERTAIN` |
| `confidence` | 판단 확신도 (0~1) | `0.7` |
| `evidence` | 그렇게 판단한 근거 | `"짧은 동의 표현으로 진심 부족 가능성"` |

#### 각 필드의 역할

- **intent**: KoBERT의 surface sentiment(POSITIVE/NEGATIVE)와 직접 비교하기 위한 분류 결과. "강요된 동의", "비꼬기" 같은 화행 라벨이 여기 들어간다.
- **confidence**: Gemma가 얼마나 확신하는지. 낮으면 모델도 헷갈리는 케이스라는 뜻이다.
- **evidence**: 가장 중요한 필드. Gemma가 어떤 근거로 판단했는지를 봐야 "텍스트 단서로 판단한 것"인지 "그냥 추측한 것"인지 구분할 수 있다. 멀티모달 필요성 가설 검증의 핵심이다.

### 1. 환경 준비 + Gemma 4 모델 로드

```python
import os
import torch
from transformers import AutoTokenizer, AutoModelForCausalLM, BitsAndBytesConfig

hf_token = os.environ.get("HF_TOKEN")
assert hf_token and hf_token.startswith("hf_"), "HF_TOKEN 환경 변수 확인 필요"
print(f"HF_TOKEN OK (길이: {len(hf_token)})")

MODEL_ID = "google/gemma-4-E4B-it"

bnb_config = BitsAndBytesConfig(
    load_in_4bit=True,
    bnb_4bit_quant_type="nf4",
    bnb_4bit_compute_dtype=torch.bfloat16,
)

tokenizer = AutoTokenizer.from_pretrained(MODEL_ID)
print("토크나이저 로드 완료")

model = AutoModelForCausalLM.from_pretrained(
    MODEL_ID,
    quantization_config=bnb_config,
    device_map="auto",
)
print("모델 로드 완료")
print(f"GPU 점유: {torch.cuda.memory_allocated() / 1e9:.2f} GB")
```

위 코드를 통해서 Gemma4 모델을 로드한다.  
이 과정에서 NF4 양자화 설정 단계를 보면 저장은 4bit, 계산은 BF16으로 한 것을 보아 계산 정확도는 유지하며 메모리는 줄이는 방식을 택한 것을 알 수 있다.

또한 모델 다운로드 단계에서 *device_map="auto"* 코드를 보면

- auto: 다운받은 해당 모델을 cpu에 올릴지 gpu에 올릴지 알아서 정해줌
- cuda: 다운받은 해당 모델을 무조건 gpu에 올림
- cpu: 다운받은 해당 모델을 무조건 cpu에 올림

3가지 방식으로 정할 수 있고 결과는 **print(next(model.parameters()).device)** 출력 결과로 확인할 수 있다.

# 실험 대상 발화 3건

    {
        "id": "suspect_2",
        "speaker": "이연재",
        "utterance": "아 정말요, 너무 좋네요.",
        "heart_rate": 102,
        "kobert_label": "POSITIVE",
        "kobert_score": 0.970,
        "expected_intent": "SARCASTIC",          # 우리 가설: 비꼬기
        "category": "suspect",
    },
    {
        "id": "control_1",
        "speaker": "서수화",
        "utterance": "괜찮아요, 충분히 가능합니다.",

여기서 중요한 필드의 역할을 정리해보자면,

- 즉, Gemma의 답을 채점하기 위한 정답 라벨을 의미
- 비교 실험의 기준

#### category의 역할
