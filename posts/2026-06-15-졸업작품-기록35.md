**mock 대시보드를 실제 Flask API에 갈아끼우기 — Phase 2-2차 React 연동 (PR #3)**

전편(Phase 2-1차)에서 Flask 백엔드 골격을 만들어 PR #2로 머지했고, 그 사이 Phase 1에서 만들어둔 React 대시보드는 mock JSON으로 돌아가고 있었다. 이제 이 둘을 잇는 차례 — 렌더 / 타입 / 폴링 훅은 그대로 두고 데이터 출처만 갈아끼우는 게 본 작업의 핵심이었다. PR #3(cec9c9b)로 머지.

실제 ML 추론 / HTTPS / EC2 배포는 여전히 11주차에 미뤘다. 본 작업은 로컬에서 연결에 집중 했다.

## "데이터 출처만" 갈아끼우는 전략

Phase 1에서 만들어 둔 자산이 꽤 됐다 — 컴포넌트 17개 / 페이지 5종 / 디자인 토큰 / usePolling 훅 / 타입 정의들. 이걸 다 mock 기준으로 검증한 상태였고, 데이터 출처만 mock에서 실제 fetch로 바뀐다고 해서 렌더 레이어가 흔들릴 이유는 없었다.

그래서 변경 범위를 최소화하는 쪽으로 잡았다.

- `dashboard/src/lib/api.ts` 의 fetchNotifications / fetchStats 함수 signature는 유지, 내부 구현만 mock → 실제 fetch로 교체
- 이 함수를 쓰는 훅이나 컴포넌트는 한 줄도 안 건드림
- 새 라이브러리(axios, TanStack Query 등) 도입 X — fetch + useEffect 패턴 그대로

이렇게 잡으니까 본 PR의 영향 반경이 좁아졌다. PR 리뷰할 때도 "데이터 출처 교체"만 보면 됐고, 만약 UI에서 버그가 나면 그건 데이터 출처 교체 외 다른 원인이라고 가정할 수 있는 격리가 생겼다.

## apiGet 공용 헬퍼 — 한 번만 짜고 끝

fetchNotifications / fetchStats 둘 다 GET이라 거의 같은 코드가 두 번 들어가야 했다 — Bearer 헤더 붙이기 / 상태 코드 검증 / JSON 파싱 / 에러 메시지 통일. 이걸 매번 반복하면 한쪽 고치고 한쪽 안 고치는 사고가 시간 문제였다.

그래서 apiGet 공용 헬퍼 하나로 묶었다.

```ts
// dashboard/src/lib/api.ts (구조)
const API_BASE = import.meta.env.VITE_API_BASE_URL || "/api/v1";
const TOKEN = import.meta.env.VITE_DASHBOARD_TOKEN || "";

async function apiGet<T>(path: string): Promise<T> {
  const base = API_BASE.endsWith("/") ? API_BASE.slice(0, -1) : API_BASE;
  const res = await fetch(`${base}${path}`, {
    headers: { Authorization: `Bearer ${TOKEN}` },
  });
  if (!res.ok) {
    throw new Error(`API ${res.status}: ${path}`);
  }
  return res.json();
}

export const fetchNotifications = (cursor?: string) =>
  apiGet<NotificationsApiResponse>(`/notifications${cursor ? `?cursor=${cursor}` : ""}`);

export const fetchStats = () =>
  apiGet<StatsApiResponse>(`/stats?period=today`);
```

base URL 끝슬래시 방어 같은 디테일은 처음에 한 번 잡아두면 끝나는 거라 헬퍼 안에 박았다. 토큰은 `.env.local`에서 VITE_DASHBOARD_TOKEN으로 읽어와서 코드에 직접 박지 않았다 — 실수로 commit해도 토큰 자체는 안 새는 구조.

## CORS — 백엔드 안 건드리고 Vite dev proxy로 우회

연결 작업하면서 가장 먼저 만난 벽이 CORS였다.

React가 localhost:5173(Vite dev), Flask가 localhost:5000. 둘이 origin이 달라서 브라우저가 fetch를 막아버렸다. 백엔드에 flask-cors를 깔고 origin allow 설정해주는 게 일반적인 해법인데, 두 가지가 걸렸다.

- Phase 2-1차에서 막 만들어 둔 백엔드 구조를 본 PR에서 또 건드리는 건 변경 범위가 번지는 거였다
- 11주차에 EC2로 배포할 때는 Nginx 동일 origin 구조가 될 가능성이 높아서, CORS 라이브러리 자체가 운영 환경에서는 안 쓰일 수도 있었다

그래서 Vite dev proxy로 우회 하는 쪽으로 갔다. 클라이언트가 상대 경로(/api/v1/...)로 호출하게 두고, Vite가 그걸 가로채서 localhost:5000으로 토스해주는 방식.

```ts
// dashboard/vite.config.ts (구조)
export default defineConfig({
  server: {
    proxy: {
      "/api": {
        target: "http://localhost:5000",
        changeOrigin: true,
      },
    },
  },
});
```

```bash
# dashboard/.env.example
VITE_API_BASE_URL=/api/v1        # 상대 경로
VITE_DASHBOARD_TOKEN=            # 비워둠, 로컬은 .env.local
```

이렇게 잡으니까 브라우저 입장에서는 모든 요청이 same-origin 으로 보였다. CORS 자체가 발생하지 않으니 preflight OPTIONS 요청도 안 날아갔다. 백엔드 코드는 한 줄도 안 바뀌었다.

> ⚠️ 솔직한 한계: dev proxy는 vite dev 전용이다. 11주차에 프로덕션 빌드를 정적 호스팅하기 시작하면 Nginx 동일 origin으로 가거나, 그게 아니면 백엔드에 CORS 설정을 별도로 깔아야 한다. decisions.md 카테고리 6에 미결로 남겨뒀다.

## 응답 타입 — 백엔드와 1:1, cursor는 additive

전편에서 백엔드를 만들 때 next_cursor / has_more 같은 cursor pagination 메타를 미리 내려놓는 구조로 잡아 두긴 했다. 그런데 그때 시점의 프론트 `dashboard/src/types/api.ts` 의 NotificationsApiResponse 타입에는 cursor 필드가 없었다 — Phase 1에서 mock 데이터에 pagination이 없어서 안 들어가 있던 상태.

이번 PR에서 그 부분을 정리했다.

```ts
// dashboard/src/types/api.ts (구조)
export interface NotificationsApiResponse {
  notifications: Notification[];
  next_cursor?: string | null;   // additive
  has_more?: boolean;            // additive
}
```

기존 notifications 키는 그대로 유지하고 cursor 메타만 옵셔널로 추가했다. 추가하는 시점에서 기존 코드를 깨지 않게 하는 게 목표였다 — 현재 UI는 아직 cursor를 쓰지 않으니까 옵셔널로 두면 안 받아도 타입 체크가 통과했다. 나중에 페이지가 늘어나서 cursor가 필요해지면 그때 옵션을 풀어쓰면 됐다.

응답 shape은 추측으로 깎지 않고 실제 curl로 확인한 결과 를 기준으로 잡았다. 백엔드가 진짜로 뭘 돌려주는지 보고 타입을 맞추는 게 맞았다.

## REST 폴링 — 기존 훅 그대로

usePolling 훅은 Phase 1에서 이미 검증된 컨벤션이라 새로 안 갈아엎었다. mock fetch를 실제 fetch로 받기만 하면 되는 구조였고, 폴링 간격(3초)은 상수로 빼서 한 군데서 바꾸면 다 바뀌도록 정리. unmount cleanup도 기존 훅이 이미 잡고 있어서 추가 작업 없었다.

여기서 새 상태 관리 라이브러리(SWR, TanStack Query 같은)를 도입하지 않은 게 의도적이었다. 기존에 잘 도는 코드가 있는데 라이브러리를 추가하면 학습 비용 + 변경 범위가 더 늘어났을 거고, REST 폴링은 본 프로젝트 규모에서 충분한 패턴이었다.

## 미니 E2E로 끝단 확인

Playwright로 끝단 시나리오를 한 번 통과시켰다. Flask와 Vite dev 둘 다 띄워두고 다음을 확인했다.

| 항목 | 결과 |
| --- | --- |
| seed 알림 11건 카드 렌더 | 통과 (초인종/노크/화재경보 한글 라벨 + ToF 표시 + STT 표시) |
| Network 탭 Authorization Bearer 헤더 | 통과 (Bearer ...) |
| Network 탭 CORS 에러 | 0건 |
| 요청 origin | localhost:5173(proxy 경유 확인) |
| 콘솔 에러 | 0건 |
| tsc / eslint / build | 전부 통과 |

여기서 한 번 헤맨 게 있었다. seed 데이터를 어제 날짜로 넣어뒀더니 stats?period=today 응답이 0으로 나왔고, 잠깐 "stats 엔드포인트가 고장난 줄" 알았다. 백엔드 코드 까보고 나서야 "당연한 거였다" — period=today는 오늘 데이터만 집계하는 게 정의였고, seed가 어제면 0이 맞았다.

오늘 날짜로 /detect 한 건 주입하고 3초 기다리니까 폴링이 신규 카드를 잡아왔고, stats도 0 → 1로 살아남. 폴링이 진짜로 도는 게 시각적으로 확인됐다.

## 5000 포트 점거 삽질

처음에 Flask를 띄웠는데 "주소 이미 사용 중" 에러가 떴다. lsof -i :5000 으로 잡으니 두 가지가 물고 있었다.

- macOS의 AirPlay 수신 (시스템 설정에서 끔)
- 이전에 죽었다고 생각했던 Flask 좀비 프로세스 (kill -9)

이걸 정리하고 나서야 Flask가 정상으로 떴다. macOS는 기본적으로 5000 / 7000 같은 포트를 AirPlay가 차지하니까, dev 서버 포트를 잡을 때 한 번은 부딪치는 함정이었다.

## 정리하면

mock → 실제 데이터 출처 교체를 작은 PR 하나로 끝낸 게 의도한 결과였다. Phase 2-1차에서 백엔드를 curl 15종으로 다 검증해둔 상태였기 때문에 본 PR에서 디버깅할 때 "이게 백엔드 문제냐 프론트 문제냐"를 거의 고민하지 않아도 됐다. 백엔드는 답이 정해진 상태였고, 의심해야 할 건 프론트 쪽 fetch / proxy / 타입뿐이었다.

CORS를 백엔드 코드를 안 건드리고 dev proxy 한 줄로 우회한 판단도 마음에 들었다. CORS 라이브러리를 깔면 그게 운영 환경에서도 그대로 끌려가는 부담이 생기는데, dev proxy는 dev 환경에서만 살고 운영 환경(11주차 Nginx 동일 origin)에서는 자동으로 비활성화되니까 책임 범위가 깔끔하게 분리됐다.

GitHub Flow도 두 번째 Squash PR 사이클이라 첫 번째(PR #2)보다 훨씬 자연스럽게 돌았다. feat 브랜치 → 작업 → push → PR → 리뷰 → Squash 머지 → 브랜치 삭제 흐름이 손에 익었다.
