## 단독 테스트 5건으로 통합 메모리 예측하기 — ESP32-S3 정적 budget 추정

5/15부터 부품이 들어오기 시작하는데, 그 전에 답해야 할 질문이 하나 있었다. 4종 페리페럴(WiFi/카메라/마이크/ToF)을 다 합쳤을 때 ESP32-S3의 320KB SRAM 안에 들어오긴 하냐는 거였고, 들어오지 못한다면 5/18 PoC 1주차 시작 전에 미리 손을 쓸 수 있어야 했다.

문제는 부품이 없으니까 실측이 불가능했다는 거였는데, 그래도 5/7부터 5/11까지 누적된 단독 테스트 5건의 RAM/Flash 수치는 있었다. 그래서 정적 분석만으로 통합 budget을 미리 추정해보기로 했다.

---

## delta sum 방식 — 단순 합산이 안 되는 이유

처음에 단순하게 생각하면 각 페리페럴 컴파일 결과를 그냥 더하면 될 것 같았다. 근데 이게 함정이었던 게, 각 env마다 베이스라인(아무 페리페럴도 안 붙인 monorepo 셋업)이 다 포함돼 있어서 4종을 단순 합산하면 베이스라인이 4중으로 카운트됐다.

그래서 delta sum 방식을 채택했다. 베이스라인 하나를 깔고, 각 페리페럴이 추가될 때마다 늘어난 만큼(delta)만 누적하는 방식이었다.

| 일자 | env | RAM | Flash | RAM delta | Flash delta |
| --- | --- | --- | --- | --- | --- |
| 5/7 | (baseline) | 5.6% | 7.6% | — | — |
| 5/8 | poc (WiFi+HTTPS) | 13.8% | 25.8% | +8.2pp | +18.2pp |
| 5/9 | camera_v2 | 7.0% | 9.4% | +1.4pp | +1.8pp |
| 5/10 | mic_dummy | 8.1% | 8.1% | +2.5pp | +0.5pp |
| 5/11 | tof_dummy | 6.1% | 11.1% | +0.5pp | +3.5pp |

이 방식으로 계산해보니까,

- **RAM** = 5.6 + 8.2 + 1.4 + 2.5 + 0.5 = **18.2%** (약 59,640 bytes / 320 KiB)
- **Flash** = 7.6 + 18.2 + 1.8 + 0.5 + 3.5 = **31.6%** (약 1,056,178 bytes / 3.34 MB)

이렇게 나왔는데, 만약 단순 합산을 했으면 RAM 35.0% / Flash 54.4%로 나와서 베이스라인 4중 중복 때문에 한참 과대평가 됐을 거였다. 한 17%p 정도 차이가 났고, 이게 Plan B 발동 여부를 바꿀 수 있는 수치라서 방법론을 정확히 잡고 가는 게 중요했다.

## 페리페럴별로 뭐가 얼마나 먹는가

delta가 나왔으니까 각 페리페럴이 정확히 어디서 자원을 쓰는지 정리했다.

| 페리페럴 | RAM delta | Flash delta | 근거 |
| --- | --- | --- | --- |
| WiFi/HTTPS | +8.2pp (~26.9 KB) | +18.2pp (~608 KB) | esp_wifi.a + lwIP + wpa_supplicant + mbedtls + WiFiClientSecure + HTTPClient + ArduinoJson |
| 카메라 OV2640 | +1.4pp (~4.6 KB) | +1.8pp (~60 KB) | esp_camera v2.1.2 driver + 센서 테이블. frame buffer는 PSRAM 점유 |
| 마이크 INMP441 | +2.5pp (~8.2 KB) | +0.5pp (~17 KB) | legacy driver/i2s.h + 8 KiB BSS (DMA 32-bit × 1024 frames × 2 buffer) |
| ToF VL53L5CX | +0.5pp (~1.6 KB) | +3.5pp (~117 KB) | SparkFun lib 1.0.3 + Wire. Flash 117KB ⊃ FW upload buffer ~84KB |

압도적으로 WiFi가 무거웠다. RAM의 8.2pp, Flash의 18.2pp가 다 WiFi 한 놈한테서 나왔는데, 이게 esp_wifi 스택 자체에 lwIP + wpa_supplicant + mbedtls까지 다 따라붙어서 그랬다. arduino-esp32 v3.20017 issue #5990에서 WIFI_STA 모드만 켜도 heap이 45KB 정도 빠진다는 보고가 있었고, issue #9741에서는 WiFi.h만 include해도 Flash가 500KB 가까이 늘어난다는 측정치가 있었는데, 본 프로젝트는 거기에 HTTPClient + WiFiClientSecure + ArduinoJson까지 얹어서 608KB까지 갔다.

반면 ToF는 Flash 117KB 중에 84KB가 FW upload buffer였다. VL53L5CX는 RAM-based sensor라서 매 power-on마다 펌웨어를 I2C로 sensor에 올려줘야 하는 구조였고(VL53L5CX UM2884), 그 펌웨어 이미지가 ESP32 Flash에 박혀 있어야 했다. 이건 줄일 수가 없는 고정 비용이라 그냥 받아들이는 게 맞았다.

## PSRAM은 카메라 frame buffer만

PSRAM 점유는 카메라 하나만 신경 쓰면 됐다. QVGA JPEG에 fb_count=2, jpeg_quality=12 설정으로 약 50KB 정도 점유하는데, 8MB PSRAM 한계 대비 0.6%라서 사실상 무제한이라고 봐도 됐다. WiFi, Mic, ToF는 PSRAM을 안 쓰니까 카메라가 frame buffer를 PSRAM에 다 떨궈도 됐고, 이게 메인 SRAM 압박을 줄이는 핵심 트릭이기도 했다.

## Plan B 트리거를 정량화하기

수치가 나왔으니 "어디서부터 위험한가"를 정량으로 정해야 했다. 처음엔 일반론으로 30/50/70% 같은 임계값을 쓰려고 했는데, 이게 ESP32-S3 사정에 맞는 숫자가 아니었다. user-available SRAM 320KB라는 한계, 동적 heap peak가 typical 30~50% 정도 추가로 들어온다는 점, WiFi TLS handshake 시점에 동적으로 80KB 정도 더 먹는다는 점을 다 반영해서 재산정했다.

| Stage | 트리거 조건 | 대응 |
| --- | --- | --- |
| Stage 1 (알람) | 정적 SRAM ≥25% OR Flash ≥40% | 알람만, `ESP.getMinFreeHeap()` 동적 측정 권장 |
| Stage 2 (최적화) | 정적 SRAM ≥35% OR Flash ≥60% | DMA buffer 축소 / VL53L5CX FW를 PSRAM 이전 / WiFi sdkconfig minimal |
| Stage 3 (Plan B) | 정적 SRAM ≥50% OR Flash ≥75% | 카메라 QVGA→CIF / ToF 8x8→4x4 / WiFi→ESP-NOW 대체 |

현재 정적 18.2% / 31.6%인데, Stage 1 임계값(25% / 40%)에도 못 미쳤다. 모든 Stage 미발동이라는 뜻이었고, 메모리 측면에서 PoC 1주차 진입은 안전권이라는 정량 근거가 확보됐다.

## 5/8 사전 추정 vs 5/12 실측 정정

이 작업 시작하기 며칠 전인 5/8에도 같은 질문을 한 번 추정해본 적이 있었다. 그때는 단독 테스트가 다 끝나기 전이라서 mic delta를 +5% 가정, tof delta를 +3% 가정, tof FW image를 +6%(~200KB) 가정해서 SRAM 22% / Flash 42%로 예측했었다.

| 자원 | 사전 추정 (5/8) | 실측 갱신 (5/12) | 차이 | 정정 사유 |
| --- | --- | --- | --- | --- |
| SRAM | 22% | 18.2% | -3.8pp | mic 사전 +5% → 실측 +2.5pp / tof 사전 +3% → 실측 +0.5pp |
| Flash | 42% | 31.6% | -10.4pp | tof FW image 사전 +6%(~200KB) → 실측 +3.5pp(~117KB) |
| PSRAM | 50 KB | 50 KB | 0 | 카메라 frame buffer만 PSRAM 점유, 일치 |

실측이 사전 추정보다 SRAM은 3.8pp, Flash는 10.4pp 작게 나왔는데, 보수적으로 추정해놓고 실제로는 더 작게 나온 패턴이라 안전 마진이 충분히 확보됐다는 결론이었다. tof FW image 가정이 실제보다 100KB 가까이 컸던 게 컸고, 이게 ToF lib 내부 구조를 직접 까보지 않고 일반론 기반으로 잡았던 한계였다.

## 보고 요약만 보고 판단하면 안 되는 이유

여기서부터가 사실 이번 작업에서 제일 인상적이었던 부분이었다.

본 프로젝트는 GitHub repo의 `decisions.md`가 최상위 SSoT고, 의사결정 채팅방 → 위임 프롬프트 생성기 → Claude Code MCP 작업 → GitHub commit으로 작업 체인이 흐르는 구조였다. 매번 결과는 보고 요약으로 올라오는데, 이게 편하긴 한데 위험한 게 있었다.

Claude Code MCP가 메모리 self-checkpoint 작업을 끝내고 commit `5c34400`을 push한 후, 의사결정 채팅방에서 "decisions.md에 추가 갱신이 필요한지" 1차 판정했다. 그때 1차 판정 결론은 "옵션 A — 추가 갱신 없음"이었다. 보고 요약만 봤을 때는 카테고리 17.1.1에 결과가 다 들어갔고, decisions-log entry도 추가됐고, 별 문제 없어 보였다.

근데 학부생인 내가 "진짜 갱신이 필요없는지 객관적으로 검증해봐"라고 push back을 했고, 그래서 2차 객관 검증을 들어갔다. 보고 요약이 아니라 `decisions.md` 실제 파일을 처음부터 catch하는 방식이었는데, 결과가 이랬다.

- **critical 1건**: 카테고리 16.1 line 248-251에 "5/12 메모리 self-checkpoint 입력 데이터" 부연이 있었고, 거기에 5/8 사전 추정값(SRAM 22% / Flash 42%)이 그대로 박혀 있었다. 카테고리 17.1.1에는 5/12 실측값(18.2% / 31.6%)이 추가됐는데 카테고리 16.1은 변경 안 됐고, 결과적으로 같은 문서 안에서 값 충돌이 발생한 상태였다.
- **moderate 2건**: 카테고리 15(5/12 재검토 카테고리 헤더)와 카테고리 17.1.3(5/21 통합 시점 영향) 본문에 5/12 결과 cross-reference가 빠져 있었다.
- **minor 2건**: 카테고리 11 / 12의 일정 표기는 시간순 보존 원칙에 따라 유지하기로 했다.

critical 1건과 moderate 2건을 후속 commit `6fa17c9`로 보강했고(7 insertions / 2 deletions / 2 files), 이게 사전 준비 11일 동안 "보고 요약 vs 실제 SSoT 갭"이 catch된 5번째 사례였다.

5/10 mic 작업, 5/11 ToF 작업에서도 같은 패턴이 한 번씩 있었는데, 매번 보고 요약 단계에서는 "별 문제 없음"으로 보였다가 실제 파일을 까보면 cross-reference 충돌이나 컨벤션 불일치가 있었다. 결국 의사결정 채팅방이 결과 검증할 때 GitHub repo 실제 파일을 직접 catch하지 않으면 정보 손실이 발생한다는 게 5/12에 정량적으로 증명된 셈이었다.

## 다음 단계

메모리 측면에서는 정량 근거가 확보됐고, Plan B 트리거도 모두 미발동이라 코어 분배 잠정안(카테고리 14)을 유지한 채로 5/18 PoC 1주차 진입이 가능해졌다. 5/15부터 부품이 들어오고 결선 + 1차 부팅을 거치고 나면, 다음 self-checkpoint는 타이밍 쪽이었는데 이건 부품 실측이 가능해진 다음에 진행하기로 했다.

부품 도착 전에 답할 수 있는 질문은 미리 답해두고, 부품 도착 후에만 답할 수 있는 질문은 그때 답하는 식으로 self-checkpoint를 쪼개 둔 게 이번에 잘 작동했다. 메모리는 정적 분석이 가능했고 타이밍은 실측이 필요했다는 게 자연스럽게 분리 기준이 됐다.
