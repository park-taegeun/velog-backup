## ESP32-S3 첫 부팅에서 잡은 잠복버그 2건 — env:poc 회귀 + PID 비교 수정 (PR #4)

전편에서 첫 실물 부팅을 통과시키면서 잠복버그 2건을 발견했다. 부팅 당일은 "검증 전용, 코드 0 수정" 원칙으로 진단만 해두고 별도 작업으로 미뤄뒀는데, 이번에 그 두 건을 PR #4(c4c8f47)로 묶어서 수정했다.

버그 성격이 달랐다 — 하나는 빌드 설정 문제(build_src_filter 회귀), 하나는 코드 로직 문제(PID 비교 잘림). 근데 둘 다 "5월에 통과시켜놓고 실물에서 처음 걸렸다"는 공통점이 있었다.

## 버그 ① env:poc build_src_filter 회귀

### 증상

첫 부팅 때 env:poc 빌드를 돌리니 링커 에러가 떴다.

```
multiple definition of `setup()'
multiple definition of `loop()'
```

main.cpp / mic_test.cpp / tof_test.cpp 세 파일이 각자 setup() / loop()를 정의하고 있어서 충돌한 거였다.

### 원인

platformio.ini의 env:poc 빌드 필터를 보면 이렇게 돼 있었다.

```ini
; 5월 시점 env:poc (회귀 상태)
[env:poc]
build_src_filter = +<*> -<camera_test_v1.cpp> -<camera_common.cpp>
```

`+<*>`로 src/ 전체를 포함하고 불필요한 파일만 빼는 blacklist 방식이었다. 5/8에 처음 poc env를 만들 때는 src/에 main.cpp 딱 하나뿐이었으니까 아무 문제가 없었다. 그런데 5/10에 mic_test.cpp, 5/11에 tof_test.cpp가 추가됐고, 이 파일들이 각자 setup() / loop()를 갖고 있었다. poc env는 그 사이에 한 번도 재빌드가 없었으니까 한 달간 잠복하다 첫 실물 빌드에서 터진 거였다.

다른 env들은 이미 whitelist 방식이었다.

```ini
; camera_v1 / mic_dummy / tof_dummy (정상 상태)
[env:camera_v1]
build_src_filter = -<*> +<camera_test_v1.cpp> +<camera_common.cpp>

[env:mic_dummy]
build_src_filter = -<*> +<mic_test.cpp>

[env:tof_dummy]
build_src_filter = -<*> +<tof_test.cpp>
```

`-<*>`로 전체를 먼저 비우고 필요한 파일만 명시적으로 포함. src/에 파일이 추가돼도 이 env들은 자동으로 영향을 받지 않는 구조다.

### 수정

```ini
; PR #4 이후 env:poc (수정 상태)
[env:poc]
build_src_filter = -<*> +<main.cpp>
```

whitelist로 통일. 이렇게 바꾸고 나서 빌드 결과의 RAM/Flash footprint를 5/8 원본과 비교했다.

|  | 5/8 원본 poc | PR #4 수정 후 |
| --- | --- | --- |
| RAM | 13.8% | 13.8% |
| Flash | 25.8% | 25.8% |

수치가 정확히 일치했다. 5월에 검증해뒀던 원본 poc 상태로 복구된 게 수치로 증명됐다.

### 왜 blacklist는 위험한가

`+<*>` blacklist는 "지금 있는 파일 기준으로 동작"하는 방식이다. 파일이 하나씩 추가될 때마다 제외 목록에도 같이 추가해줘야 하는데, 이걸 놓치면 묵시적으로 새 파일이 빨려 들어온다. 프로젝트가 계속 파일을 추가하는 구조에서는 잠복 회귀의 씨앗이 된다.

`-<*>` whitelist는 반대다. 명시적으로 포함시키지 않으면 아무 파일도 안 들어온다. 나중에 src/에 파일이 몇 개가 추가되더라도 기존 env가 영향을 받지 않는다. 본 프로젝트처럼 모듈별 env를 격리해서 쓰는 구조에서는 whitelist가 유일하게 안전한 방식이었다. decisions.md 카테고리 27.6에 "모든 env는 `-<*>` 먼저"로 명문화했다.

## 버그 ② camera PID 비교 잘림

### 증상

camera_v1 부팅 시리얼을 보면 카메라 init은 정상이었는데 센서 이름 표기가 이상했다.

```
Camera init OK
Sensor: (UNKNOWN)
```

OV3660이 달려있는 게 실측으로 확인됐는데(PID 0x3660) 왜 UNKNOWN이 나오는지 확인했다.

### 원인

camera_common.cpp의 `sensorIdToName()` 함수를 보니까 이렇게 박혀 있었다.

```cpp
// camera_common.cpp (버그 상태)
case 0x36:
    return "OV3660";
```

OV3660의 실제 PID는 uint16_t `0x3660`인데 `0x36`으로 비교하고 있었다. `0x36 != 0x3660`이라 매칭이 실패해서 default(UNKNOWN)로 떨어지는 거였다.

이 버그의 영향이 이름 오표기 하나로 끝나지 않았다. 같은 파일 아래 dark-image 보정 분기가 있었는데(Khangura 함정 #6, decisions.md 카테고리 25), 거기도 같은 PID 비교가 쓰이고 있어서 보정이 아예 안 걸리고 있었다. 캡처 자체는 정상이었으니까 1차 부팅에선 무영향이었지만, 나중에 시연 영상 밝기 보정에 직결되는 버그였다.

### 수정

sensor.h에 `OV3660_PID`(값: 0x3660) 매크로가 이미 정의돼 있었다. 매직 넘버 대신 매크로로 교체하고, 0x36 비교 사이트를 전량 수정했다.

```cpp
// camera_common.cpp (PR #4 수정 후)
case OV3660_PID:          // 0x3660, sensor.h:22에서 정의
    return "OV3660";

// 보정 분기 (수정 후)
if (sensor.id.PID == OV3660_PID) {
    // dark-image 보정 (Khangura #6)
    sensor.set_brightness(&sensor, 1);
    sensor.set_saturation(&sensor, -2);
}
```

grep으로 0x36 비교 사이트를 전량 enumerate해서 2곳(L49 case / L79 보정 분기)을 확인하고 다 바꿨다. 수정 후 컴파일 결과 확인.

```
Camera init OK
Sensor: OV3660 (PID=0x3660)
```

UNKNOWN이 OV3660으로 바뀌고, 보정 분기도 정상 진입하는 게 시리얼로 확인됐다.

## PR #4 — 두 수정을 묶어서 Squash merge

두 버그 수정을 feat/firmware-fix-poc-boot 브랜치에서 작업하고 PR #4로 올렸다. 컴파일 검증은 두 env 모두.

| env | 결과 |
| --- | --- |
| poc | SUCCESS (multiple definition 해소) |
| camera_v1 | SUCCESS (캡처 로직 무손상, 보정 진입 확인) |

Squash merge로 c4c8f47 하나로 main에 들어왔다. 이번이 GitHub Flow 코드 PR 3번째 사이클(PR #1 대시보드 / PR #2 Flask / PR #3 React 연동 / PR #4 펌웨어)이었는데, 브랜치 생성 → 작업 → push → PR → 리뷰 → Squash 머지 → 브랜치 삭제 흐름이 이제 완전히 손에 익었다.

## 배운 것들

**"5/8 컴파일 SUCCESS"는 영원한 SUCCESS가 아니다.** env:poc 회귀가 정확히 이 케이스였다. 5월에 검증한 시점 이후에 환경(src/ 파일 추가)이 바뀌었고, 그 검증 기록은 더 이상 현재 상태를 보장하지 않았다. 정적 기록이 시간이 지나며 무효화되는 건 36편에서 얘기한 pio venv `/tmp` 소실이랑 같은 패턴이었다 — 환경이 바뀌면 기록이 거짓이 된다.

**검증과 수정을 분리한 게 맞았다.** 1차 부팅 때 "0 수정 검증"으로 진단만 해두고 이번에 별도 PR로 수정했는데, 이 덕에 "부팅 검증에서 뭔가 안 됐을 때 내가 건드린 게 원인인지 아닌지"를 고민 안 해도 됐다. 원인이 명확하게 격리된 상태에서 수정만 하면 됐다.

**PID 매직 넘버는 매크로로.** 0x36이 0x3660으로 잘린 게 그냥 타이포였는데, 처음부터 `OV3660_PID` 매크로를 쓰면 컴파일러가 타입 체크(uint16_t)를 해줘서 이런 버그가 컴파일 시점에 잡혔을 가능성이 있었다. 앞으로 센서 ID 비교는 매크로 전용.
