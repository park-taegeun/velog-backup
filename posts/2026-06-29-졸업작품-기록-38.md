# 대시보드를 "마무리"하려다 만난 것들 — 베테랑 리뷰, 접근성 3조각, 그리고 git 히스토리가 꼬인 사건

부품 도착을 기다리는 chunk가 또 생겨서, 이번엔 웹 대시보드 마무리에 손을 댔다. 대시보드는 기능적으로는 이미 다 됐었다 — Phase 1에서 React로 화면을 다 만들었고, Phase 2에서 실제 Flask API에 연결까지 끝낸 상태였다. 근데 "마무리"하려고 코드를 다시 들여다보니까, 정작 마무리해야 할 건 기능이 아니라 **코드 품질과 접근성** 이었다.

특히 접근성은 이 프로젝트에서 그냥 "있으면 좋은" 게 아니었다. 사용자가 청각장애인이라 시각 / 스크린리더 / 키보드 의존도가 높았고, 접근성이 곧 본질 가치였다. 그래서 이번 작업(PoC-(19))은 베테랑 리뷰로 코드 전체를 점검하고 → 접근성을 3개 PR로 강화하는 흐름으로 잡았다. 그리고 마지막에 git 히스토리가 꼬이는 사건이 하나 터지면서 새 운영 규칙(학습 18)이 생겼다.

## 베테랑 리뷰를 왜 먼저 분리했나 — 그리고 🔴 0건의 의미

코드를 바로 고치기 전에, **read-only 리뷰** 를 먼저 분리했다. Claude Code MCP에 "코드 0 수정, 정적 리뷰만" 원칙으로 위임해서 `dashboard/`(55개 소스) + `server/`(13개)를 전수로 훑었다.

결과는 이렇게 분류됐다.

| 심각도 | 건수 | 의미 |
| --- | --- | --- |
| 🔴 즉시 수정 | 0 | 당장 고쳐야 할 치명 문제 없음 |
| 🟡 개선 권장 | 4 | Phase B에서 처리 |
| 🟢 참고 | 6 | 인지만 |
| deferred | 6 | 11주차 배포 시점으로 |

여기서 가장 인상적이었던 건 **🔴가 0건으로 정직하게 나온 거** 였다. 리뷰라는 게 "뭐라도 찾아내야 일한 것 같은" 압박이 있어서, 없는 문제를 만들어내거나 사소한 걸 심각하게 부풀리기 쉬운데, 리뷰가 "없는 🔴를 만들지 않았다"는 판정을 내리고 "그대로 Phase B(접근성 강화) 진입해도 안전하다"고 선언했다.

이게 신뢰할 수 있는 코드 리뷰어의 조건이라고 생각했다. 리포트를 부풀려서 일한 티를 내는 게 아니라, 실제 상태를 정확히 보고하는 것. 🔴가 0건이라는 게 "리뷰를 대충 했다"가 아니라 "코드가 실제로 그 정도로 안정적이었다"는 뜻이었고, 이건 뒤에 strict 켰을 때 한 번 더 증명됐다.

## strict를 토대로 먼저 켠 이유

접근성 작업(B-1a, B-1b) 들어가기 전에 **TypeScript strict 활성화** 를 별도 PR(B-0, PR #5)로 먼저 분리했다.

```jsonc
// dashboard/tsconfig.app.json
{
  "compilerOptions": {
    "strict": true,    // additive
    // ...
  }
}
```

토대를 먼저 까는 게 맞다고 봤다. strict를 켜둔 상태에서 접근성 코드를 짜야 새 코드가 처음부터 엄격한 타입 체크를 통과하고, 나중에 한꺼번에 켜면 접근성 변경분이랑 strict 에러가 뒤섞여서 PR이 지저분해질 거였다.

그런데 strict를 켜고 빌드를 돌렸더니 — **에러가 0건이었다.** 단순히 strict만 켜는 작업인 줄 알았는데, 막상 빌드를 돌리니 에러가 안 나서 그동안 짜둔 null 가드랑 타입 정의가 이미 strict를 통과하고 있었다는 걸 알게 됐다.

이게 의미하는 게 컸다. strict 에러 0건은 **그동안 코드를 제대로 짜왔다는 후행 증명** 이었다. null 체크를 빼먹지 않았고, 타입을 `any`로 도망가지 않았고, 옵셔널 처리를 제대로 했다는 게 strict라는 객관적인 잣대로 확인된 거였다. 베테랑 리뷰의 🔴 0건이 strict 0건으로 한 번 더 뒷받침된 셈이었다.

## 접근성 3조각 — 청각장애인 페르소나와 직결

본 작업의 핵심. 접근성을 두 PR로 나눠서 처리했다.

### 1. 상태 색상 단독 의존 해소 (WCAG 1.4.1)

모바일 화면에서 알림 상태(정상 / 경고 / 화재경보)를 **색깔 점으로만** 구분하고 있었다. WCAG 1.4.1(색상만으로 정보를 전달하지 말 것) 위반이었고, 색각 이상이 있거나 스크린리더를 쓰는 사용자한테는 그 점이 무슨 의미인지 전달이 안 됐다.

```tsx
// Header.tsx — 상태 dot에 aria-label 부여
<span
  className={statusDotClass}
  role="img"
  aria-label={statusLabel}   // "정상" / "경고" / "화재경보"
/>
```

색깔 점에 `aria-label`을 붙여서 스크린리더가 상태를 읽어주도록 했다. 화면으로 보는 사용자한텐 색깔로, SR 사용자한텐 텍스트로 — 같은 정보가 두 채널로 전달되게.

### 2. aria-live — "신규 도착만" announce

청각장애인 사용자한테 새 알림이 왔다는 걸 어떻게 알릴까. 화면 폴링(3초)으로 카드는 갱신되는데, 스크린리더 사용자는 새 카드가 추가된 걸 능동적으로 인지하기 어려웠다. 그래서 `aria-live` region으로 신규 알림을 announce하기로 했다.

여기서 핵심 로직이 **"신규 도착분만"** 읽어주는 거였다. 폴링할 때마다 전체 알림 리스트가 다시 오는데, 그걸 매번 다 읽으면 SR이 끊임없이 떠들어서 못 쓴다. 그래서 이미 본 알림을 추적하는 ref를 두고, 신규 도착분만 필터링했다.

```tsx
// NotificationAnnouncer.tsx (구조)
const seenRef = useRef<Set<string>>(new Set());
const initializedRef = useRef(false);

useEffect(() => {
  // 초기 마운트는 무음 (기존 알림 11건을 다 읽지 않게)
  if (!initializedRef.current) {
    notifications.forEach(n => seenRef.current.add(n.id));
    initializedRef.current = true;
    return;
  }
  // 신규 도착분만 announce
  const fresh = notifications.filter(n => !seenRef.current.has(n.id));
  fresh.forEach(n => seenRef.current.add(n.id));
  if (fresh.length > 0) announce(fresh);
}, [notifications]);
```

그리고 announce 우선순위도 나눴다. **화재경보는 `assertive`**(진행 중인 SR 발화를 끊고 즉시 읽음), **그 외(초인종/노크)는 `polite`**(현재 발화 끝나고 읽음). 화재경보는 생명과 직결되니까 즉시성이 우선이었다.

### 3. 키보드 — skip-link + drawer 포커스 트랩

키보드 / SR 사용자를 위한 두 가지. **Skip-to-content 링크** 로 반복되는 네비를 건너뛰고 본문으로 바로 점프할 수 있게 했고, **모바일 drawer에 포커스 트랩** 을 걸어서 메뉴가 열렸을 때 포커스가 drawer 밖으로 새지 않게 했다.

```tsx
// AppShell.tsx (구조)
<a href="#main-content" className="skip-link">
  본문으로 건너뛰기
</a>
<main id="main-content" tabIndex={-1}>
  {children}
</main>
```

drawer는 직접 짠 커스텀이었는데 포커스 트랩을 손으로 구현하기보다 radix Dialog로 감싸는 쪽을 택했다. 검증된 트랩 로직을 가져다 쓰는 게 안전했다.

### radix 자동 복원이 조용히 죽는 함정

여기서 베테랑 디테일 하나가 걸렸다. radix Dialog로 감싸면 포커스 트랩은 잘 되는데, 본 프로젝트처럼 **외부 트리거(메뉴 버튼)** 로 drawer를 여는 구조에서는 닫을 때 포커스 복원이 조용히 죽었다. drawer를 닫으면 포커스가 메뉴 버튼으로 돌아가야 하는데, 아무 데도 안 가고 사라지는 거였다.

Playwright로 실측해서 발견했고(육안으론 안 보이는 종류), `onCloseAutoFocus`로 명시적 복원을 보강했다.

```tsx
<Dialog.Content
  onCloseAutoFocus={(e) => {
    e.preventDefault();
    triggerRef.current?.focus();   // 메뉴 버튼으로 명시 복원
  }}
>
```

"라이브러리가 알아서 해주겠지"라고 가정한 부분이 실제로는 no-op이었던 케이스라, 실측으로 확인하지 않았으면 그냥 넘어갔을 버그였다.

## 학습 18 발굴 — PR #6 히스토리가 꼬인 사건

이번 작업에서 가장 많이 배운 건 사실 접근성 코드가 아니라, **git 히스토리가 꼬인 사건** 이었다.

### 화면 한 줄에서 시작된 catch

B-1a(PR #6)를 GitHub 웹에서 squash 머지하고 나서, PR 화면에 뜬 한 줄을 우연히 봤다.

```
This pull request merged 2 commits into main
```

"merged 2 commits"? B-1a는 분명히 1개 PR이었는데 왜 2 커밋이 머지됐다고 뜨지, 싶어서 `git log`를 실측했다. 확인해보니 로컬 main이 직전 PR(B-0, PR #5)을 안 끌어온 상태로 뒤처져 있었고, PR #6 브랜치가 그 뒤처진 main 위에서 갈라져서 **PR #5의 strict 커밋을 같이 끌고 들어간** 거였다.

### 왜 꼬였나

원인은 단순했다. **GitHub 웹에서 PR을 squash 머지하면 remote main에 새 해시가 생기는데, 로컬 main은 그걸 모른다.**

- B-0(PR #5)를 웹에서 squash 머지 → remote main에 새 커밋 `56e44b8` 생성
- 근데 로컬 main은 그 전 상태 그대로
- 그 로컬 main 위에서 B-1a 브랜치를 따니까, B-1a가 갈라진 지점이 이미 remote보다 뒤처진 상태
- B-1a를 머지하니 squash로 사라진 PR #5 원본 커밋이 PR #6에 딸려 들어가고 merge commit까지 생김

### 복구

다행히 히스토리 rewrite 없이 fast-forward로 복구됐다.

```
$ git checkout main
$ git pull origin main
Updating e9b9879..3408d97
Fast-forward
```

`Fast-forward`로 떴다는 게 핵심이었다 — rewrite가 0건이라 안전하게 정렬됐다는 뜻이었다.

### 영구 반영 — "git pull 폐지" 룰의 예외

이전에 "동일 로컬 머신에서는 매번 `git pull` 안 해도 된다"는 룰을 세워뒀었는데(불필요한 pull이 흐름을 끊으니까), 이 사건으로 그 룰에 **명시적 예외** 가 생겼다.

> GitHub 웹에서 PR을 squash 머지한 직후에는 반드시 git checkout main && git pull origin main.

웹 머지 = remote main에 새 해시가 생기는 시점이니까, 다음 feature 브랜치를 따기 전에 로컬 main을 무조건 동기화해야 했다. 이걸 decisions.md 카테고리 20과 프로젝트 지침 Git 섹션에 학습 18로 박았다.

정적 가정(로컬 = remote)이 웹 머지라는 이벤트로 무효화된 사례였는데, 이게 36편의 "정적 기록이 시간 지나 무효화" 패턴이랑 정확히 같은 결이었다. 그때는 `/tmp` venv가 재부팅으로 날아갔고, 이번엔 로컬 main이 웹 머지로 뒤처졌다. **마지막으로 맞춰둔 상태가 어떤 이벤트로 깨졌는데 그 변화를 인지 못 하면 사고가 난다** 는 거.

## AI가 박은 것도 catch 대상이다

이번 작업에서 한 가지 원칙이 또 작동했다. **AI(Claude / Claude Code MCP)가 박아둔 것도 검증 대상** 이라는 거.

- 위임 프롬프트에 박아둔 노션 DB3 ID 추정값이 틀려서, MCP가 실제 노션 API로 실측해서 정정했다.
- 그리고 stats 폴링 배율도 — 이전에 AI가 "2중 폴링"으로 SSoT에 박아뒀던 값이 실제로는 **3중(StatsPage + Header 등) + announcer 1 = 4중** 이었고, 베테랑 리뷰가 이걸 실측으로 정정했다.

AI가 SSoT에 박은 값이라고 해서 그게 검증을 면제받는 게 아니었다. 사람이 박은 가정이든 AI가 박은 가정이든, 실제 코드 / 실제 API / 실제 git log로 대조하지 않으면 틀린 채로 굳어진다는 게 또 한 번 확인됐다.

## 정리하면

기능적으로 다 됐다고 생각한 대시보드를 "마무리"하려고 보니, 정작 마무리해야 할 건 코드 품질과 접근성이었다. 베테랑 리뷰로 🔴 0건을 정직하게 확인하고, strict를 토대로 깔고(에러 0건으로 그동안의 코드 품질이 증명됨), 접근성 3조각(색상 의존 해소 / aria-live 신규만 announce / 키보드 + radix 복원)을 청각장애인 페르소나에 맞춰 채웠다.

그리고 예상 못 한 git 꼬임 사건에서 학습 18을 건졌는데, 화면의 "merged 2 commits" 한 줄을 그냥 지나치지 않고 git log로 실측한 게 시작이었다. 정적 가정이 이벤트로 무효화되는 패턴, AI가 박은 것도 검증 대상이라는 원칙 — 둘 다 이번에 한 번 더 작동했다.

다음은 남은 UI polish + 브레드보드 확보 후 마이크·ToF 결선이다.
