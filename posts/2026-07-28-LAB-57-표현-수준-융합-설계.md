## 파인튜닝한 embed_audio와 audio_tower을 그대로 사용하지 못 하는 이유

이전에 짧은 발화로 인한 환각현상을 완화시키기 위해 파인튜닝한 embed_audio와 audio_tower을 그대로 사용하지 못 하는 이유.

**[ audio_tower(귀) ]**

- audio_tower는 예를 들어 3초짜리 음성이 들어오면 3초를 통째로 삼키지 않고 잘개 쪼갬
- 짧은 조각으로 끊어서 조각 하나하나마다 "이 순간 소리가 어떤가"를 숫자 벡터로 뽑음
- 따라서 귀가 최종적으로 뱉는 것은 1000차원 벡터가 수백 개 줄지어 있는 줄(시퀀스)
- 귀의 출력은 점 하나가 아닌 쭉 이어진 줄 -> 길이가 발화마다 들쭉 날쭉

**[ embed_audio(통로/번역기) ]**

- embed_audio는 위에서 뱉은 시퀀스를 받아서 LLM이 알아듣는 임베딩 공간의 단어 자리(soft token)으로 번역해서 끼워넣음
- 즉, 통로는 귀가 뱉은 시퀀스를 LLM이 알아듣는 방식으로 번역해주는 번역기

하지만 본 실험에서 사용하는 음향 벡터는 발화 1개당 126차원 딱 하나

차이점)

1. 통로는 수백개짜리 줄을 기대하는데 본 실험은 점 1개를 내밈
2. 통로 입력 구멍은 1000차원인데 본 실험은 126차원
3. 이전 통로가 학습한 것은 audio_tower가 뱉은 생짜 프레임 특징과 LLM 공간의 대응관계 -> 하지만 본 실험은 화자 정규화까지 거친 요약 통계

**[ 결론 ]**

126차원을 LLM 임베딩 공간으로 보내려면 embed_audio를 재활용하는 것이 아니라 본 실험 용 새 번역기(projection)을 설계해야 함

## 1. 개념 정리

**[ embedding ]**

- 임베딩: 뜻을 숫자 벡터로 바꿔 놓은 것
- 임베딩 차원: 숫자 벡터의 길이

뜻이 비슷한 단어는 벡터 공간에서 가까이 놓이도록 학습돼 있음. 즉, 임베딩은 단순한 번호표가 아니라 뜻의 지도 위 좌표 -> LLM은 이 좌표들 사이의 거리 및 방향을 계산해서 문장을 이해

**[ projection ]**

- 투영: 차원이 다른 벡터를 다른 차원으로 옮겨주는 변환기

## 2. 실험 설계

### 비교축: 융합-진짜 vs 융합-placebo

**[ 비교축을 프롬프트 vs 융합이 아닌 융합-진짜 vs 융합-placebo로 한 이유 ]**

핵심 질문: "델타가 (+)로 나오면 그게 정말 오디오 덕분일까?"

- 이전 프롬프트 실험에서는 gemma를 학습시키지 않음(제로샷) -> 그래서 텍스트 vs 텍스트 + 음향을 비교했을 때 둘의 차이는 순수하게 "음향 정보를 줬냐 안 줬냐"에서만 옴

하지만 본 실험의 번역기인 projection은 학습을 시켜야 돌아감

- 126차원을 어떻게 2560차원으로 옮길지, 그 변환 규칙을 배워야 함

학습 자체가 점수를 올려버림

- gemma가 학습 과정에서 해당 데이터셋에 익숙해짐 -> 즉, 델타가 (+)로 나와도 오디오가 도와서인지 그냥 학습을 시켜서인지 구분이 안 됌

그래서 가짜벡터가 등장

- 학습 효과를 양쪽에 똑같이 깔아버리고 오디오 진짜/가짜만 다르게 함
- 모델A: projection에 진짜 어조 벡터를 넣고 학습
- 모델B: projection에 가짜 벡터를 넣고 학습(같은 감정 안에 순서만 뒤섞은 것)

진짜 = placebo → 오디오는 기여 0. 델타가 +로 나왔어도 그건 전부 학습효과였던 것.
진짜 > placebo → 이 격차가 곧 "오디오가 순수하게 기여한 몫". 학습효과를 걷어내고도 남은 진짜 실력.

## 확인 사실

**[ gemma-4-E4B-it 오디오 경로 실물 확인 (verify-first, meta device 구조 조회 + transformers 소스 대조) ]**

임베딩 차원 = 2560

- text_config.hidden_size = 2560
- 우리가 만들 projection의 "도착 차원"이 이걸로 고정됨: 126 -> projection -> 2560

오디오 경로 모듈 실명 (model 내부 구조)

- audio_tower (Gemma4AudioModel) = 귀. wav(mel)를 프레임 시퀀스로 변환
- embed_audio (Gemma4MultimodalEmbedder) = 통로. 인코더 출력을 LLM 임베딩 공간으로 번역
- 차원 체인: audio_tower 내부 1024폭 -> output_proj(1024->1536) -> embed_audio 입력 1536 -> Linear(1536->2560) -> 2560
- ★정정: embed_audio 입력은 1024가 아니라 1536 (내 기억 1024는 틀림. output_proj_dims=1536, config.json 실물 대조로 확인)
- 결론은 불변: embed_audio는 1536차원 입력 전용이라 우리 126차원 벡터에 재활용 불가 -> 새 projection 필요

**[ gemma의 오디오 주입 방식 = 자리표시자 갈아끼우기 ]**

비유: 행사장 예약석 시스템

- LLM은 소리를 직접 못 먹음. LLM이 먹는 건 임베딩(뜻의 좌표)뿐 -> gemma는 문장에 "여기 오디오 들어올 자리"라는 팻말만 미리 꽂아둠

1단계: 빈 자리(팻말) 심기

- 문장을 토큰화할 때 소리 들어갈 곳에 audio_token(258881) 특수표시를 심음
- `[이][오디오][258881][어떤][감정][이야][?]` ← 258881이 팻말 자리
- 예약석에 "예약석" 팻말만 놓는 것

2단계: 임시로 아무거나 채우기

- LLM에 들어가려면 모든 자리가 임베딩이어야 함. 근데 팻말 자리는 아직 알맹이 없음
- 그래서 일단 pad 임베딩(의미없는 채움용 벡터)으로 임시로 채워둠
- 손님 아직 안 온 빈 예약석 상태

3단계: 진짜 오디오로 갈아끼우기 (masked_scatter)

- audio_tower(귀) -> embed_audio(통로) 거쳐 2560차원 오디오 임베딩 완성
- 아까 pad로 채웠던 팻말 자리를 진짜 오디오 임베딩으로 바꿔치기
- masked_scatter = 갈아끼우는 도구
  - mask(마스크) = 어느 자리 바꿀지 표시한 지도 (audio_token 자리만 True)
  - scatter(뿌리다) = 표시된 자리에만 새 값 뿌리기
  - -> "예약석 표시된 자리에만 골라서 오디오 손님 앉혀라". 텍스트 자리는 그대로 둠

주입 지점: inputs_embeds 뽑은 직후, language_model 호출 전

- 순서: 문장 -> 임베딩 변환(inputs_embeds) -> [여기서 오디오 갈아끼우기] -> LLM 본체가 읽음
- LLM 본체는 오디오가 이미 앉혀진 완성된 임베딩 줄을 받음 -> "원래 거기 있었네" 하고 자연스럽게 읽음

이미지/비디오도 동일 패턴 (get_placeholder_mask + masked_scatter)

★우리한테 결정적인 이유

- 우리도 똑같이 하면 됨: 문장에 audio_token(258881) 팻말 심고 -> projection이 만든 126->2560 어조 임베딩을 -> 그 팻말 자리에 masked_scatter로 앉힘
- gemma가 이미 만들어둔 "예약석 시스템"을 그대로 빌려 씀. 새 배선 발명 불필요

우리 projection이 지켜야 할 스펙 (실물 제약에서 도출)

- 입력 126 -> 출력 2560 (masked_scatter 대상은 반드시 2560차원)
- 심는 soft token 개수(N) = 문장에 심은 audio_token 자리 수와 정확히 일치해야 함 (forward 내 개수 검사 있음)

## 주입 구조 결정 (k / 분할 / projection)

**[ 선행연구 3편 조사(StyleTalk, ParalinGPT, Dual Information SLM) 후 확정 ]**

전제 정정

- StyleTalk 저장소는 데이터셋만 공개. 모델/Connector 코드 없음(README가 TBA). "코드공개 참조대상"은 틀린 정보였음
- 따라서 StyleTalk 수치는 전부 논문 본문 기술이지 코드 실물 아님

② k토큰 개수 = 1개로 확정

- 선행 3편의 k는 사실상 1 또는 10뿐. 그 사이값(2,4,8)이나 그 이상은 전례 0건 → 인계의 "k=4~8"은 근거 없는 숫자였음
- k=10 사례 두 개(StyleTalk-chunk, Dual-Info)는 원래 시퀀스였던 걸 10개로 유지/축약한 것. 1개를 10개로 늘린 게 아님
- 126차원은 시퀀스 없는 요약 1개 → 전례상 대응되는 건 k=1(ParalinGPT, StyleTalk-utt)
- 근거 3겹: (1)전례 부합 (2)정보량 논리 - 고정요약이라 토큰 수 늘려도 정보량 안 늘어남 (3)귀속 명확 - 단순할수록 진짜vs placebo 해석 깨끗

③ 항목별 분할 = 안 함 (k=1이면 자동)

- "고정길이 벡터 1개를 여러 토큰으로 쪼개는" 연산을 한 논문 0건
- StyleTalk이 k=10에서 나았던 이유를 저자가 "토큰 수가 많아서"가 아니라 "chunk가 평균보다 정보가 많아서"로 설명(§4.3)
- 126은 이미 고정 요약 → 4조각 내도 정보 총량 동일, 나눠 담는 것뿐. "쪼개면 낫다" 근거 우리한텐 성립 안 함

① projection 구조 = gemma embed_audio 복제형

- RMSNorm(126, scale 없음) → Linear(126 → 2560, bias 없음)
- 3편 모두 마지막 단계 Linear 1층, 비선형 MLP 쓴 데 0건. 정규화는 StyleTalk만 LayerNorm
- gemma의 embed_audio 자체가 이미 "RMSNorm(scale없음) + bias없는 Linear 1층" 구조
- → "norm + Linear 1층"은 선행연구 표준 + gemma 기존 설계 양쪽에 동시 부합. 새로 발명 안 하고 gemma 것을 126→2560으로 복제

나중 카드 (폐기 아니라 미뤄둠, phase 1 성공 후 ablation)

- 다중토큰 확장(126 → k×2560 후 reshape): 전례 미확인 영역이라 phase 1엔 제외
- 항목별 분할(피치/MFCC 토큰 나눠 뭐가 기여했나 ablation)
- 첫 실험은 가장 단순하고 해석 깨끗한 것으로. 복잡한 변형은 단순한 게 되는 걸 확인한 뒤 얹음

미리 박아둔 경고 (phase 1 진행 중 문제 생기면 의심할 지점)

- 학습 잘 안 되면 → 20배 확대(126→2560) 안정성 의심. 전례는 1024→1024, 768→4096 등 훨씬 작은 비율뿐, 20배 사례 없음
- 오디오가 무시되는 느낌이면 → 위치 고정 붕괴 의심. Dual-Info는 soft prompt 위치를 일부러 흔들어 task 전용 벡터로 붕괴하는 걸 막음. audio_token 자리는 항상 고정이라 이 위험 있음

확정 요약

- k = 1 (audio_token 자리 1개)
- 분할 없음 (126 통째로)
- projection = RMSNorm(126, no scale) → Linear(126→2560, no bias)

우리 projection = gemma embed_audio와 소스 레벨 동일 확증

- Gemma4MultimodalEmbedder = RMSNorm(scale없음) → Linear(bias없음). 우리 것은 차원만 126→2560
- tone_norm = Gemma4RMSNorm(126, eps=audio_config.rms_norm_eps, with_scale=False) → 파라미터 0개
- tone_proj = nn.Linear(126, 2560, bias=False) → 학습 대상은 이 weight 하나뿐

결정1: boa/eoa로 감싼다 ([256000, 258881, 258883])

- 비용 0에 가깝고 모델 로직상 부작용 없음(모델은 258881만 봄)
- gemma 정식 오디오 학습이 항상 boa…audio…eoa로 감쌈(L219) → 얼린 LLM이 오디오 자리를 자연스럽게 인식할 확률 높임
- 리스크 비대칭: 감싸서 나빠질 시나리오 거의 없음 / 안 감싸면 "LLM이 오디오 자리 못 알아봄" 위험

결정2: projection 직접 초기화 (post_init 재호출 안 함)

- nn.init.normal_(tone_proj.weight, std=config.initializer_range)
- post_init 2회 호출은 미검증 → 동작 명확한 직접 초기화 선택(verify-first)
- 새 파라미터는 tone_proj.weight 하나뿐이라 전체 post_init 불필요
- ★초기화 스케일은 20배 확대 학습 안정성과 연결. 학습 초반 loss 튀면 이 스케일 제일 먼저 의심

학습 설정 (확정)

- audio_tower / embed_audio / language_model 전부 requires_grad_(False)
- tone_proj.weight만 학습 (tone_norm 파라미터 0개)
- save_pretrained 시 model.tone_proj.weight 키로 저장

남은 미확인 (코드 단계에서 실증할 것)

- 실제 gemma 가중치로 로드→generate 엔드투엔드 (조사는 합성 텐서 로직검증만)
- audio/boa/eoa 토큰 문자열 표기 (id로 우회하므로 무관)
- 126→2560 20배 확대 학습 안정성 (선행연구 전례 없음)
