교수님이 말씀하신 토크나이저 관련해서 한국어가 토크나이저에서 어떻게 토큰으로 쪼개지는지를 관찰하려고 한다.

## 1. 토크나이저 실험

```python
samples = [
    "안녕하세요. 오늘 회의를 시작하겠습니다.",
    "바야흐로 칠월입니다.",
    "구십",
    "Hello, let's start the meeting today.",
]

for text in samples:
    ids = tokenizer.encode(text, add_special_tokens=False)
    toks = tokenizer.convert_ids_to_tokens(ids)
    decoded = tokenizer.decode(ids)
    print(f"원문: {text}")
    print(f"  토큰 {len(toks)}개: {toks}")
    print(f"  IDs: {ids}")
    print(f"  round-trip 일치: {decoded == text}  | decoded: {decoded!r}")
    print()
```

```

  토큰 8개: ['안녕하세요', '.', '▁오늘', '▁회', '의', '를', '▁시작하겠습니다', '.']
  IDs: [61659, 236761, 31694, 38012, 237281, 237482, 173161, 236761]

  IDs: [238505, 238215, 242485, 237323, 236743, 242508, 238174, 15245, 236761]

  토큰 2개: ['구', '십']

  round-trip 일치: True  | decoded: "Hello, let's start the meeting today."
```

결과를 확인해보면, 테스트한 한국어 문장 모두 encode→decode가 원문을 정확히 복원한다. 만약 어떤 글자를 날리거나 깨진 조각으로 쪼갰다면 decode에서 원문이 복원되지 않았을 것이다.

토큰 분할 양상을 확인해보면, 빈해("회의를"→▁회/의/를), 희귀·문어체는 음절 단위로 분해("바야흐로"→바/야/흐/로). ▁ 기호는 SentencePiece의 어절 시작(띄어쓰기) 표시일 뿐 오류가 아니며 decode 시 공백으로 정상 복원된다.

여기서 "구십"의 경우를 살펴보자. 대표 환각 트리거였던 "구십"(ref "구십" → 긴 환각 문장 생성, CER 19.5)이 토큰화 자체는 완벽(['구','십'] 2토큰, round-trip True)이다. 즉, 동일한 짧은 입력이 텍스트 경로에선 멀쩡한데 ASR에선 심한 환각을 유발한다. **환각 원인이 토크나이저·텍스트가 아니라 오디오 경로임**을 확인할 수 있다.

## 2. 오디오 데이터 흐름

```
[입력]
오디오 ──→ 오디오타워 ──→ 오디오 임베딩(벡터) ─┐
                                              ├─→ LLM ──→ 출력 토큰 ──→ decode ──→ 전사 텍스트
텍스트 프롬프트 ──→ 토크나이저 ──→ 토큰 임베딩 ─┘
```

입력이 두 갈래로 따로 들어온다. 텍스트는 원래 이산 기호(글자처럼 딱딱 떨어지는 단위)라 토크나이저로 정수 ID를 매기고 임베딩 테이블에서 벡터를 꺼내온다. 오디오는 연속 신호(파형)라 토큰화 대상 자체가 아니고 오디오 타워(인코더)가 신호를 직접 벡터로 계산한다.

오디오 타워가 하는 일: 6초 오디오 입력 → 짧은 시간 조각들로 나눔 → 각 조각을 임베딩 벡터 하나로 → 벡터 시퀀스를 뱉음. `<|audio|>` placeholder가 끼어드는 방식으로, 프롬프트에 오디오 벡터 개수만큼 placeholder 토큰 임베딩이 들어가고 실제 forward 때 그 N칸을 오디오타워가 만든 벡터로 덮어쓴다.

LLM은 그냥 벡터 시퀀스 처리기라 벡터가 토큰에서 온 건지 오디오 타워에서 온 건지 구분하지 않는다. 출력은 LLM이 매 스텝 다음 토큰 확률 분포를 예측해 하나씩 짓고 붙이는 결과물이며, 이 출력 토큰열을 decode하면 전사 텍스트가 된다.

환각이 정확히 어디서 터지나: **생성 스텝**. 각 생성 스텝은 오디오 벡터 + 지시 + 지금까지 생성한 토큰에 조건부다. 오디오 벡터가 빈약하면(짧은 클립 = N이 작고 정보 적음) → 조건이 약해짐 → 예측이 오디오가 아니라 모델 prior + 프롬프트에 지배됨 → 환각 토큰을 생성한다.

## 3. 태그 실험

오디오 구간이 어떻게 표시되는지 확인하기 위해 오디오 태그(boa/audio/eoa) vocab id를 조회했다.

오디오 구간이 3종 태그로 구획된다 — boa(`<|audio>`), audio(`<|audio|>`), eoa(`<audio|>`)가 시작-본체-끝 구조다. 실제 입력은 `[256000][258881 × N][258883]` 형태로 들어가고 가운데 N칸을 오디오타워 벡터가 덮어쓴다. 모든 태그가 단일 정수 ID인 것으로 보아 등록된 atomic 토큰(더 이상 안 쪼개지는 토큰)임을 알 수 있다(이미지도 동일 구조).

추가로 실제 1초짜리 더미 오디오를 넣고 처리된 토큰 시퀀스에서 boa/audio/eoa가 각각 몇 개 나오는지 세어 구조를 확인했다. 실제 1초 오디오 입력 시 토큰 시퀀스가 `[boa][audio×25][eoa]`로 펼쳐지고, placeholder 개수 N(≈25/초)은 오디오 길이에 비례한다.

정리하면, 오디오 구간의 태그 처리는 모델 어휘(vocab)에 boa/audio/eoa가 전용 special token으로 예약돼 있고, 오디오 입력이 들어오면 프로세서가 `[boa][audio×N][eoa]` 구조를 자동으로 깔아준다. 따라서 오디오의 시작과 끝이 입력 규격 차원에서 이미 구조적으로 명시되므로 **프롬프트에 별도 텍스트 태그로 오디오 경계를 명시할 필요가 없다.**
