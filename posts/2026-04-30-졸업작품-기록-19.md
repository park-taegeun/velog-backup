# "이론상 가능합니다"는 부족하다. 
Claude Code로 카메라+마이크 동시 동작을 검증하다

> 부품 발주 전에 가장 큰 리스크를 먼저 검증하고 싶었고, Claude Code MCP로 ESP-IDF 드라이버 코드 레벨까지 파고들었다.

---

## 가장 큰 의심 — "정말 동시에 될까?"

부품 리스트를 정리하면서 결정적인 의심 하나가 남았다.

**XIAO ESP32-S3 Sense 보드에서 카메라와 외장 INMP441 마이크를 동시에 돌릴 수 있을까?**

이게 안 되면 시스템 전체가 무너지는 구조였다. A-1+A-3 통합 컨셉이 사진 + 자막을 동시에 캡처해야 하는데, 카메라가 마이크 페리페럴을 점유한다면 2차 알림 자체가 불가능해진다.

22주 일정에서 PoC 1주차에 검증하기로 했지만, 부품 도착 전에 미리 답을 알고 싶었다. 혹시 안 되는 거면 1차 발주 자체를 바꿔야 하니까.

---

## 일반 검색은 위험했다

처음엔 그냥 "XIAO ESP32-S3 Sense camera microphone simultaneous"로 검색해봤는데 답답했다.

- Seeed 공식 wiki: 카메라 단독 예제 / PDM 마이크 단독 예제만 있음
- 일반 블로그: "이론상 가능합니다" 같은 무책임한 답변
- 포럼 글: "I2S0가 충돌한다"는 우려글에 답변 없음

이대로면 부품 사고 PoC 1주차 첫날에 "안 됩니다" 발견하는 상황이 올 수 있었는데, 22주 일정에서 1주 손실은 치명적이었다.

그래서 Claude Code에 깊이 있는 조사를 시켰는데, 프롬프트를 그냥 "조사해줘"로 던지지 않고 MCP를 명시적으로 활용하도록 지정했다.

## 결정적 발견 — 카메라는 I2S가 아니라 LCD_CAM을 쓴다

Claude Code가 ESP-IDF 공식 esp32-camera 드라이버 코드를 직접 확인했는데, 결정적인 차이가 나왔다.

**구형 ESP32 (`target/esp32/ll_cam.c`)**:
```c
#include "soc/i2s_struct.h"
I2S0.conf2.camera_en = 1;     // I2S0를 카메라 모드로 점유
I2S0.conf.rx_start = 1;
periph_module_enable(PERIPH_I2S0_MODULE);
```

**ESP32-S3 (`target/esp32s3/ll_cam.c`) — 우리 보드**:
```c
#include "soc/lcd_cam_struct.h"   // LCD_CAM 페리페럴
#include "soc/gdma_struct.h"       // GDMA (I2S DMA가 아님)

LCD_CAM.cam_ctrl1.cam_start = 1;
gdma_new_ahb_channel(...);
periph_ll_enable_clk_clear_rst(PERIPH_LCD_CAM_MODULE);
```

해석이 명확했다.

- 구형 ESP32: 카메라가 I2S0 점유 → I2S 마이크 동시 사용 어려움
- **ESP32-S3: 카메라가 LCD_CAM + GDMA 사용 → I2S0와 I2S1 둘 다 자유**

"이론상"이 아니라 코드상 명백히 확인된 사실이었다.

## 보조 증거 — 검증된 작동 펌웨어 5건

코드 레벨 분석에 더해 GitHub에서 실제 작동 사례 5건을 발견했다.

| # | 출처 | 핵심 |
|---|------|------|
| 1 | Lokch777/EE3070-Design-Project | ESP32-S3 + INMP441 + 스피커 동시 동작 졸업프로젝트 |
| 2 | omanandswami2005/omni-agent-hub | 카메라+마이크 권장 핀맵까지 명시 |
| 3 | eulicesl/omi-fork PR#10 | "No resource conflicts (separate DMA, cores)" 명시 |
| 4 | sn0wmn/esp-marcus-bot | `board=seeed_xiao_esp32s3` 정확히 같은 보드 |
| 5 | derek-miller/esphome-configs | Waveshare ESP32-S3 + INMP441 동작 |

특히 1번 Lokch777 사례가 결정적이었는데, 졸업프로젝트라 비슷한 상황이었고 카메라 + 마이크 + 스피커까지 동시에 돌아가는 펌웨어가 실제로 작동 중이었다. 우리 시나리오보다 더 어려운 경우가 이미 검증된 셈이었다.

Seeed Forum에서도 흥미로운 걸 발견했는데, 처음 글쓴 사람이 "I2S0 충돌이 우려된다"는 글을 올렸다가 본인이 직접 정정했다.

> "Found out that although camera lib for ESP32 uses I2S0 DMA, the ESP32S3 uses GDMA, so PDM mic can be used simultaneously"

코드 분석과 완전히 일치하는 답변이었다.

## 새로 발견한 함정 3가지

조사 보고서 신뢰도가 높았는데, 그 안에서 PoC 시 주의할 함정도 함께 발견됐다.

**함정 1: INMP441 power-up noise 250ms**
I2S 클럭 시작 시 INMP441이 power-down에서 깨어나며 약 250ms 동안 노이즈가 발생했다. 첫 12-14 DMA buffer 폐기 코드가 필수였다.

**함정 2: 핀 배선의 SD 카드 충돌**
원래 INMP441에 D1/D2/D3 할당 예정이었는데, D2(GPIO3)가 SD 카드 CS 핀과 충돌하는 게 확인됐다. D6/D7/D0으로 이동이 권고됐는데, 핀 배선 재정리는 다음 글에서 더 자세히 다룰 예정이다.

**함정 3: 멀티코어 활용 권고**
Lokch777 패턴이 카메라(메인 루프) + 마이크(Core 0) + 다른 작업(Core 1)으로 분리하는 구조였는데, `xTaskCreatePinnedToCore()` 사용이 권고됐다.

## 결론 — 🟢 가능, Plan A 그대로 진행

이 한 번의 조사로 22주 일정의 가장 큰 리스크가 거의 해소됐다. 부품은 그대로 발주하기로 했고, PoC 1주차에 위 함정 3가지만 신경 쓰면서 통합 검증하면 됐다.

1시간 정도의 Claude Code 조사 시간으로 PoC 1주차의 1주 손실 가능성을 차단한 셈이었다.

---

## 이 경험에서 배운 것

세 가지가 남았다.

첫째, **AI한테 "그냥 검색해줘"는 위험하다.** 1차 증거(코드/사례)를 명시적으로 요구해야 의미 있는 답변이 나왔다.

둘째, **공식 문서만 보고 결정하면 안 된다.** Seeed 공식은 카메라 단독, 마이크 단독만 다루고 동시 사용 가이드는 없었는데, 그게 "안 된다"는 의미가 아니었다. 코드 레벨로 들어가야 진짜 답이 나왔다.

셋째, **PoC 진입 전 사전 검증의 가치.** 부품 사기 전에 1시간 투자해서 1주 시간을 산 셈이었다.
