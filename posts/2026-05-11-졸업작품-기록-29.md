## 출처 catch 검증 — 학습 13 적용

5/9 Khangura 6개 함정 사례에서 출처 전체 항목을 사전에 확인하지 않으면 부분 인용으로 끝난다는 학습 13이 정착됐는데, 이번 작업 위임에도 강제로 적용했다.

INMP441 datasheet 6가지, ESP-IDF I2S 문서 5가지, 라이브러리 선택지 2가지, 총 13개 항목을 모두 catch 검증했고 13/13 통과였다.

그 중 하나가 눈에 띄었는데, INMP441 datasheet의 파워업 타이밍이었다.

> **2^18 clock cycles to restart after VDD applied**

계산해보면 16kHz × 64 = 1.024MHz BCLK 기준으로 **2^18 / 1,024,000 = 256ms ≈ 250ms** 였다. 코드에 이미 박아둔 250ms 상수가 datasheet 수치와 정확히 일치했는데, 이전에 사전 검증에서 잡아둔 값이 검증된 셈이었다.

## 첫 시도 — 공식 권장 API가 컴파일 fatal error를 뱉었다

ESP-IDF 5.x 공식 문서는 `driver/i2s_std.h` (new API)를 권장하고 `driver/i2s.h` (legacy)는 deprecated라고 명시하고 있었다. 당연히 공식 권장을 따랐는데,

```
fatal error: driver/i2s_std.h: No such file or directory
```

처음엔 경로 문제인가 싶었는데, 패키지 내부를 직접 확인해봤다.

```
find ~/.platformio/packages/framework-arduinoespressif32/tools/sdk/esp32s3/include/driver/include/driver/
```

결과: `i2s.h`만 존재하고 `i2s_std.h`는 없었다. arduino-esp32 v3.20017 SDK 패키징이 새 API 헤더를 아직 노출하지 않은 거였다. 공식 문서 권장과 실제 패키지 상태가 달랐던 것이었다.

legacy `driver/i2s.h`로 fallback하고 다시 컴파일했는데, deprecation warning 0건에 바로 통과됐다. **이게 학습 15의 발굴 지점이었다.**

## 학습 14/15/16 발굴 스토리

이날 작업에서 예상치 못한 학습 3건이 발굴됐는데, 단순 버그 수정이 아니라 위임 워크플로우 전체에 영향을 주는 메타 학습이었다.

### 학습 14: 위임 프롬프트 repo 구조 가정 검증 누락

**어떻게 발굴됐나**

위임 프롬프트를 작성하면서 카메라 작업 컨벤션을 인계 패키지 추상 표현 그대로 참조했는데, Claude Code MCP가 작업 시작 직후 "임의 결정 금지" 원칙을 자율 발동했다. 실제 카메라 v1/v2 작업이 `firmware/src/` 직접 + `build_src_filter` 격리 패턴이었는데, 위임 프롬프트는 `firmware/dummy_tests/camera_dummy/` 디렉토리 분리 가정으로 작성됐던 것이었다.

세 가지 옵션을 받았는데, 실제 카메라 패턴과 일치시키는 옵션 1을 채택했다.

**왜 발생했나**

인계 패키지의 "camera_dummy 컨벤션 일치"라는 추상 표현을 그대로 신뢰하고 5/9 실제 commit 내용을 직접 확인하지 않았던 게 원인이었다. 추상 표현이 실제 파일 경로를 대신할 수는 없었다.

**영구 반영**

위임 프롬프트 작성 시 인계 패키지 추상 표현은 신뢰하지 않고, `git log -p` 또는 GitHub 직접 확인으로 실제 컨벤션을 검증하는 절차가 추가됐다. decisions.md 카테고리 27 신설, 프로젝트 지침 원칙 7번 추가.

### 학습 15: packaging 제약 vs 공식 권장 분리 검증

**어떻게 발굴됐나**

위에서 설명한 `i2s_std.h` fatal error 상황이었는데, 공식 문서 권장값을 그대로 복붙했다가 실제 SDK에 헤더가 없다는 걸 직접 확인한 사례였다.

arduino-esp32 같은 wrapper SDK는 upstream ESP-IDF 변경을 즉시 반영하지 않는 구조인데, 이 패키징 상태를 검증하는 절차가 없었던 게 문제였다.

**4단계 검증 절차 영구 반영**

| 단계 | 내용 |
| --- | --- |
| 1 | 공식 권장값 확인 |
| 2 | 실제 패키지 헤더 노출 여부 확인 |
| 3 | 컴파일 통과 여부 확인 |
| 4 | 런타임 동작 확인 |

학습 13(출처 전체 항목 catch)의 보강 형태로 자리잡았다. 외부 출처 인용이 문서에만 해당되는 게 아니라 SDK 패키징 상태 검증에도 적용된다는 확장이었다. decisions.md 카테고리 28 신설, 프로젝트 지침 원칙 8번 추가.

마이그레이션 트리거는 arduino-esp32가 새 API 헤더를 노출하는 시점 또는 ESP-IDF 직접 사용으로 전환하는 시점으로 잡아뒀다.

### 학습 16: 위임 프롬프트와 실제 컨벤션 충돌 시 기존 컨벤션 우선

**어떻게 발굴됐나**

위임 프롬프트에 Serial race 방지 패턴으로 `while (!Serial && millis() < 2000) { delay(10); }`이 명시되어 있었는데, 실제 카메라 v1/v2 컨벤션은 `delay(SERIAL_BOOT_DELAY_MS=200)`이었다.

Claude Code MCP가 자율 판단으로 카메라 패턴을 우선 채택했는데, 이 판단이 맞았다. 위임 프롬프트는 일반론이고 기존 컨벤션은 검증된 패턴이라서 일관성 우선이 합리적이었다.

**영구 반영**

위임 프롬프트의 구체 코드 패턴이 기존 repo 컨벤션과 충돌할 때는 기존 컨벤션 우선이라는 원칙이 정착됐다. 예외는 기존 컨벤션이 명백한 오류일 때만이고, 그 경우에는 decisions-log entry로 변경 사유를 기록하도록 했다. decisions.md 카테고리 29 신설, 프로젝트 지침 원칙 9번 추가.

자체 검증 ② 리팩토링의 "기존 컨벤션 일치" 항목이 이 catch의 그물 역할을 하는 구조였다.

## 학습 3건의 공통점

14/15/16을 나란히 놓고 보면 공통된 패턴이 있었는데, 셋 다 **"추상 표현이나 공식 문서를 신뢰했다가 실제 환경에서 불일치를 발견한 사례"** 였다.
